## B. Notion Adapter Implementation

### Real-mode Entry Point
The NotionAdapter's real-mode execution path is through the `execute()` method which dispatches to specific action handlers based on the context.action parameter:
- search_pages (default)
- get_page
- create_page
- update_page  
- query_database

### Mock-mode Behavior
When no MCPManager is provided (or connection fails), the adapter operates in test/disconnected mode:
- `_default_tool()` raises NotImplementedError requiring MCP connection
- `connect()` returns False when MCPManager is None
- All operations that require connection will fail gracefully with ERROR ExecutionResults

### Connection Behavior
- Uses MCPManager via stdio transport to connect to Notion MCP server
- Connection established via `connect()` method which calls MCPManager.connect()
- Tool discovery performed automatically on first connection via `_discover_tools()`
- Connection state tracked via `_connected` boolean flag
- Cleanup via `disconnect()` method

### Authentication Behavior
Authentication is delegated to the MCP layer - the adapter itself does not handle authentication directly. The MCP server (when real) would handle Notion API authentication.

### Required Credentials
Based on the implementation and configuration:
- Notion API token (typically starts with "secret_" or similar pattern)
- Credentials are expected to be provided to the MCP server via environment variables or configuration
- The adapter itself does not store or handle credentials directly

### Required Environment Variables
From config/integrations.yaml (notion section):
- No explicit environment variables defined in the adapter code
- Configuration relies on MCP server to handle authentication
- Real mode requires: AIOS_REAL_INTEGRATION_ENABLED=1 (gated integration)
- Requires user resource: Notion API token (user_resource_present: false indicates not yet provided)

### API Endpoints (via MCP Tools)
The adapter exposes these MCP tool operations:
- search_pages: Search Notion pages by query
- get_page: Retrieve a Notion page by ID
- create_page: Create a new Notion page
- update_page: Update an existing Notion page
- query_database: Query a Notion database

### Request Methods
All operations use MCP's tools/call mechanism via the MCPManager.

### Payload Structure
Payloads vary by operation:
- search_pages: {"query": str, "parent": str|None, "limit": int}
- get_page: {"page_id": str}
- create_page: {"title": str, "parent_id": str, "content": dict, "properties": dict}
- update_page: {"page_id": str, "content": dict, "properties": dict}
- query_database: {"database_id": str, "filter": dict|None, "sorts": list|None, "limit": int}

### Page/Database Operations
- Read: search_pages, get_page
- Write: create_page
- Update: update_page
- Delete: NOT IMPLEMENTED (no delete_page method)
- Query: query_database (for database filtering)

### Timeout Handling
- Default timeout: 30 seconds (configurable via constructor)
- MCP calls wrapped in asyncio.wait_for() with timeout handling
- Timeout results in NotionTimeoutError → ERROR ExecutionResult

### Error Handling
- Custom error hierarchy: NotionError → NotionUnavailableError, NotionTimeoutError, NotionValidationError, NotionSecurityError, MalformedNotionResponseError
- All errors caught and converted to ERROR ExecutionResults (never propagate as exceptions)
- Network failures, timeouts, malformed responses all yield structured error results
- Missing resources (page not found) return SUCCESS with found=False (not error)

### Retry Behavior
- No automatic retry logic in the adapter
- Relies on MCPManager's auto_reconnect and max_retries configuration (3 retries)

### Size/Bounds Validation
- MAX_CONTENT_SIZE = 10240 bytes (10 KB)
- MAX_QUERY_LENGTH = 1000 characters
- MAX_SEARCH_RESULTS = 100
- Validation in _validate_content() and _validate_query() methods

### Sensitive-input Validation
- SENSITIVE_PROPERTY_KEYS frozenset: password, token, secret, api_key, apikey, authorization, credential, private_key, access_token
- SECRET_VALUE_PATTERNS regexes for API keys, Bearer tokens, password assignments
- Validation prevents sensitive data from being sent to Notion

### SecurityManager Gate
- The adapter validates input locally before making external calls
- No direct SecurityManager calls in the adapter (follows architecture boundary)
- Security validation happens at adapter level via _validate_content() and _validate_query()
- Real-mode gating controlled by config/integrations.yaml + AIOS_REAL_INTEGRATION_ENABLED=1

### Provenance Fields
All results include complete provenance:
- source: "notion"
- adapter: "notion_adapter" 
- operation: operation name (search_pages, get_page, etc.)
- correlation_id: UUID (resolved from ambient context or generated)
- execution_id: from caller context
- task_id: from caller context
- timestamp: ISO 8601 UTC
- request_id: UUID
- authority: "contextual"
- advisory: True
- trust_level: "untrusted"
- notion_timestamp: UTC ISO string

### Execution/Result Normalization
- All successful results wrapped in ExecutionResult with status=SUCCESS
- All error results wrapped in ExecutionResult with status=ERROR
- Findings array contains structured error information when applicable
- Raw data includes the actual Notion response with provenance marking
- Metrics collection for monitoring/debugging
