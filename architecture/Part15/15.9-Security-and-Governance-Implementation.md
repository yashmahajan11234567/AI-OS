## 2. Purpose and Scope

### 2.1 What This Document Does

This document translates the security and governance architecture established in Parts 0–14 into implementation-facing requirements. It specifies:

- How SecurityManager (EXISTING, Part 4 §4.7) is the sole enforcement authority
- How ABAC authorization (EXISTING, Part 4 §4.7.2/§4.7.4) is expressed and evaluated
- How IdentityProvider (EXISTING, Part 3 §3.7) provides authentication
- How secrets flow through the four-layer configuration merge (DERIVED, Part 0 §0.4 Principle 10 + Part 3 §3.5 + Part 4 §4.7.6)
- Which trust boundaries are defined and enforced (EXISTING, Part 4 §4.7.9)
- Which governance components are EXISTING, PROPOSED, UNSPECIFIED, or GAP
- Which security concerns are EXISTING, GAP, CONFLICT, UNSPECIFIED, PROPOSED, FUTURE, or RETRACTED

### 2.2 What This Document Does NOT Do

This document does NOT:

- Invent security mechanisms not present in Parts 0–14
- Define authentication protocols, algorithms, or key management approaches not already specified
- Create governance architecture not present in Parts 0–14
- Define testing requirements for security (UNSPECIFIED — testing.md is empty in Part 15)
- Prescribe specific cryptographic implementations (UNSPECIFIED)
- Resolve any CONFLICT or GAP — these are escalated to ARB per anti-invention rules
- Presuppose that AuthN/AuthZ is mandatory in v1.0 (CONFLICT-03 / Part 0 §0.2.2)

### 2.3 Compliance Rules

This document follows the Part 14 anti-invention rules:

1. No security mechanism is invented — every claim traces to Parts 0–14
2. Every claim carries exactly one status label: EXISTING, DERIVED, ASSUMPTION, UNSPECIFIED, GAP, PROPOSED, FUTURE, CONFLICT, or RETRACTED
3. CONFLICTS are preserved and escalated to ARB, not silently resolved
4. GAPs and UNSPECIFIED items are recorded, not filled with invented content
5. PROPOSED items (Draft governance artifacts) are clearly labeled and not treated as mandatory
6. RETRACTED items are documented with the retraction reason

### 2.4 v1.0 Trusted-Process Constraint

**Status:** EXISTING (Part 0 §0.2.2)

## 4. Security Architecture Overview

### 4.1 SecurityManager as Central Enforcement Authority

**Status:** EXISTING (Part 4 §4.7.1)

> "SecurityManager SHALL serve as the **sole enforcement authority** for all security policies within the Hermes Kernel."

SecurityManager owns: Authentication, Authorization, Policy Enforcement, Secret Handling, Audit Coordination, Identity Management, Trust Boundaries.

**Source:** Part 4 §4.7.1 verbatim; Part 4 §4.7.2 §Responsibilities.

### 4.2 IdentityProvider as Authentication Source

**Status:** CONFLICT-CC-01 (Part 3 §3.7 vs Part 4 §4.1 vs Part 0 §0.3.2 — see §28.1)

| Source | Classification of IdentityProvider |
|--------|-----------------------------------|
| Part 3 §3.7 | Core Component C5 |
| Part 4 §4.1 | Core Component (listed alongside EventBus, ServiceRegistry, ConfigurationAuthority) |
| Part 0 §0.3.2 | Not listed (defines 4 Core Components as EventBus, StateManager, WorkflowManager, ResourceManager) |

**Implementation guidance:** IdentityProvider is EXISTING as a Core Component in Part 3 §3.7 and referenced by Part 4 §4.7.3. Implementations MUST support `identity.validate(credentials)` and `identity.getPrincipal(id)` regardless of which Core Component set is eventually selected by ARB.

### 4.3 ABAC Authorization Model

**Status:** EXISTING (Part 4 §4.7.2/§4.7.4)

SecurityManager uses **Attribute-Based Access Control (ABAC)** for all authorization decisions.

**Decision Inputs:**
- **Principal** — Authenticated context (ID, roles, attributes, trust level)
- **Action** — Operation being attempted
- **Resource** — Target resource
- **Context** — Request metadata (time, network zone, certification level)

**Authorization interface:** `security.authorize(principal, action, resource, context)` → ALLOW / DENY / CHALLENGE.

**Policy language:** Declarative, versioned, stored in ConfigurationAuthority. Supports allow/deny with obligations, condition evaluation (CEL or equivalent), data-dependent decisions, delegation and impersonation constraints.

**INT-SEC-AUTH-001** (Part 14 §14.10 §5.2) formally documents this interface.

### 4.4 ConfigurationAuthority / ConfigurationManager

**Status:** CONFLICT-CC-01 (Part 3 §3.5 ConfigurationManager vs Part 4 §4.1 ConfigurationAuthority)

Part 3 §3.5 defines ConfigurationManager (Core Component C3). Part 4 §4.1 uses ConfigurationAuthority. Both govern four-layer merge and store policy definitions for SecurityManager. This entity is EXISTING regardless of name; implementations MUST support whichever name the codebase uses and preserve the conflict (see §28.1).

### 4.5 Trust Boundary Hierarchy

**Status:** EXISTING (Part 4 §4.7.9)

| Boundary Type | Enforcement |
|---------------|-------------|
| Network Zones | Ingress/egress policies per zone; mTLS required cross-zone |
| Capability Boundaries | Capability invocation restricted by trust level; Security Context field enforced at registration (Part 4 §4.8.3); SecurityManager filters Capability resolution (Part 4 §4.8.5 Step 2) |
| Data Classification | Storage namespace access by data classification (Part 4 §4.6) |
| Workflow Isolation | Workflow tenants isolated unless explicit sharing |
| Manager Boundaries | Core Managers at SYSTEM trust level (highest); services at lower |

**Trust Level Hierarchy:** SYSTEM (kernel Core Managers) → PRIVILEGED (platform services) → STANDARD (user services) → UNTRUSTED (external systems). Derived from Part 4 §4.7.9. No "zero-trust" model is attributed to these boundaries.

### 4.6 v1.0 Trusted-Process Model

**Status:** EXISTING (Part 0 §0.2.2)

> "Kernel assumes trusted single-tenant process; multi-tenant auth is v2.0."

In v1.0, kernel-internal components operate within a trusted single-tenant process boundary. SecurityManager authorization is architecturally EXISTING per Parts 3–4, but whether it is mandatory for all kernel-internal operations in v1.0 is CONFLICT (CONFLICT-03: Part 0 §0.2.2 trusted-process model versus Part 13 GOV-17 governance overlay). Per Part 14 §14.10 §3, integration components MUST NOT assume internal authentication is required in v1.0 unless the governance overlay is active.

## 5. SecurityManager Implementation Requirements

### 5.1 SecurityManager as Core Manager

**Status:** EXISTING (Part 4 §4.7; Part 1 §1.8.1)

SecurityManager is initialized in Phase 7 (Workflows & Security phase) per Part 1 §1.10.2.

**Dependencies (from Part 4 §4.2):**
- LifecycleManager (required; CONFLICT-CC-01: Part 4 §4.1 classifies LifecycleManager as a Core Component, Part 3 §3.5 does not)
- IdentityProvider (Core Component, required for authentication; CONFLICT-CC-01 for component identity)
- ConfigurationAuthority/ConfigurationManager (required for policy definitions)

**Downstream dependents (require SecurityManager authorization):**
- WorkflowManager — `workflow.submit/cancel/pause` authorization (Part 4 §4.7.5)
- CapabilityManager — `capability.invoke` authorization (Part 4 §4.7.5; Part 4 §4.8.5 Step 2)
- ResourceManager — `resources.reserve` authorization (Part 4 §4.9.8)
- StorageManager — `storage.read/write/delete` authorization (Part 4 §4.7.5)
- StateManager — `state.transition` authorization (Part 4 §4.7.5)

### 5.2 Authentication Implementation

**Status:** EXISTING with GAP for v1.0 (Part 0 §0.2.2; Part 4 §4.7.3; Part 14 §14.10 §4)

**Critical Gap:** Part 0 §0.2.2 explicitly defers AuthN/AuthZ to v2.0.

| Principal Type | Authentication Method | v1.0 Status | Source |
|----------------|-----------------------|-------------|--------|
| Core Managers | Kernel-internal identity (bootstrapped at init) | EXISTING | Part 4 §4.7.3 |
| Human Operators | OIDC/OAuth2, mTLS, SSH certificates, WebAuthn | PROPOSED (v2.0) | Part 4 §4.7.3 |
| Services | mTLS, SPIFFE/SPIRE, JWT, API keys (deprecated) | PROPOSED (v2.0) | Part 4 §4.7.3 |
| Workflows | Short-lived workload identity (SPIFFE), capability tokens | PROPOSED (v2.0) | Part 4 §4.7.3 |
| External Systems | Mutual TLS, signed requests, pre-shared keys (rotated) | PROPOSED (v2.0) | Part 4 §4.7.3 |

**Implementation guidance for v1.0:** Implement only Core Manager kernel-internal identity per Part 0 §0.2.2. IdentityProvider (EXISTING, Part 3 §3.7) is the authentication source. Multi-tenant authentication methods are PROPOSED for v2.0 and MUST NOT be implemented as v1.0 mandatory requirements.

### 5.3 Authorization Implementation

**Status:** EXISTING (Part 4 §4.7.4/§4.7.5)

**ABAC Decision Flow:**
1. Caller invokes `security.authorize(principal, action, resource, context)` via `kernel.security` accessor
2. SecurityManager evaluates applicable policies in priority order
3. SecurityManager returns Decision: ALLOW, DENY, or CHALLENGE (step-up auth)
4. SecurityManager emits `AuthorizationDecisionEvent` (audit)

**Enforcement Points (verbatim from Part 4 §4.7.5):**

| Enforcement Point | Protected Operations | Required Permission |
|-------------------|---------------------|---------------------|
| Capability Invocation | `capability.invoke()` | `capability.invoke` on target |
| State Transition | `state.transition()` | `state.transition` on target category |
| Storage Access | `storage.read/write/delete` | `storage.*` on namespace |
| Workflow Control | `workflow.submit/cancel/pause` | `workflow.*` on workflow |
| Secret Access | `secret.get/set/rotate` | `secret.*` on secret path |
| Configuration | `config.read/write` | `config.*` on key path |
| Manager Admin | `manager.restart/configure` | `kernel.admin` |

**Implementation requirement:** All protected operations above MUST invoke `security.authorize(principal, action, resource, context)` before execution. CONFLICT-03 qualified: mandatory when governance overlay is active (GOV-17); trusted-process boundary sufficient when overlay is not active (Part 0 §0.2.2).

**Enforcement Modes (verbatim Part 4 §4.7.5):**
- **Blocking** (default): Request waits for decision
- **Non-blocking**: Decision cached; async re-evaluation on policy change
- **Audit-only**: Log decision but allow (for policy testing)

### 5.4 Secret Handling Implementation

**Status:** EXISTING with GAP for storage/rotation/HSM (Part 4 §4.7.6; Part 14 §14.10 §9)

**What EXISTING (verbatim from Part 4 §4.7.6):**
- SecurityManager governs the complete secret lifecycle
- Secret types: Static Secrets (API keys, database passwords); Dynamic Secrets (database credentials, cloud tokens); Certificates (mTLS certs, signing keys); Encryption Keys (data encryption keys, KEK — HSM-backed; never exported; key handles only); Workflow Secrets (per-workflow credentials — scoped, auto-revoked on completion)
- Secret operations: `secret.create(path, type, policy)`; `secret.get(handle)`; `secret.rotate(path)`; `secret.revoke(path)`
- Invariant: "SecurityManager SHALL never log secret values. All secret access SHALL be audited." (Part 4 §4.7.13)

**GAP:** Secret storage mechanism, rotation schedule, HSM integration interface, SecretManager API surface, and key management are UNSPECIFIED in Parts 0–14. Part 14 §14.10 §9.2 documents SecretManager as a dependency (CM-15, INF-08) but does not define its interface.

**Logger redaction:** UNRES-08 / GAP — StructuredLogger (Part 3 §3.6) has no secret-value redaction logic. The non-logging invariant (Part 4 §4.7.13) requires zero secret values in any log output.

### 5.5 Audit Coordination Implementation

**Status:** EXISTING (Part 4 §4.7.7/§4.7.13; Part 14 §14.10 §14)

SecurityManager emits `SecurityAuditEvent` for all security-relevant actions to the `audit` namespace on EventBus. ObservabilityManager (Part 4 §4.11) ensures durable delivery to the audit store.

**Audit Event Categories (verbatim Part 4 §4.7.7):** Authentication; Authorization; Secret Access; Policy Changes; Identity Changes; Trust Boundary.

**Audit Event Structure:** Timestamp, principal, action, resource, decision, policy version, correlation ID, request context.

**Audit Retention:** StorageManager audit namespace has mandatory encryption and 7-year TTL (Part 4 §4.5.3; DERIVED from StorageManager namespace specification).

**Invariant (verbatim Part 4 §4.7.13):** Every protected operation has SecurityAuditEvent. Integration components MUST emit SecurityAuditEvent for every allow, deny, and challenge decision.

### 5.6 SecurityManager Interaction Contracts

**Status:** EXISTING (Part 4 §4.7.10)

**EventBus (Bidirectional):**
- Emits: SecurityAuditEvent, AuthenticationFailedEvent, AuthorizationDecisionEvent, SecretRotatedEvent, PolicyUpdatedEvent, TrustBoundaryViolationEvent, SecurityDegradedEvent, SecurityPolicyErrorEvent, SecurityPolicyConflictEvent, SecurityHSMUnavailableEvent, SecurityAuditBufferFullEvent
- Consumes: AuthenticateRequestEvent, AuthorizeRequestEvent, SecretRequestEvent, PolicyChangeEvent

**IdentityProvider (Outbound):**
- `identity.validate(credentials)`
- `identity.getPrincipal(id)`

**ServiceRegistry (Outbound):** Registers self as `kernel.security`

**ConfigurationAuthority/ConfigurationManager (Inbound):** Reads `kernel.security.*` configuration; policy definitions

**Core Managers (Inbound — authorization requests):**
- CapabilityManager: `capability.invoke` authorization; SecurityManager also filters Capability resolution (Part 4 §4.8.5 Step 2)
- StateManager: `state.transition` authorization
- StorageManager: `storage.*` authorization; provides key handles
- WorkflowManager: `workflow.*` authorization
- ResourceManager: `resources.reserve` authorization

**HealthManager (Inbound):** Reports SecurityManager health; HealthManager monitors SecurityManager readiness per Part 4 §4.10.4

**ObservabilityManager (Outbound):** Emits security metrics (auth latency, authz decisions, violations)

### 5.7 SecurityManager Failure Handling

**Status:** EXISTING (Part 4 §4.7.11)

| Failure Mode | Response | Source |
|--------------|----------|--------|
| IdentityProvider unavailable | Cache recent authentications (short TTL); deny new; emit SecurityDegradedEvent | Part 4 §4.7.11 |
| Policy evaluation error | Default deny; emit SecurityPolicyErrorEvent; alert | Part 4 §4.7.11 |
| Secret rotation failure | Retry; alert; do not revoke old until new confirmed | Part 4 §4.7.11 |
| HSM unavailable | Queue key operations; emit SecurityHSMUnavailableEvent | Part 4 §4.7.11 |
| Audit event loss | Buffer locally; retry with backoff; emit SecurityAuditBufferFullEvent if persistent | Part 4 §4.7.11 |
| Policy conflict (allow+deny) | Default deny; emit SecurityPolicyConflictEvent | Part 4 §4.7.11 |

**Invariant (verbatim Part 4 §4.7.11/§4.7.13):** SecurityManager SHALL fail closed (deny) on any internal failure. Availability degradation SHALL NOT weaken enforcement.

**Shutdown behavior:** SecurityManager shuts down in Phase S7 (parallel with WorkflowManager) per Part 1 §1.11.2.

### 5.8 SecurityManager Extension Rules

**Status:** EXISTING (Part 4 §4.7.12)

**Extension Points (MAY be extended):**
- Custom authentication methods (pluggable validators)
- Custom policy language (if CEL-compatible)
- Custom obligation handlers (post-authorization actions)
- Custom trust boundary types
- Custom secret types with custom rotation logic

**Extension Constraints (MUST be preserved):**
- ABAC model SHALL be preserved
- Single enforcement point SHALL be preserved
- Fail-closed behavior SHALL be preserved
- Audit completeness SHALL be preserved
- IdentityProvider as authn source SHALL be preserved

**Forbidden Extensions:**
- Bypassing authorization for "internal" calls
- Caching allow decisions beyond TTL
- Logging secret values in any form
- Custom encryption without SecurityManager coordination

### 9.3 PII and Secret Redaction in Events

**Status:** EXISTING / SCOPED (P12-ADR-008 Accepted; Part 0 §0.2.2)

> **P12-ADR-008 verbatim:** "Every inter-agent action MUST be authorized via SecurityManager. Agents operate on least-privilege. Signed events; PII and secrets redacted in payloads."

**Scope qualification:** P12-ADR-008 applies to the **Part 12 multi-agent collaboration domain** specifically. It does NOT extend to all AI-OS events or to the kernel's trusted-process model. Redaction is recorded via `metadata.redacted_fields` JSON pointers in the Part 12 envelope.

**Integration components emitting Part 12 domain events** within the Part 12 multi-agent collaboration domain MUST redact PII and secrets from payload content per P12-ADR-008. Integration components operating outside the Part 12 collaboration domain are NOT bound by P12-ADR-008's redaction requirement.

**GAP-SEC/UNRES-08:** Part 2 base Event and EventBus have no redaction logic. StructuredLogger (Part 3 §3.6) has no secret-value redaction logic.

## 33. AI Coding Agent Rules

When implementing or reviewing AI-OS security and governance code:

1. **Trace every security claim to Parts 0–14 before writing.** If the claim does not appear verbatim or as DERIVED, mark it UNSPECIFIED. Do not add "reasonable" security features.
2. **Use §28 CONFLICT Registry names verbatim.** When a conflict is named (CONFLICT-CC-01, CONFLICT-CM-01, CONFLICT-GOV-01, CONFLICT-INIT-01, CONFLICT-EVENT-01, CONFLICT-03, CONFLICT-ES-01), use the exact name. Do not resolve silently.
3. **Use Part 13 components.md G-xx identifiers exactly.** There are 16 governance components (G-00 through G-15). Do not invent additional governance components or G-xx identifiers.
4. **Event names MUST use SCREAMING_SNAKE_CASE with domain prefix** per Part 2 §2.2. PascalCase event names (visible in Part 12/14) are CONFLICT-EVENT-01 non-conformances unless an ADR validates them.
5. **Secret values MUST NEVER appear in logs, events, or observability output.** This is a non-negotiable invariant (Part 4 §4.7.13). If you find a secret value in a log or event payload, this is an architecture defect.
6. **All protected operations MUST call `security.authorize()` before execution** (Part 4 §4.7.5). This is a single enforcement point. Do not add custom authorization logic — this is a Forbidden Extension (Part 4 §4.7.12).
7. **Fail-closed is mandatory.** If SecurityManager encounters any failure during an authorization call, it MUST return DENY (Part 4 §4.7.11/§4.7.13). Do not implement fail-open behavior.
8. **CONFLICT-03 scope awareness.** When implementing auth/authz in v1.0, verify whether the governance overlay is active. Under the trusted-process model (Part 0 §0.2.2), kernel-internal components share the process trust boundary. Under the governance overlay, all governance and inter-agent operations require SecurityManager authorization.
9. **Capability Security Context is mandatory on registration.** Every capability registration MUST include Security Context (required trust level, authentication, authorization policy). Missing Security Context causes registration rejection (Part 4 §4.8.3/§4.8.10).
10. **Configuration freeze is a security boundary.** No configuration changes after Phase 2 initialization. Post-freeze changes require SecurityManager authorization. Breaking this invariant is a security defect.
11. **Do NOT implement multi-tenant auth in v1.0.** OIDC/OAuth2, SPIFFE/SPIRE, JWT, mTLS for services, WebAuthn — all are PROPOSED for v2.0 per Part 0 §0.2.2 and Part 4 §4.7.3.
12. **Do NOT implement event signing as a global feature.** Ed25519 signing via the Part 12 envelope `security{}` block is scoped to Part 12 domain events only. Do not add signing to Part 2 base Events.
13. **Governance overlay code MUST be conditional.** All governance security code (GOV-17, default-deny, P13-ADR-005 signing requirements) MUST be gated behind governance overlay activation. This MUST NOT be unconditional mandatory v1.0 behavior.
14. **Do NOT implement HSM, sandboxing, or rotation mechanisms.** HSM interface (GAP-P15-02), extension sandboxing mechanism (GAP-P15-04), secret rotation schedule (GAP-P15-03) — all are UNSPECIFIED or GAP. Do not invent implementations.
15. **External system credentials via SecretManager only.** Never read environment variables or local files directly as a credential bypass. Use the four-layer merge (DERIVED constraint per Part 14 §14.10 §9.1).
16. **All governance operations are conditional on CONFLICT-03.** Whether G-00 through G-15 governance components require SecurityManager authorization in v1.0 depends on overlay activation. Implement both paths; do not pick one.
17. **Use Part 3 Core Component names (C1–C4) when referring to Part 3's definition.** Use Part 4 Core Component names when referring to Part 4. Do not conflate or silently select one over the other (CONFLICT-CC-01).
18. **Do NOT conflate Core Manager sets.** Part 0 Capability Managers (Retry, Checkpoint, …), Part 1 Core Managers (Memory, LLM, …), and Part 4 Core Managers (Lifecycle, State, …) are three different sets (CONFLICT-CM-01). Use the qualified form appropriate to your source.
19. **Check Part 13 components.md §1 for governance component definitions.** All 16 components (G-00–G-15) are defined there. Do not mark any as UNSPECIFIED without verifying against the source.
20. **Review checklist:** Before marking any section COMPLETE, verify: (a) every claim has a status label, (b) every EXISTING claim cites source, (c) every DERIVED claim shows inference path, (d) every CONFLICT is preserved with both sides, (e) every GAP/UNSPECIFIED is recorded in §29, (f) zero invented mechanisms, governance bodies, or ADR IDs.
