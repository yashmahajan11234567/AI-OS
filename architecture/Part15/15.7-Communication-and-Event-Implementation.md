## 3. Event Model

### 3.1 Event Definition

**Status:** EXISTING (Part 2 §2.2.1)

> "Event: Immutable, timestamped, correlated data carrier emitted to the EventBus. The SOLE mechanism for inter-component communication."

### 3.2 Event Base Contract

**Status:** EXISTING (Part 2 §2.2.1)

Every Event MUST conform to the base contract. This contract is IMMUTABLE — no field may be added, removed, or redefined without ARB approval.

```
Event {
  // Identity
  eventId: UUIDv7
  eventType: EventType
  eventVersion: SemanticVersion

  // Temporal
  timestamp: ISO8601Instant
  timestampMonotonic: MonotonicNs

  // Correlation & Causation
  correlationId: UUID
  causationId: UUID | null

  // Routing
  source: ComponentIdentity
  target: ComponentIdentity | null

  // Priority & Category
  priority: EventPriority
  category: EventCategory

  // Payload
  payload: EventPayload

  // Integrity
  checksum: SHA256Hex
}
```

**Source:** Part 2 §2.2.1

| Field | Invariant | Status |
|-------|-----------|--------|
| eventId | UUIDv7 globally unique | EXISTING INV-EVT-002 |
| timestamp | UTC, nanosecond precision | EXISTING INV-EVT-003 |
| correlationId | Required, tracks workflow | EXISTING INV-EVT-004 |
| causationId | null for root events | EXISTING INV-EVT-005 |
| source | ComponentIdentity | EXISTING INV-EVT-006 |
| checksum | SHA-256 of payload | EXISTING INV-EVT-007 |

### 3.3 Event Immutantiy

**Status:** EXISTING (Part 2 §2.2.7 INV-EVT-001)

All fields are read-only after construction. Events are immutable value objects.

**Invariant:** `INV-EVT-001` — All fields are read-only after construction. — Part 2 §2.2.1

**Invariant:** `INV-EVT-012` — EventBus MUST verify immutability on publish. — Part 2 §2.2.7

### 3.4 ComponentIdentity

**Status:** EXISTING (Part 2 §2.2.2)

```
ComponentIdentity {
  componentType: 'kernel' | 'core_component' | 'core_manager' |
                  'engineering_service' | 'capability_facade' | 'app_service' | 'extension'
  componentName: string
  instanceId: UUID | null
  version: SemanticVersion
}
```

### 3.5 EventPriority

**Status:** EXISTING (Part 2 §2.2.3)

| Priority | Value | Description | Source |
|----------|-------|-------------|--------|
| CRITICAL | 0 | Kernel lifecycle, fatal errors | Part 2 §2.2.3 |
| HIGH | 1 | Workflow control, retry/exhaustion | Part 2 §2.2.3 |
| NORMAL | 2 | Standard SDLC events (default) | Part 2 §2.2.3 |
| LOW | 3 | Telemetry, metrics, heartbeats | Part 2 §2.2.3 |
| BACKGROUND | 4 | Maintenance, consolidation | Part 2 §2.2.3 |

**Ordering Guarantee:** Events of higher priority MUST be dispatched before lower priority events. — Part 2 §2.2.3

### 3.6 EventCategory

**Status:** EXISTING (Part 2 §2.2.4)

| Category | Description | Source |
|----------|-------------|--------|
| SYSTEM | Kernel, core component, core manager lifecycle | Part 2 §2.2.4 |
| CONTROL | Workflow orchestration, service coordination | Part 2 §2.2.4 |
| DATA | State changes, artifacts, checkpoints | Part 2 §2.2.4 |
| AUDIT | Governance, council decisions, security | Part 2 §2.2.4 |
| DIAGNOSTIC | Metrics, traces, health checks | Part 2 §2.2.4 |

**Routing Rule:** Subscribers MAY filter by category. EventBus MUST support category-based subscription. — Part 2 §2.2.4

### 4.2 Internal Queues

**Status:** EXISTING (Part 2 §2.4.4)

| Queue | Capacity | Overflow | Ordering |
|-------|----------|----------|----------|
| Publish Queue | Configurable (default: 10,000) | REJECT_NEW | FIFO per priority lane |
| Dispatch Queue | Unbounded | N/A | Priority-sorted |

**Invariant:** `INV-EB-006` — Event ordering within a priority lane is FIFO by timestampMonotonic. — Part 2 §2.4.4

## 6. EventLifecycle

### 6.1 Complete Lifecycle

**Status:** EXISTING (Part 2 §2.6.1)

```
CREATION → VALIDATION → PUBLICATION → QUEUING → DISPATCH → SUBSCRIBER → COMPLETION
```

### 6.2 Dispatch Algorithm

Per Part 2 §2.4.6:

1. Pop event from highest non-empty priority lane
2. Find subscriptions matching eventType
3. Sort by HandlerPriority, then subscriptionId
4. For each subscription: filter → concurrency → handler → success/failure
5. Apply retry policy on failure
6. Move to DLQ after retry exhaustion

**Source:** Part 2 §2.4.6

**Invariant:** `INV-EB-009` — Dispatch MUST process events in strict priority order. — Part 2 §2.7.1

## 7. Delivery Guarantees

### 7.1 At-Least-Once (Default)

**Status:** EXISTING (Part 2 §2.8.3)

Events dispatched to ALL matching subscribers with retry on failure.

**Source:** Part 2 §2.8.3 — "The default delivery guarantee is at-least-once."

### 7.2 At-Most-Once (Opt-In)

**Status:** EXISTING (Part 2 §2.8.4)

No retry on failure; handler failure → log, discard, emit EventDeliveryFailed.

### 7.3 Exactly-Once (Opt-In)

**Status:** GAP

**Source:** Part 2 §2.8.4 INV-DLV-003 — "Exactly-once MUST NOT be claimed without persistent deduplication store."

## 8. Ordering Guarantees

**Status:** EXISTING (Part 2 §2.7.1)

| Guarantee | Scope | Mechanism | Source |
|-----------|-------|-----------|--------|
| Global Total Order | All events | timestampMonotonic + priority | Part 2 §2.7.1 |
| Priority Order | Within dispatch | CRITICAL → BACKGROUND | Part 2 §2.7.1 |
| Correlation Order | Same correlationId | FIFO within lane | Part 2 §2.7.2 |
| Causation Order | Event and effects | causationId ensures order | Part 2 §2.6.1 |
| Per-Subscriber Order | To same subscriber | Sequential by priority | Part 2 §2.4.6 |

**Invariant:** `INV-ORD-001` — Global order is strictly priority-major, timestamp-minor. — Part 2 §2.7.1

**Invariant:** `INV-ORD-002` — Given identical input, dispatch order MUST be bit-for-bit reproducible. — Part 2 §2.7.1

## 15. Audit: Security and Communication Boundaries

### 15.1 Communication is NOT a Security Boundary

Per Part 0 §0.4 Principle 1:
- EventBus is the communication mechanism
- Security (authentication, authorization) is handled by SecurityManager (Part 4 §4.7)

**Cross-reference:** Part 15.7-Security-and-Trust-Implementation.md for security implementation requirements.

### 15.2 No Communication Protocol is Defined

Per Part 2 §2.1.4:
- EventBus is "a routing substrate, not a broker"
- Transport protocols are "adapter concerns"
- The architecture is silent on: HTTP, gRPC, WebSockets, TCP, UDP, AMQP, MQTT
