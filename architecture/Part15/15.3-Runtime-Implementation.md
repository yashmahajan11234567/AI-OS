## 3. HermesKernel Singleton Architecture

**Source:** Part 1 §1.6, Part 1 §1.9.1

**State Machine (8-state FSM per Part 4 §4.3.3, implemented in LifecycleManager):**
UNINITIALIZED → INITIALIZING → OPERATIONAL → DEGRADED → SHUTTING_DOWN → TERMINATED
Plus: ROLLBACK_IN_PROGRESS (from UNINITIALIZED/DEGRADED/OPERATIONAL), RECOVERY_IN_PROGRESS (from DEGRADED)

**Invariants (IMPLEMENTED):**
- INV-LC-001: State transitions MUST follow exact sequence defined in `_TRANSITIONS` map
- INV-LC-002: Kernel MUST NOT transition OPERATIONAL directly to TERMINATED (must go through SHUTTING_DOWN)
- INV-LC-003: Once TERMINATED, re-initialization is PROHIBITED
- INV-LC-004: Degraded state requires explicit recovery before returning to OPERATIONAL

**Core Component Accessors (EXISTING):**
- `kernel.eventBus` (C1, Phase 0)
- `kernel.serviceRegistry` (C2, Phase 1)
- `kernel.configuration` (C3, Phase 2)
- `kernel.logger` (C4, Phase 3)

**Core Manager Accessors (EXISTING per Part 1 §1.8.1):**
- M1-M9 via LifecycleManager registry

## 7. Kernel Lifecycle States

**Source:** Part 4 §4.3.3 (implemented); Part 1 §1.9.1 (superseded)

| State | Entry Condition | Exit Condition | Events | Status |
|-------|----------------|----------------|--------|--------|
| UNINITIALIZED | Kernel constructed | `initialize()` invocation | KernelInitializationStarted | IMPLEMENTED |
| INITIALIZING | `initialize()` invocation | Phases 0-8 complete | PhaseCompleted events | IMPLEMENTED |
| OPERATIONAL | Phases 0-8 complete | `shutdown()` or fatal error | KernelReady | IMPLEMENTED |
| DEGRADED | Fatal error during OPERATIONAL | Recovery initiated | CoreManagerDegraded | IMPLEMENTED |
| SHUTTING_DOWN | `shutdown()` invocation | All shutdown phases S0-S9 complete | KernelShutdownStarted | IMPLEMENTED |
| TERMINATED | Phase S0 complete | (terminal state) | KernelTerminated | IMPLEMENTED |
| ROLLBACK_IN_PROGRESS | Initialization failure | Rollback complete | KernelInitializationFailed | IMPLEMENTED |
| RECOVERY_IN_PROGRESS | Degraded → recovery | Recovery complete | KernelRecoveryEvent | IMPLEMENTED |

**Transition Diagram (IMPLEMENTED per Part 4 §4.3.3):**

```
UNINITIALIZED → INITIALIZING → OPERATIONAL → SHUTTING_DOWN → TERMINATED
      ↑              ↓                ↓              ↓
      └──── ROLLBACK_IN_PROGRESS ────┘              │
                           ↑                        │
      ┌────────────────────┴─────────────────────────┘
      │                  fatal error
      ↓                   (any state)
   OPERATIONAL → DEGRADED → RECOVERY_IN_PROGRESS → OPERATIONAL
                                          ↓
                                    (recovery fails)
                                          ↓
                                       DEGRADED
```

## 14. Shutdown Sequencing

**Source:** Part 1 §1.11.2

### 14.1 Shutdown Phases S0-S9 (EXISTING)

| Phase | Component/Manager | Action |
|-------|-------------------|--------|
| S9+ | Services | Reverse topological shutdown |
| S8 | ObservabilityManager | Telemetry flush |
| S7 | ReviewManager, SecurityManager | Governance finalization |
| S6 | PlanningManager, CodingManager | Capability cleanup |
| S5 | LifecycleManager, WorkflowManager | Orchestration end |
| S4 | StateManager, StorageManager | State persistence |
| S3 | StructuredLogger | Log flush, sink close |
| S2 | ConfigurationManager | Hash archive |
| S1 | ServiceRegistry | Deregister, subscriptions clear |
| S0 | EventBus | DRAINING → SHUTDOWN |

### 14.2 Termination Lifecycle (EXISTING per Part 1 §1.11.3)

After Phase S0 completes (EventBus SHUTDOWN → DRAINING → SHUTDOWN), the kernel transitions to TERMINATED state and publishes the `KernelTerminated{timestamp, shutdownDurationMs, errors: Error[]}` event.

**Specified (EXISTING):**
| Element | Specification | Source |
|---------|---------------|--------|
| TERMINATED state entry | After S0 completion | Part 1 §1.11.2 |
| KernelTerminated event | Published on TERMINATED entry | Part 1 §1.11.3 |
| Event payload | `{timestamp, shutdownDurationMs, errors: Error[]}` | Part 1 §1.11.3 |
| Process termination | "eventually exits" implied | Part 1 §1.11.3 |

**Implementation Responsibility:**
- Process exit mechanism (process.exit(), thread termination, etc.)
- Any post-shutdown cleanup after EventBus S0
- Final resource deallocation timing

## 16. Configuration Runtime Model

**Source:** Part 3 §3.5, Part 1 §1.10.2

### 16.1 Freeze Behavior (EXISTING per Part 3 §3.5.6)

The configuration is frozen after Phase 3 completes, before Manager initialization begins. Post-freeze, all configuration values become immutable.

| Milestone | Event | Status |
|-----------|-------|--------|
| Phase 3 end | ConfigurationFrozen{hash} | EXISTING |
| Manager Phase 4 start | Immutable access | EXISTING |

### 16.2 Four-Layer Merge (EXISTING per Part 3 §3.5.2)

Configuration values merge in strict priority order (later layers override earlier):

| Layer | Source | Override Priority |
|-------|--------|-------------------|
| 1 | Built-in defaults | Lowest |
| 2 | app.yaml | Medium-low |
| 3 | env.yaml | Medium-high |
| 4 | AIOS_* env vars | Highest |

### 16.3 Configuration Validation

Schema validation is performed during Phase 2 configuration merge. The specific validation rules (type constraints, range limits, required fields, cross-field dependencies) are defined by implementation choice per configuration.md §11.
