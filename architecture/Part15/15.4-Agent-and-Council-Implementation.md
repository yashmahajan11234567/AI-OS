## §10 — Agent Architecture Source Map

**Source:** Part 12.1 §6, Part 12 components.md Appendix A (15 components), Part 12.3 §2, §4–§9, §12, §15, P12-ADR-002

Agents are first-class participants in the AI-OS collaboration framework (Part 12.1 §6). They possess six defining attributes:

1. **Capabilities** — Self-described via standardized schemas in the Capability Registry (Part 12.1 §6, Agent Characteristics; Part 12.3 §2 — Core Components → Capability Registry, P12-ADR-002)
2. **Availability** — Published through the Agent Directory with health and load metrics (Part 12.1 §6; Part 12.3 §2 — Core Components → Agent Registry; §8 — Health Status)
3. **Reputation** — Tracked via Council Manager for trust-based matchmaking (Part 12.1 §6; Part 12.5 §2)
4. **Isolation** — Execute in supervised runtimes with enforced resource quotas (Part 12.1 §6; Part 9 §9.1, Part 10)
5. **Communication** — Participate via the Collaboration Bus (Communication Bus) which translates to EventBus events (Part 12.1 §6; Part 12.7 §2–§4; P12-ADR-001)
6. **Autonomy** — Retain full control over internal reasoning and decision processes (Part 12.1 §6)

**Agent attributes are EXISTING** per Part 12.1 §6 (Agent Characteristics). No additional behavioral attributes are invented.

**Agent placement in architectural layers** (Part 12 components.md Appendix A diagram, Layer 0–4):
- **Foundation layer** (Layer 1): Communication Bus, Security Gateway, Component Registry

- **Governance layer** (Layer 4): Council Manager, Negotiation Engine, Conflict Resolution Manager

Agents operate across Coordination, Governance, and Registry layers as runtime participants.

## §12 — Agent Discovery & Registration

**Source:** Part 12.3 §2 (Core Components), §5 (Registration Workflow), §6 (Deregistration Workflow), P12-ADR-002

### Agent Registry (Part 12.3 §2 — Core Components → Agent Registry)

The Agent Registry maintains a directory of all active agents. Each entry includes:
- Unique agent identifier (agentId — UUID)
- Current status (active, inactive, maintaining, unregistering)
- Network endpoint information
- Registration timestamp
- Last heartbeat timestamp
- Associated capabilities
- Metadata tags for classification

**Status:** EXISTING — From Part 12.3 §2 (Core Components — Agent Registry) and §15 (Metadata Schema).

### Capability Registry (Part 12.3 §2 — Core Components → Capability Registry)

The Capability Registry stores detailed information about capabilities that agents can provide. Each capability entry includes:
- Capability identifier and version
- Human-readable description
- Input/output schemas
- Required skills and permissions
- Performance characteristics
- Associated agents providing the capability
- Deprecation and migration information

**Status:** EXISTING — From Part 12.3 §2 (Core Components — Capability Registry) and §15 (Metadata Schema).

### Registration Workflow (Part 12.3 §5)

1. Agent prepares registration manifest with:
   - Agent ID and version
   - Network endpoints (primary and backup)
   - Capability list with versions
   - Metadata tags
   - Security credentials
2. Agent sends registration request to nearest registry node
3. Registry validates:
   - Agent authenticity
   - Capability schema compliance
   - Resource availability
   - Policy adherence
4. Registry stores agent information and returns registration confirmation
5. Agent begins periodic heartbeat transmission
6. Registry replicates agent information to peer nodes

**Status:** EXISTING — All from Part 12.3 §5.

### Deregistration Workflow (Part 12.3 §6)

1. Agent sends deregistration request (graceful) or stops heartbeats (ungraceful)
2. For graceful deregistration:
   - Agent stops accepting new requests
   - Completes in-progress operations
   - Sends final deregistration message
   - Registry marks agent as unregistering
   - Registry removes agent after confirmation timeout
3. For ungraceful deregistration:
   - Registry detects missing heartbeats
   - Marks agent as inactive after timeout period
   - Moves to unregistered state after grace period

**Status:** Existing — From Part 12.3 §6.

### Discovery Protocols (Part 12.3 §9)

The system supports multiple discovery protocols:
- REST/HTTP: Standard CRUD operations on registry endpoints
- gRPC: High-performance streaming for real-time updates
- WebSocket: Bidirectional communication for event-driven updates
- mDNS/DNS-SD: Local network zero-configuration discovery
- Custom Binary Protocol: For high-performance internal communication

**Status:** EXISTING — From Part 12.3 §9.

- `version`: SemanticVersion (Part 2 §2.2.1)
- `payload`: Immutable value object (Part 2 §2.2.6)
- `checksum`: SHA-256 (Part 2 §2.2.1)

- `event_type`

**Correlation and Causation Semantics** (Part 0 §0.3.2 Principle 8; Part 12 events.md §4):

**Generation algorithm:** UNSPECIFIED — The architecture does not specify how correlation_id or causation_id values are generated (UUIDv7, UUIDv4, etc.). This is an implementation decision.
