## 2. Purpose

This document defines **what must be tested to prove implementation conformance** for AI-OS. It answers:

- **What must be tested:** Specific architectural requirements from Parts 0–14
- **Where it comes from:** Source documentation (Parts 0–14, contracts, ADRs)
- **What constitutes a violation:** Failing the normative requirement
- **How to verify:** Verification methods and evidence criteria

**Authority Model:**

```
Parts 0–14 (Architectural Requirements)
        ↓
Implementation Contracts (CMP.MUST.1-5, CFG.MUST.1-4, SEC.MUST.1-5, etc.)
        ↓
Test Specifications (What to test)
        ↓
Test Implementations (How to test)
        ↓
Execution Evidence (Test results)
        ↓
Conformance Judgment (Pass/Fail)
```

**Status:** GAP — Testing architecture documented in `testing.md`; test specifications and implementations are pending.

## 3. Conformance Model

Per Part 0 §0.5.1, conformance levels are:

| Level | Name | Description | Verification Methods |
|-------|------|-------------|---------------------|
| L1 | **Structural Conformance** | Code compiles, imports resolve, base classes implemented | Static analysis, type checking |
| L2 | **Contract Conformance** | Event schemas match spec; interfaces honor signatures | Unit tests, contract tests |
| L3 | **Behavioral Conformance** | Runtime invariants hold: event ordering, lifecycle progression, failure routing | Integration tests, system tests |
| L4 | **Architectural Conformance** | No principle violations: direct calls, missing correlation IDs, kernel domain logic | System tests, static analysis, manual review |

### 3.1 Verification Method Categories

| Level | Static | Unit | Integration | Contract | System |
|-------|--------|------|-------------|----------|--------|
| L1 | ✓ | ✓ | — | — | — |
| L2 | ✓ | ✓ | ✓ | ✓ | — |
| L3 | ✓ | ✓ | ✓ | ✓ | ✓ |
| L4 | ✓ | ✓ | ✓ | ✓ | ✓ |

**Note:** These indicate *potential* verification methods, not mandatory technologies.

## 7. EventBus Communication Verification

### 7.1 Substrate Verification

**Requirement:** EventBus is the sole communication substrate for all inter-component communication after Kernel initialization.

**Source:** Part 2 §2.1, CMP.MUST.1

**Verification Method:**
- **Static:** No direct imports/function calls between service components
- **Runtime:** All service-to-service communication observable via EventBus

**Test Specification:** TEST-EVT-001-SPEC

**Violation:** Any direct REST call, gRPC invocation, or message queue usage between services constitutes a violation of the EventBus substrate invariance.
