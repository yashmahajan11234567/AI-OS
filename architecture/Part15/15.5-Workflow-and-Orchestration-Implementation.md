## 1. Purpose and Scope

**Status:** EXISTING — Part 14 README §Purpose; Part 00 §0.2.1

Part 15.5 is the fifth implementation-focused chapter of Part 15. It translates the authoritative workflow and orchestration architecture established in Parts 0–14 into implementation-facing requirements and constraints.

**What Part 15.5 covers:**
- Hermes Kernel as the pure orchestrator owning Core Components and Core Managers
- WorkflowManager (M7) as the sole governance authority for workflow execution
- Workflow Definition, Instance, Execution, and State as architecturally distinct planes
- DAG-based workflow execution with coordination primitives
- Event-driven orchestration via EventBus with correlation_id and causation_id
- Lifecycle states, transitions, and invariants
- Context propagation, boundary enforcement, nested workflows
- Scheduling, cancellation, timeouts, retry, compensation
- Fault handling, checkpointing, deterministic replay
- Council decision integration, cross-capability coordination
- Integration with StateManager, StorageManager, SecurityManager, ResourceManager, ObservabilityManager
- Implementation contracts, gaps, conflicts, and anti-invention rules

**What Part 15.5 does NOT cover:**
- Workflow framework selection, scheduler implementation, queue technology, worker topology
- Retry counts, timeout values, backoff parameters, compensation semantics not established by Parts 0–14
- Persistence technology, storage schema, database selection
- Source code, API implementations, or concrete class designs
- Deployment topology, network transport, process boundaries
- Technology choices for checkpoint storage, replay logging, or context serialization

**Anti-Invention Constraints:**
- Where Parts 0–14 are silent, Part 15.5 records UNSPECIFIED and does not invent values, schemas, or rules.
- No workflow framework, scheduler, queue technology, persistence backend, or deployment topology is invented.
- Implementation-mapped names (StateManager, CheckpointManager, RetryManager, etc.) are recorded as implementation-mapped; their canonical Core Manager mappings are UNSPECIFIED where not established by Parts 0–14.

## 3. Terminology and Status Taxonomy

**Status:** EXISTING — Part 14 context.md §0.1; Part 14 README §Status Taxonomy; glossary.md §2

Every normative statement in Part 15.5 carries exactly one status label from the Part 14 taxonomy. Labels are mutually exclusive.

| Status | Meaning |
|--------|---------|
| **EXISTING** | Verbatim or field-for-field present in Parts 0–14 or accepted ADR, with explicit source citation. |
| **DERIVED** | Logically implied by one or more EXISTING statements. The inference path and source anchors must be stated. |
| **ASSUMPTION** | Adopted for continuity or scoping clarity. Not explicitly stated in source Parts. Must be flagged, reviewed before implementation, and resolved to EXISTING, DERIVED, or GAP. |
| **UNSPECIFIED** | Source Parts and accepted ADRs are silent on this detail. Part 15.5 must NOT invent a value, schema, or rule to fill the silence. |
| **GAP** | Source Parts partially define a concern but leave required fields, interfaces, or behavior unspecified for implementation use. Requires a PROPOSED resolution or explicit deferral. |
| **PROPOSED** | A recommendation for Part 15.5 chapter authors to resolve a GAP or UNSPECIFIED item. Must NOT be stated as architecture fact or binding requirement. |
| **FUTURE** | Explicitly deferred in source Parts to a named future horizon. Must NOT be introduced as v1.0 behavior. |
| **CONFLICT** | Two or more authoritative sources disagree on this point. Both sources must be preserved. Part 15.5 must NOT silently resolve, override, or paper over the disagreement. |

## 5. Architectural Boundaries

**Status:** DERIVED — Part 14.1 §9; Part 14.2 §2; Part 07 §7.4.6, §7.6.6

Part 15.5 recognizes the following architectural boundaries that implementation must preserve.

### 5.1 Kernel Boundary

**Status:** EXISTING — context.md §1.1 (citing Part 01 §1.5.2, §1.5.3)

The Hermes Kernel owns exactly four Core Components and nine Core Managers. The Kernel is the sole orchestrator of the platform foundation. The Kernel does not execute step logic, does not invoke capabilities directly, and does not expose internal component references to Services.

### 5.2 Capability Autonomy Boundary

**Status:** EXISTING — Part 00 §0.4 P2; Part 07 §7.2.3, §7.6.2, §7.6.6

WorkflowManager coordinates capabilities exclusively through their execution contracts. WorkflowManager does not access, modify, direct, or bypass capability internal behavior. This boundary is non-negotiable and applies to all workflow operations including fault handling, compensation, and recovery.

### 5.3 Workflow Boundary

**Status:** EXISTING — Part 07 §7.4.6, §7.6.6, §7.7.5

A Workflow Boundary defines the architectural limits of a workflow's coordination authority. It constrains:
- which capabilities participate
- which context elements are visible
- which transitions are valid
- which events are consumed
- the extent of coordination authority

Boundaries are established in Initialized state and released in Terminated state. They are invariant across all lifecycle states.

### 5.4 Integration Boundary

**Status:** DERIVED — Part 14.1 §9.1; Part 14.2 §1.1

The integration boundary separates the AI-OS architectural domain from external systems. External systems cross only through Facade Services or Core Manager bridges. The EventBus is a kernel-internal boundary; external systems do not participate in it.

### 5.5 Boundary Non-Implications

**Status:** DERIVED — Part 14.1 §9.1; Part 14.2 §1.1

Architectural boundaries do not automatically imply:
- process boundaries
- network boundaries
- host boundaries
- container boundaries
- security/trust boundaries
- deployment boundaries

Where source Parts establish physical boundary semantics, they are EXISTING. Where source Parts are silent, boundary type is UNSPECIFIED.

**Status:** EXISTING

The Hermes Kernel is responsible for:
- configuration authority
- lifecycle orchestration
- failure handling
- ownership of Core Components and Core Managers

The Kernel does NOT:
- execute step logic
- invoke capabilities directly

### 6.2 Kernel Implementation vs Kernel Role

**Status:** DERIVED — Part 14.2 §1.2

## 7. WorkflowManager (M7) — Governance Authority

**Status:** EXISTING — Part 01 §1.8.1 M7; Part 04 §4.6

### 7.1 WorkflowManager Identity

**Status:** EXISTING

WorkflowManager is the seventh Core Manager (M7), owned by the Hermes Kernel. It is the sole governance authority for workflow execution within the AI-OS platform.

### 7.2 WorkflowManager Responsibilities

**Status:** EXISTING — Part 04 §4.6

WorkflowManager is responsible for:
- execution governance — validating, creating, scheduling, and monitoring workflow instances
- lifecycle management — enforcing lifecycle states and transitions
- scheduling — prioritizing and dispatching workflow steps based on readiness, resources, priority, fairness, and affinity
- cancellation — supporting cooperative and forced cancellation modes
- timeout enforcement — step-level and workflow-level timeouts
- retry management — configurable retry policies with max attempts, backoff strategy, base delay, max delay, jitter, retryable errors, circuit breaker
- nested workflow management — parent-child workflow relationships with isolation and bounded depth
- coordination primitives — Join, Branch, Signal, Barrier, Aggregate
- outcome determination — classifying workflow outcomes per Workflow Definition criteria

### 7.3 WorkflowManager Interaction Contracts

**Status:** EXISTING — Part 04 §4.6

WorkflowManager interacts with the following architectural elements through documented contracts:

| Contract Partner | Interaction |
|-----------------|-------------|
| EventBus | Publishes WORKFLOW_* and TASK_* events; consumes external trigger events |
| CapabilityManager | Invokes capability execution contracts for workflow steps |
| ResourceManager | Requests resource allocation for workflow execution |
| SecurityManager | Evaluates authorization for workflow operations |
| StorageManager | Persists checkpoints and workflow artifacts |
| HealthManager | Monitors workflow health and participant health |
| ObservabilityManager | Emits workflow lifecycle and step metrics/traces |

### 7.5 WorkflowManager Architectural Invariants

**Status:** EXISTING — Part 04 §4.6

WorkflowManager preserves the following architectural invariants:
1. **DAG execution:** Workflow execution proceeds as a DAG of steps. No cycles, no implicit ordering.
2. **Saga compensation:** Completed steps may be compensated via declared compensation actions when workflow outcome requires it.
3. **Resource accounting:** Resources allocated to workflow execution are accounted and released.
4. **Capability mediation:** All capability invocations are mediated through execution contracts.
5. **State machine completeness:** Every valid lifecycle state has defined entry conditions, exit conditions, and transitions.
6. **Correlation integrity:** correlation_id and causation_id are preserved across all workflow events.

## 8. Workflow Definition Plane

**Status:** EXISTING — Part 07 §7.4.1; Part 04 §4.6

### 8.1 Definition Identity

**Status:** EXISTING

A Workflow Definition possesses an immutable identity that distinguishes it from all other definitions. The identity is assigned at definition creation and SHALL NOT be changed, reassigned, or revoked.

### 8.2 Definition Immutability

**Status:** EXISTING — Part 07 §7.4.1 Invariant 1; Part 07 §7.5.8 Invariant 1

A Workflow Definition is architecturally immutable once established. No architectural operation SHALL modify:
- identity
- participating capabilities
- workflow steps
- transitions
- context propagation rules
- boundaries
- outcome criteria

**Implementation implication:** Implementation MUST enforce immutability at the architectural boundary. Any mechanism that would modify a Definition after establishment is non-conforming (Part 07 §7.10.4).

### 8.3 Definition Contents

**Status:** EXISTING — Part 07 §7.4.1; Part 04 §4.6

A Workflow Definition SHALL define:
- **workflow identity** — the immutable identifier
- **participating capabilities** — the set of capability identities coordinated through execution contracts
- **workflow steps** — the ordered collection of step specifications, each identifying a capability execution contract invocation
- **transitions** — architectural rules governing progression between steps (sequence, branching, synchronization, iteration)
- **context propagation rules** — how context flows between steps (transformation, filtering, scoping)
- **workflow boundaries** — the architectural scope of the workflow (participating capabilities, coordination authority)
- **outcome criteria** — architectural conditions determining workflow completion and classifying the outcome
- **cancellation semantics** — immediate vs. graceful cancellation behavior
- **compensation actions** — per-step compensation actions for semantic undo
- **timeout specifications** — step-level and workflow-level timeout values
- **retry policies** — per-step and workflow-level retry configurations

### 8.4 Definition Lifecycle

**Status:** EXISTING — Part 13.8

Workflow Definitions progress through a governance lifecycle:
- **DRAFT** — under authoring, not yet executable
- **REVIEW** — under architectural review
- **APPROVED** — reviewed and approved, not yet published
- **PUBLISHED** — active and executable
- **DEPRECATED** — superseded by a newer definition
- **RETIRED** — no longer executable

Implementation MUST NOT execute a Definition that is not in PUBLISHED state. Execution of DEPRECATED or RETIRED Definitions is UNSPECIFIED.

### 8.5 Definition Versioning

**Status:** EXISTING — Part 07 §7.9.2 Decision 1

Workflow Definition versioning is explicit through identity. A new definition requires a new identity. No architectural operation modifies an existing definition. Governance processes operate on definitions as atomic, immutable units.

## 9. Workflow Instance Plane

**Status:** EXISTING — Part 07 §7.4.2; Part 04 §4.6

### 9.1 Instance Identity

**Status:** EXISTING

Each Workflow Instance possesses a unique, immutable instance identity distinct from its Workflow Definition identity. Instance identities SHALL NOT be reused, reassigned, or predicted. Instance identity is architecturally bound to its Definition identity at instantiation.

### 9.2 Instance Separation

**Status:** EXISTING — Part 07 §7.4.10 Invariant 2; Part 07 §7.10.2 Requirement 2

Each Workflow Instance is architecturally isolated from every other Workflow Instance. The state, context, progress, and outcome of one instance SHALL NOT architecturally affect another instance, even when realized from the same Workflow Definition.

**Implementation implication:** Implementation MUST maintain strict isolation between instances. Shared mutable state between instances is non-conforming.

### 9.3 Instance State

**Status:** EXISTING — Part 07 §7.4.2

A Workflow Instance maintains:
- **workflow state** — execution progress (which steps invoked, completed, active, pending)
- **execution progress** — architectural position within the workflow definition
- **workflow context** — accumulated context (input, intermediate, pending)
- **outcome status** — classification (incomplete, success, failure, compensation, partial completion, cancellation)

### 9.4 Instance-to-Definition Relationship

**Status:** EXISTING — Part 07 §7.4.2

A Workflow Instance references exactly one Workflow Definition. Multiple instances are realizable from a single Definition. The Instance SHALL NOT modify its associated Definition.

## 10. Workflow Execution Plane

**Status:** EXISTING — Part 04 §4.6; Part 07 §7.6

### 10.1 Execution Model

**Status:** EXISTING — Part 04 §4.6

Workflow execution follows this model:
1. **Submit** — via EventBus with workflow definition identity and input context
2. **Validate** — WorkflowManager validates the submission against the Definition
3. **Create Instance** — WorkflowManager creates a Workflow Instance
4. **Schedule** — WorkflowManager schedules steps based on readiness, resources, priority, fairness, and affinity
5. **Execute** — steps execute via capability execution contracts mediated by CapabilityManager
6. **Complete/Compensate** — workflow reaches terminal outcome or enters compensation

### 10.2 Execution as DAG

**Status:** EXISTING — Part 04 §4.6; Part 07 §7.3

Workflow execution proceeds as a Directed Acyclic Graph (DAG) of steps. The DAG structure is defined by the Workflow Definition's steps and transitions. No cycles are architecturally permitted.

### 10.3 Capability Execution Contract Invocation

**Status:** EXISTING — Part 07 §7.6.2

A Workflow Instance coordinates a capability by invoking its execution contract. The invocation specifies:
- capability identity
- execution contract identity
- input context derived from Workflow Context

The Workflow Instance SHALL NOT specify how the capability fulfills the contract.

### 10.4 Step Uniqueness

**Status:** EXISTING — Part 07 §7.4.10 Invariant 3

Within a single Workflow Instance, each Workflow Step SHALL possess a unique architectural identity. No two steps within the same instance SHALL share the same step identity.

## 11. Workflow State Plane

**Status:** EXISTING — Part 07 §7.4; Part 04 §4.6

### 11.1 Workflow State vs Lifecycle State

**Status:** EXISTING — Part 07 §7.5.7

**Workflow Lifecycle State** is the high-level architectural phase (Created, Initialized, Ready, Running, etc.). **Workflow State** is the fine-grained execution progress representation (active steps, completed steps, context values). Lifecycle State constrains Workflow State evolution: steps may only progress in Running and Completing states; context may only be produced in Running, Completing, and Compensating states.

### 11.2 Workflow Context

**Status:** EXISTING — Part 07 §7.4.5; Part 07 §7.6.3

Workflow Context is the architectural information flowing between steps. Context:
- is initialized in Created state
- is produced at step completion (atomic with step completion)
- is consumed at step invocation (without mutating source)
- is propagated along declared transition paths
- is scoped by Workflow Boundaries
- is preserved across Suspended, Waiting, and Compensating states
- is finalized in Completing state

## 12. Lifecycle State Machine

**Status:** EXISTING — Part 07 §7.5.2, §7.5.3

### 12.1 Lifecycle States

**Status:** EXISTING

The Workflow Architecture defines the following lifecycle states for Workflow Instances:

| State | Architectural Meaning |
|-------|----------------------|
| **Created** | Instance instantiated; identity, definition reference, and resources allocated; no coordination commenced |
| **Initialized** | Initialization complete; boundaries established; capabilities resolved; prepared for execution |
| **Ready** | Preconditions satisfied; ready to invoke capability execution contracts |
| **Running** | Actively coordinating capabilities; steps invoking or awaiting |
| **Suspended** | Architecturally paused; state and context preserved; no steps invocable |
| **Waiting** | Blocked on architecturally defined condition (capability response, event, barrier, timeout) |
| **Completing** | All steps completed; evaluating outcome conditions; finalizing context |
| **Completed** | Terminal success state; outcome classified as success |
| **Failed** | Terminal failure state; outcome classified as failure |
| **Cancelled** | Terminated by cancellation signal prior to natural completion |
| **Compensating** | Executing compensation actions for completed steps |
| **Compensated** | All compensation actions completed |
| **Terminated** | Final disposition; resources released; no further coordination |

### 12.2 Valid Lifecycle Transitions

**Status:** EXISTING — Part 07 §7.5.3

| Source State | Valid Target States |
|-------------|---------------------|
| Created | Initialized |
| Initialized | Ready, Failed, Terminated |
| Ready | Running, Suspended, Waiting, Cancelled |
| Running | Waiting, Suspended, Completing, Failed, Cancelled |
| Waiting | Running, Suspended, Failed, Cancelled |
| Suspended | Running, Cancelled, Terminated |
| Completing | Completed, Failed, Compensating |
| Completed | Terminated |
| Failed | Compensating, Terminated |
| Cancelled | Terminated |
| Compensating | Compensated, Terminated |
| Compensated | Terminated |

**Invalid transitions:** Any transition not listed above is architecturally invalid. Specifically:
- Transitions from terminal states (Completed, Failed, Compensated, Terminated) to any other state
- Transitions bypassing required intermediate states
- Transitions that violate state invariants

### 12.3 Terminal States

**Status:** EXISTING — Part 07 §7.5.3

**Completed, Failed, Compensated, and Terminated are terminal states.** A Workflow Instance in a terminal state SHALL NOT transition to any other state.

### 12.4 Lifecycle Invariants

**Status:** EXISTING — Part 07 §7.5.8

The Workflow Lifecycle enforces the following invariants:
1. **Definition Immutability** — Definition SHALL NOT be modified across any lifecycle state
2. **State Consistency** — Lifecycle State SHALL be consistent with Workflow State
3. **Transition Validity** — Every transition SHALL be a member of the defined valid transition set
4. **Context Preservation** — Context SHALL be preserved across all transitions including Suspension, Waiting, Cancellation, Compensation
5. **Boundary Preservation** — Boundaries SHALL remain invariant from Initialized through Terminated
6. **Capability Autonomy** — No lifecycle state SHALL violate Capability Autonomy
7. **Terminal State Finality** — Terminal states are permanent
8. **Compensation Integrity** — All declared compensations SHALL be executed for all completed steps with defined compensations
9. **Outcome Consistency** — Outcome classification SHALL be consistent with terminal Lifecycle State
10. **Lifecycle Determinism** — Identical inputs and responses produce identical lifecycle sequences

## 13. DAG Execution Model

**Status:** EXISTING — Part 04 §4.6; Part 07 §7.3

### 13.1 DAG Structure

**Status:** EXISTING

Workflow execution proceeds as a DAG of steps. The DAG is defined by the Workflow Definition's steps and transitions. Each step is a node; each transition is a directed edge. The DAG has a single entry point (initial step or steps) and one or more terminal points (outcome steps).

### 13.2 Step Invocation

**Status:** EXISTING — Part 07 §7.6.2

Steps are invoked when:
- their preconditions are satisfied (as declared in the Workflow Definition)
- their incoming transitions have activated
- resources are available
- authorization is granted

Step invocation SHALL be mediated by the capability's execution contract. The Workflow Instance SHALL NOT dictate how the capability fulfills the contract.

### 13.3 Step Completion

**Status:** EXISTING — Part 07 §7.6.3

Upon step completion:
- produced context becomes available for propagation
- step outcome is recorded in Workflow State and Workflow Context
- outgoing transitions are evaluated for activation
- step completion triggers transition evaluation

### 13.4 Parallel Execution

**Status:** EXISTING — Part 04 §4.6; Part 07 §7.6.4

Independent steps (steps with no dependency relationship) MAY execute in parallel. Parallel execution is an implementation choice; it SHALL NOT alter architecturally observable behavior or violate invariants.

| **Join** | Converge multiple parallel branches into a single continuation point |

## 15. Context Propagation

**Status:** EXISTING — Part 07 §7.4.5, §7.6.3

### 15.1 Context Production

**Status:** EXISTING — Part 07 §7.6.3

Context is produced atomically with step completion. The produced context is the output context defined by the capability's execution contract, transformed according to the Workflow Definition's context propagation rules for that step. No partial context is visible to other steps.

### 15.2 Context Consumption

**Status:** EXISTING — Part 07 §7.6.3

Context is consumed at step invocation. The consumed context is derived from the current Workflow Context according to the step's consumed context specification. Context consumption SHALL NOT mutate the source context.

### 15.3 Context Propagation Rules

**Status:** EXISTING — Part 07 §7.6.3

Context propagation follows the architectural paths defined by Workflow Transitions and the context propagation rules of the Workflow Definition. Context SHALL:
- flow from producing steps to consuming steps along transition paths
- NOT propagate outside declared transition paths
- NOT propagate to steps whose preconditions are not satisfied

### 15.4 Context Visibility

**Status:** EXISTING — Part 07 §7.6.3, §7.7.3

Context visibility is governed by the Workflow Definition's context scoping rules and the Boundary Component. Context elements are visible only to steps declared within their scope. Context SHALL NOT be visible across workflow boundaries except through explicitly declared workflow inputs and outputs.

### 15.5 Context Continuity

**Status:** EXISTING — Part 07 §7.6.3, §7.5.8 Invariant 4

Context continuity SHALL be maintained across all coordination points: step invocations, transition evaluations, suspension and resumption, and compensation. Context SHALL NOT be reinitialized, truncated, or reordered except as explicitly specified by context transformation rules in the Workflow Definition.

### 15.6 Context Integrity

**Status:** EXISTING — Part 07 §7.4.5, §7.7.3

Context integrity SHALL be maintained throughout the lifecycle of a Workflow Instance. Context SHALL NOT be corrupted, lost, or spuriously generated. All context transformations SHALL be architecturally explicit and declared within the Workflow Definition.

## 16. Boundary Enforcement

**Status:** EXISTING — Part 07 §7.4.6, §7.6.6, §7.7.5

### 16.1 Boundary Establishment

**Status:** EXISTING — Part 07 §7.5.4

Workflow Boundaries are established in Initialized state. Boundaries define:
- workflow scope — which capabilities participate
- capability participation — how capabilities enter, participate in, and exit the workflow's coordination domain
- coordination authority — the boundary of the workflow's authority to coordinate capabilities
- context visibility — which context is internal, which is visible externally, which is opaque
- isolation — the guarantee that internal coordination does not leak to external elements

### 16.2 Boundary Enforcement Points

**Status:** EXISTING — Part 07 §7.6.6, §7.7.5

Boundaries are enforced at every architectural interface:
- step invocation SHALL NOT cross a boundary
- context propagation SHALL NOT leak across a boundary
- transitions SHALL NOT reference steps outside the boundary
- event consumption SHALL NOT bypass boundary visibility rules

### 16.3 Composition Boundaries

**Status:** EXISTING — Part 07 §7.6.6, §7.7.5

When workflows are composed, each composed workflow retains its own Coordination Boundaries. The parent workflow coordinates the child workflow as a single unit through the child's execution contract. The parent SHALL NOT access the child's internal steps, context, transitions, or state.

### 16.4 Boundary Release

**Status:** EXISTING — Part 07 §7.5.4

Boundaries are released in Terminated state. After termination, the workflow's coordination authority, context visibility, and capability participation SHALL NOT persist.

## 22. Compensation

**Status:** EXISTING — Part 04 §4.6, §4.7; Part 07 §7.5.6, §7.8.5

### 22.1 Compensation Responsibility

**Status:** EXISTING — Part 07 §7.8.5

The Workflow Instance SHALL execute compensation actions for completed steps when the workflow outcome requires it. Compensation actions are defined per-step in the Workflow Definition. Compensation Responsibility is architectural; it is not delegated to capabilities.

### 22.2 Compensation Scope

**Status:** EXISTING — Part 07 §7.8.5

Compensation Scope is determined by:
- the Workflow Definition's compensation dependency graph
- the fault classification and detection point
- the workflow's current lifecycle state

Compensation Scope SHALL NOT include steps that have not completed. Compensation Scope SHALL NOT include steps without declared compensation actions.

### 22.3 Compensation Ordering

**Status:** EXISTING — Part 07 §7.8.5

The default compensation ordering is the **reverse of step completion order** (last completed, first compensated). The Workflow Definition MAY declare an alternative compensation ordering that respects architectural dependency constraints.

### 22.4 Compensation Completion

**Status:** EXISTING — Part 07 §7.8.5

The Workflow Instance remains in the Compensating state until Compensation Completion — all compensation steps in the Compensation Scope have reached a terminal outcome. If a compensation step fails and has no declared compensation of its own, the instance transitions to Terminated with a Compensation Failed outcome.

### 22.5 Compensation Boundaries

**Status:** EXISTING — Part 07 §7.8.5

A Workflow Instance's compensation SHALL NOT cross into a parent workflow's coordination unless the parent's definition explicitly includes the child's compensation in its own compensation scope. A composed workflow's internal compensation is invisible to the parent except through the child's execution contract outcome.

### 22.6 Compensation vs Rollback

**Status:** EXISTING — Part 07 §7.5.6; Part 12.4

Compensation is NOT rollback. Compensation is architecturally defined corrective action with semantic intent (reverse, remediate, notify). Rollback implies restoring a prior state; compensation implies executing corrective actions. Compensation actions are capability execution contract invocations with semantically inverse or remedial intent.

## 23. Fault Handling

**Status:** EXISTING — Part 07 §7.8; Part 04 §4.6

### 23.1 Fault Classification

**Status:** EXISTING — Part 07 §7.8.2

| Fault Category | Architectural Origin |
|---------------|---------------------|
| **Workflow Fault** | Invalid transition, unreachable step, context transformation violation, boundary violation |
| **Capability Fault** | Execution contract returns failure outcome, signals lifecycle fault, fails to respond |
| **Transition Fault** | Transition cannot be evaluated: undefined context reference, inconsistent topology, indeterminate condition |
| **Context Fault** | Context integrity violation: absent required context, schema violation, invalid transformation result |
| **Coordination Fault** | Coordination responsibilities cannot be fulfilled: capability unresolvable, contract incompatible, authority exceeded |
| **Security Fault** | Workflow architectural action violates security invariant: unauthorized access, boundary violation, invocation without authorization |
| **External Interaction Fault** | Architectural interaction with external domain fails: Registry unavailable, EventBus delivery failure, Memory Architecture persistence failure |

### 23.2 Fault Detection

**Status:** EXISTING — Part 07 §7.8.3

Fault detection occurs at the architectural component where the fault originates or is first observable. Detection SHALL be architecturally deterministic: given identical conditions, the same fault SHALL be detected at the same architectural point.

### 23.3 Fault Propagation

**Status:** EXISTING — Part 07 §7.8.3

Faults propagate according to architecturally defined relationships:
- Capability Fault → Transition Components connected to the step's outcome
- Transition Fault → Workflow Instance coordination authority
- Context Fault → Steps and transitions depending on the affected context
- Coordination Fault → Workflow Instance lifecycle management
- Security Fault → Workflow Instance security boundary enforcement
- Workflow Fault → Workflow Definition architectural validity
- External Interaction Fault → Architectural dependency that failed

Faults SHALL NOT propagate through capability internal mechanisms, shared implementation state, timing channels, or undeclared architectural paths.

### 23.4 Fault Containment

**Status:** EXISTING — Part 07 §7.8.3

Fault effects are limited to defined scope:
- Workflow Boundaries: a fault in one workflow SHALL NOT affect another workflow
- Step Boundaries: a fault in one step SHALL NOT corrupt unrelated steps' context or state
- Capability Boundaries: a capability fault SHALL NOT expose capability internal state
- Context Scopes: a context fault SHALL NOT invalidate context outside its declared scope

### 23.5 Fault Visibility

**Status:** EXISTING — Part 07 §7.8.3

Every detected fault SHALL be recorded in Workflow Context as a fault record containing:
- fault classification
- detection point architectural identity
- architectural conditions at detection
- propagation path

Fault records SHALL be immutable once recorded.

### 23.6 Recovery Semantics

**Status:** EXISTING — Part 07 §7.8.4

Recovery is the architectural re-establishment of coordination validity after a fault. Recovery is declared in the Workflow Definition through:
- alternative transitions
- compensation paths
- suspension points
- explicit recovery steps

Recovery boundaries are architecturally defined points: step completions, synchronization points, or declared checkpoints. Recovery SHALL NOT resume from arbitrary points within step execution.

### 23.7 Fault Handling Invariants

**Status:** EXISTING — Part 07 §7.8.7

1. **Workflow Consistency** — State, Context, and Outcome SHALL remain internally consistent despite faults
2. **Context Preservation** — Context SHALL be preserved in its entirety; fault records SHALL be added, not replacing existing context
3. **Boundary Preservation** — Faults SHALL NOT cause coordination authority, context visibility, or capability participation to cross declared boundaries
4. **Capability Autonomy** — Fault responses SHALL NOT violate, bypass, or direct capability internal behavior
5. **Deterministic Fault Propagation** — Identical conditions produce identical fault propagation paths and outcomes
6. **Recovery Consistency** — Declared recovery paths SHALL be architecturally valid
7. **Compensation Integrity** — All declared compensations SHALL be executed in declared order
8. **Security Preservation** — All fault handling actions SHALL conform to Workflow Security invariants
9. **Fault Isolation** — A fault in one instance SHALL NOT affect another instance
10. **Outcome Consistency** — Final outcome SHALL be consistent with fault handling actions taken

- **causation_id** — direct cause event identifier
- **timestamp** — event creation timestamp
- **source** — emitting architectural element

### 27.4 Correlation and Causation

**Status:** EXISTING — Part 00 §0.4 P8; Part 02 §2.2.1

- **correlation_id** tracks the logical workflow from initiation to completion. All events within a single workflow instance share the same correlation_id.
- **causation_id** identifies the direct cause of an event. It links an event to the specific prior event that caused it.

### 27.5 Event Categories

- **SYSTEM** — kernel-internal operational events
- **CONTROL** — workflow/task lifecycle events
- **DATA** — data propagation events

## 33. Cross-Capability Coordination

**Status:** EXISTING — Part 06; Part 04 §4.6

### 33.1 Coordination Without Distributed Transactions

**Status:** EXISTING — Part 06

Cross-capability coordination does NOT use distributed transaction semantics. The architecture explicitly prohibits distributed transactions across capability facades. Coordination is achieved through:
- workflow-managed step sequencing
- explicit context propagation
- compensation actions for semantic undo
- event-driven state observation

### 33.2 Capability Facade Services

**Status:** EXISTING — Part 00 §0.3.2; Part 06

Four Capability Facade Services provide the integration boundary for external capability access:
- SkillService — skill/tool capability invocation
- CouncilService — council deliberation
- MCPService — MCP server access
- MemoryService — memory store access

Engineering Services access external capabilities exclusively through Facade Services. No direct Engineering Service access to external systems is architecturally permitted.

### 33.3 Coordination Through Execution Contracts

**Status:** EXISTING — Part 07 §7.6.2; Part 07 §7.10.2 Requirement 5

All cross-capability coordination is mediated through capability execution contracts. The workflow layer specifies sequencing and context; the capability layer specifies fulfillment and internal behavior. No coordination mechanism bypasses the execution contract boundary.

- implicit context sharing
- boundary violations

**Status:** EXISTING — Part 07 §7.10.3; Part 07 §7.9.2 Decision 4

The Workflow Architecture is technology-neutral. Implementation MUST NOT privilege a specific technology, execution model, or deployment pattern.

### 34.5 Determinism Requirement

**Status:** EXISTING — Part 07 §7.10.2 Requirement 10; Part 07 §7.8.7 Invariant 5

Given identical architectural inputs, implementation MUST produce identical outputs. Non-determinism in externally observable behavior is a conformance violation. This constraint prohibits speculative execution optimizations that would alter observable step invocation sequences.
