## 2. Deployment Unit Model

### 2.1 Single Deployable Unit

**[EXISTING]** Part 15 `deployment.md` §"Deployment Unit Model": HermesKernel is the single deployable unit of AI-OS. All Core Components, Core Managers, Engineering Services, Capability Facade Services, Extensions, and Governance Services operate within this single unit.

**[EXISTING]** Part 14 `14.9-Deployment-and-Infrastructure-Integration.md` §1.1: Part 00 §0.2.2 establishes v1.0 as single-process, in-memory only.

**[DERIVED]** Inference path: Single deployable unit + single-process constraint → HermesKernel is the only deployment artifact. There is no multi-process deployment topology defined in Parts 0–14.

**[UNSPECIFIED]** Packaging format, artifact type, distribution mechanism, and installation method for HermesKernel. Parts 0–14 do not specify how HermesKernel is packaged, delivered, or installed.

**[IMPLEMENTATION DECISION REQUIRED]** The implementer must choose the packaging and distribution mechanism for HermesKernel. No source Part mandates a specific format.

### 2.2 Component vs. Process vs. Deployment Unit

**[EXISTING]** Part 15 `deployment.md` §"Deployment Unit Model": Component is not process, service is not container, manager is not deployment unit. HermesKernel is the single deployable unit; all other entities are internal architectural constructs.

**[DERIVED]** Inference path: If HermesKernel is the single deployable unit, then no Core Component, Core Manager, Engineering Service, or Extension is independently deployable. All internal entities are instantiated within HermesKernel.

**[UNSPECIFIED]** Whether any internal entity may be deployed or updated independently of HermesKernel. Parts 0–14 do not establish independent deployment boundaries for internal components.

### 2.3 External System Boundary

**[EXISTING]** Part 15 `deployment.md` §"External-System Boundaries": External systems (MCP servers, model providers, identity providers, Obsidian, Graphify, web search, regulatory frameworks) are reached through the EventBus mediated by Facade Services and Core Managers. The deployment boundary is the HermesKernel process; external systems are outside this boundary.

**[DERIVED]** Inference path: External systems are outside the HermesKernel deployment boundary. Deployment concerns for external systems are the responsibility of the external system operator, not the HermesKernel deployer.

**[UNSPECIFIED]** Network topology, connectivity requirements, timeout semantics, and connection management for external system access. Parts 0–14 do not specify how HermesKernel connects to external systems at the network level.

## 4. Configuration for Deployment

### 4.1 Four-Layer Configuration Model

**[EXISTING]** Part 15 `configuration.md` §"Four-Layer Configuration Model": Configuration uses a four-layer merge: Layer 1 Defaults → Layer 2 app.yaml → Layer 3 env.yaml → Layer 4 Environment Variables. No hardcoded defaults in Kernel or Manager code.

**[EXISTING]** Part 15 `configuration.md` §"Configuration Sources": The four layers are processed in order; each subsequent layer overrides the previous.

**[DERIVED]** Inference path: Deployment configuration flows through the same four-layer model. Environment-specific values are supplied via env.yaml (Layer 3) and environment variables (Layer 4). Defaults (Layer 1) are the only values that do not require external configuration.

**[UNSPECIFIED]** The exact schema, key namespaces, and default values for Layer 1. Parts 0–14 do not define the complete configuration schema.

### 4.2 Configuration Freeze

**[EXISTING]** Part 15 `configuration.md` §"Configuration Lifecycle": Configuration is frozen at the Phase 2/3 boundary, after ConfigurationManager initialization and before Core Managers Phase 4+.

**[EXISTING]** Part 15 `deployment.md` §"Startup Semantics": Configuration loading occurs during startup; freeze occurs after Phase 3.

**[DERIVED]** Inference path: Configuration is immutable after freeze. Deployment operators must supply all required configuration through the four-layer merge before Phase 3 completes. Runtime configuration changes are not permitted.

**[UNSPECIFIED]** Whether any configuration reload mechanism exists for services. Parts 0–14 do not define runtime configuration reload for kernel components; service-level reload may exist but is not documented as a deployment concern.

### 4.3 Environment Variables

**[EXISTING]** Part 14 `14.9` §3.4/§13: Part 03 §3.5 establishes `AIOS_*` prefix for kernel-level environment variable overrides. `dependency-map.md` INF-06 confirms DEFINED.

**[EXISTING]** Part 15 `configuration.md` §"Environment Variables": Layer 4 uses `AIOS_<SECTION>_<KEY>` naming convention.

**[DERIVED]** Inference path: Environment variables are the highest-precedence configuration layer. They are frozen at the Phase 2/3 boundary. Integration components read configuration through `kernel.configuration` accessor, not directly from environment variables.

### 4.4 Configuration Validation

**[DERIVED]** Part 15 `configuration.md` §"Configuration Validation": Schema validation during merge is DERIVED. Type checking, required-field validation, range validation, and cross-field validation are UNSPECIFIED.

**[UNSPECIFIED]** Configuration validation rules, validation error handling, and fallback behavior when configuration is invalid. Parts 0–14 do not define the complete validation contract.

### 4.5 Secret Configuration

**[EXISTING]** Part 15 `deployment.md` §"Secret/Security Boundary": Secrets originate from Layer 4 (environment variables) or an external secrets mechanism. The exact mechanism is UNSPECIFIED.

**[UNSPECIFIED]** Secret loading mechanism, secret rotation policy, and secret access control. Parts 0–14 do not specify how secrets are loaded, rotated, or controlled.

## 5. Startup Sequence

### 5.1 Kernel Initialization Phases

**[EXISTING]** Part 15 `deployment.md` §"Startup Semantics": The Hermes Kernel initializes through nine phases (0–8) plus Phase 9+ for services:

| Phase | Name | What Initializes |
|-------|------|-----------------|
| Phase 0 | EventBus Bootstrap | EventBus initializes (C1, no dependencies) |
| Phase 1 | Registry Bootstrap | ServiceRegistry initializes (C2, depends: EventBus) |
| Phase 2 | Configuration Freeze | ConfigurationManager loads 4-layer merge, freezes (C3, depends: EventBus) |
| Phase 3 | Lifecycle Bootstrap | LifecycleManager initializes (C4, depends: EventBus, ServiceRegistry, ConfigurationManager) |
| Phase 4 | Memory & LLM | MemoryManager, LLMManager initialize (parallel, depends: EventBus, ConfigurationManager) |
| Phase 5 | Tools & Storage | ToolManager, StorageManager initialize (parallel, depends: Phase 4 managers) |
| Phase 6 | Context & Agents | ContextManager, AgentManager initialize (parallel, depends: Phase 4–5 managers) |
| Phase 7 | Workflows & Security | WorkflowManager, SecurityManager initialize (parallel, depends: Phase 4–6 managers) |
| Phase 8 | Observability | ObservabilityManager initializes (depends: all prior managers) |
| Phase 9+ | Service Initialization | Registered services initialize in dependency order |

**[CONFLICT]** Part 15 `runtime-map.md` §"Initialization Ordering": Model A (Part 1 nine-phase model, Phase 0–8 + Phase 9+ Services) vs Model B (Part 4 five-phase model, Phases 1–5). Preserved as CONFLICT-INIT-01. Part 15 MUST NOT silently resolve this conflict.

### 5.2 Startup Failure Behavior

**[EXISTING]** Part 15 `deployment.md` §"Startup Semantics": Startup failure behavior is defined as:

| Failure Point | Behavior |
|---------------|----------|
| Phase 0–3 failure | Kernel cannot start; FATAL |
| Phase 4–8 failure | Specific manager isolated; partial initialization rolled back per INV-INIT-001 |
| Phase 9+ failure | Specific service failed; other services continue |

**[EXISTING]** Part 15 `runtime-map.md` §"Runtime Failure Model": Partial initialization always rolled back on failure (INV-INIT-001).

**[DERIVED]** Inference path: If a Core Component or Core Manager fails during initialization, the failure cascades to subsequent phases. Services in Phase 9+ may fail independently without cascading to kernel shutdown.

### 5.3 Configuration Loading During Startup

**[EXISTING]** Part 15 `deployment.md` §"Startup Semantics": Configuration loading occurs during startup; freeze occurs after Phase 3.

**[DERIVED]** Inference path: The four-layer merge is evaluated during Phase 2. Configuration is frozen before Phase 4 begins. All components initialized in Phases 4–9+ read from the frozen configuration.

**[UNSPECIFIED]** What happens when configuration validation fails during Phase 2. Parts 0–14 do not define the error handling behavior for invalid configuration.

### 5.4 Global Singleton Accessor Availability

**[EXISTING]** Part 15 `deployment.md` §"Kernel Runtime State": Global Singleton Accessors throw `KernelNotReadyError` before the RUNNING state. Accessors are available only after Phase 3 completes.

**[EXISTING]** Part 01 §1.8.4: 13 Global Singleton Accessors (`get_eventBus`, `get_serviceRegistry`, `get_configuration`, `get_lifecycle`, `get_memory`, `get_llm`, `get_tools`, `get_storage`, `get_context`, `get_agent`, `get_workflow`, `get_security`, `get_observability`).

**[DERIVED]** Inference path: Services in Phase 9+ may safely use Global Singleton Accessors because Phase 3 has completed. Components initializing in Phases 0–3 must not use accessors for components that have not yet initialized.

## 6. Shutdown Sequence

### 6.1 Reverse Initialization Order

**[EXISTING]** Part 15 `deployment.md` §"Shutdown Sequence": Shutdown reverses initialization order:

| Shutdown Phase | Component |
|---------------|-----------|
| S9+ | Services unsubscribe and complete pending work |
| S8 | ObservabilityManager flushes metrics |
| S7 | WorkflowManager + SecurityManager shutdown |
| S6 | ContextManager + AgentManager shutdown |
| S5 | ToolManager + StorageManager shutdown |
| S4 | MemoryManager + LLMManager shutdown |
| S3 | LifecycleManager teardown |
| S2 | ConfigurationManager archives final config |
| S1 | ServiceRegistry teardown |
| S0 | EventBus drains in-flight events and shuts down (last) |

**[EXISTING]** Part 01 §1.11.2: Shutdown reverses initialization order with failure handling.

### 6.2 Shutdown Protocol

**[EXISTING]** Part 15 `deployment.md` §"Shutdown Semantics": Shutdown follows reverse initialization order. Integration events propagate shutdown status.

**[DERIVED]** Inference path: EventBus (S0) is the last component to shut down, ensuring all in-flight events are drained. Services (S9+) are the first to shut down, allowing them to complete pending work before infrastructure is torn down.

### 6.3 Shutdown Timeout

**[UNSPECIFIED]** Part 15 `deployment.md` §"Shutdown Semantics": Shutdown timeout is UNSPECIFIED (GAP-DEP-03). Parts 0–14 do not define the maximum duration allowed for shutdown completion.

**[GAP]** Shutdown timeout mechanism. The implementer must define and implement a shutdown timeout mechanism. No source Part specifies this behavior.

### 6.4 Forced Shutdown

**[UNSPECIFIED]** Part 15 `deployment.md` §"Shutdown Semantics": Forced shutdown behavior is UNSPECIFIED (GAP-DEP-04). Parts 0–14 do not define what happens when a component or service does not respond to shutdown requests within the timeout.

**[GAP]** Forced shutdown mechanism. The implementer must define and implement a forced shutdown mechanism. No source Part specifies this behavior.

### 6.5 Re-Initialization Prohibition

**[EXISTING]** Part 15 `runtime-map.md` §"Runtime Invariants": Once TERMINATED, re-initialization is PROHIBITED (INV-LC-003).

**[EXISTING]** Part 15 `deployment.md` §"Shutdown Semantics": Once a component or service reaches TERMINATED state, it cannot be re-initialized within the same HermesKernel instance.

**[DERIVED]** Inference path: After HermesKernel reaches TERMINATED state, a new kernel instance must be created for re-initialization. This is a process-level restart, not a component-level restart.

## 7. Health and Readiness

### 7.1 Health Check Model

**[EXISTING]** Part 15 `deployment.md` §"Health/Readiness": Four probe concepts are defined: Health, Liveness, Readiness, and Startup.

**[EXISTING]** Part 15 `deployment.md` §"Health/Readiness": Health aggregation is performed. Readiness criteria are defined.

**[CONFLICT]** Part 04 §4.7/§4.10 defines HealthManager as the health authority with readiness/liveness/heartbeat/diagnostics/recovery/aggregation responsibilities. Part 01 §1.8.1 does not include HealthManager in the canonical 9 Core Manager set. Part 01 §1.7.1 defines LifecycleManager as C4. This is CONFLICT-CM-01.

### 7.2 Liveness Semantics

**[EXISTING]** Part 15 `deployment.md` §"Health/Readiness": Liveness detects whether a component is alive (not deadlocked, not crashed). Liveness failure triggers immediate recovery action (restart, failover).

**[EXISTING]** Part 04 §4.10.5: Liveness indicates process viability.

**[DERIVED]** Inference path: Liveness probes detect deadlocks and crashes. When liveness fails, the component must be restarted or failed over. The specific probe mechanism, interval, and timeout are UNSPECIFIED.

**[UNSPECIFIED]** Liveness probe mechanism, interval, timeout, and failure threshold. Parts 0–14 do not define the implementation of liveness probes.

### 7.3 Readiness Semantics

**[EXISTING]** Part 15 `deployment.md` §"Health/Readiness": Readiness indicates whether a component can serve traffic or perform its function. Readiness failure triggers traffic draining.

**[EXISTING]** Part 04 §4.10.4: Readiness indicates ability to serve current function.

**[EXISTING]** Part 15 `runtime-map.md` §"Readiness Model": Service states include RUNNING, DEGRADED, and FAILED.

**[DERIVED]** Inference path: A component in DEGRADED state is not ready to serve full traffic. A component in FAILED state is not ready at all. Readiness is determined by HealthManager per Part 04 §4.10, but HealthManager's status as a Core Component is CONFLICT-CM-01.

**[UNSPECIFIED]** Readiness probe mechanism, traffic draining mechanism, and routing removal semantics. Parts 0–14 do not define how readiness is exposed to external consumers.

### 7.4 Startup Probe Semantics

**[EXISTING]** Part 15 `deployment.md` §"Health/Readiness": Startup probe determines whether a component has successfully initialized.

**[UNSPECIFIED]** Startup probe mechanism, initialization completion criteria, and startup timeout. Parts 0–14 do not define startup probe implementation.

### 7.5 Collaboration Domain Probe Semantics

**[EXISTING]** Part 15 `deployment.md` §"Health/Readiness": Collaboration domain probe semantics define 100ms response time and 3 consecutive non-responses → restart (liveness) or routing removal (readiness).

**[EXISTING]** Part 15 `deployment.md` cross-reference: RI-005/RI-006 from Part 12 define collaboration domain probe semantics.

**[DERIVED]** Inference path: The 100ms/3-strikes semantics are defined for collaboration services. The same semantics may apply to other service categories but this is not explicitly established.

### 7.6 Probe Exposure Mechanism

**[UNSPECIFIED]** Part 15 `deployment.md` §"Health/Readiness": Probe exposure mechanism is UNSPECIFIED (GAP-DEP-06). Parts 0–14 do not define how health/liveness/readiness probes are exposed to external monitoring systems.

**[GAP]** Probe exposure mechanism. The implementer must define how probes are exposed. No source Part specifies the exposure mechanism.

## 8. Failure Classification, Handling, and Recovery

### 8.1 Four Failure Classifications

**[EXISTING]** Part 15 `deployment.md` §"Failure/Recovery": Four failure classifications:

| Classification | Description | Response |
|----------------|-------------|----------|
| TRANSIENT | Retryable failure | Retry max 3 with exponential backoff |
| DEGRADED | Component continues with reduced capacity | Continue; emit ComponentDegraded event |
| CRITICAL | Component isolated | Isolate; restart max 2; emit ComponentFailed event |
| FATAL | Kernel shutdown triggered | Emergency shutdown; emit KernelFatalError event |

**[EXISTING]** Part 01 §1.12: Failure classification definitions.

**[EXISTING]** Part 01 §1.12.1: Retry budget — max 3 retries for TRANSIENT, max 2 restarts for CRITICAL.

### 8.2 Event-Mediated Failure Communication

**[EXISTING]** Part 15 `deployment.md` §"Failure/Recovery": Failures are communicated via Events, not exceptions crossing architectural boundaries. ADR-009 establishes this as an active decision.

**[EXISTING]** Part 15 `deployment.md` §"Failure/Recovery": Failure events carry correlation and causation IDs per the immutable event contract.

**[DERIVED]** Inference path: All failure communication must flow through EventBus. No exception may cross a service or component boundary. Failure events must carry correlation_id and causation_id.

### 8.3 Retry and Backoff

**[EXISTING]** Part 02 §2.4/§2.6.3: EventBus provides retry queues and dead-letter queues. Retry policy defaults: max 3 retries with exponential backoff (backoffMultiplier: 2.0).

**[EXISTING]** Part 15 `deployment.md` §"Failure/Recovery": Retry/backoff mechanisms are defined at the EventBus level.

**[DERIVED]** Inference path: TRANSIENT failures trigger retry at the EventBus level. After max retries are exhausted, the event moves to the dead-letter queue. The specific retry intervals and backoff parameters are defined in Part 02 §2.6.

**[UNSPECIFIED]** Whether integration components have independent retry budgets or participate in the kernel's RetryBudget. Parts 0–14 do not define integration-specific retry policy.

### 8.4 Circuit Breakers

**[EXISTING]** Part 14 `14.1-Architecture-Overview.md` §"Anti-Invention Corrections": Circuit breakers respond to TRANSIENT and DEGRADED operational failures only. Circuit breakers MUST NOT be triggered by architectural conformance violations.

**[DERIVED]** Inference path: Circuit breakers are a runtime resilience mechanism for operational failures. They are not a governance or conformance enforcement mechanism. The specific circuit breaker implementation, thresholds, and recovery mechanisms are UNSPECIFIED.

**[UNSPECIFIED]** Circuit breaker implementation, thresholds, and recovery mechanisms. Parts 0–14 do not define the circuit breaker contract or implementation.

### 8.5 Dead-Letter Queue

**[EXISTING]** Part 02 §2.4/§2.6.3: EventBus provides dead-letter queues. Dead-letter events are emitted as `EventDeliveryFailed` with full context. DLQ capacity is configurable (default: 10,000).

**[EXISTING]** Part 02 §2.6.3: DLQ overflow triggers escalation to `system.dlq.entry` and oncall notification. The overflowing DLQ is frozen to prevent unbounded growth.

**[DERIVED]** Inference path: Events that exhaust retry budgets are moved to the DLQ. DLQ overflow is a DEGRADED or CRITICAL condition requiring operator attention.

### 8.6 Recovery Actions

**[EXISTING]** Part 15 `deployment.md` §"Failure/Recovery": Recovery actions table defines actions for each failure classification.

**[EXISTING]** Part 15 `runtime-map.md` §"Runtime Recovery": Recovery actions include RETRY_WITH_BACKOFF, RETURN_TO_PLANNING, RETURN_TO_CODING, RETURN_TO_REVIEW, RETURN_TO_TESTING, ROLLBACK, ESCALATE_TO_HUMAN.

**[DERIVED]** Inference path: Recovery actions are triggered by RootCauseAnalyzer classification results. The WorkflowManager routes recovery actions to the responsible service via EventBus.

### 8.7 Checkpoint and Restore

**[EXISTING]** Part 15 `deployment.md` §"Failure/Recovery": Checkpoint state before CRITICAL/FATAL shutdown.

**[EXISTING]** Part 15 `runtime-map.md` §"Shutdown Model": Checkpoint state before CRITICAL/FATAL shutdown.

**[EXISTING]** Part 01 §1.11.2: Shutdown protocol includes state preservation.

**[DERIVED]** Inference path: Before CRITICAL or FATAL shutdown, the system checkpoints its state. Checkpoints are persisted to filesystem/disk. Restore loads the checkpoint and resumes execution.

### 8.8 Automatic vs. Manual Recovery

**[EXISTING]** Part 14 `14.8` §8.1: Failure communication via events does NOT imply automatic recovery. Recovery actions require explicit architectural specification.

**[EXISTING]** Part 15 `deployment.md` §"Failure/Recovery": Recovery actions are defined but automatic execution is not guaranteed.

**[DERIVED]** Inference path: Some recovery actions may be automatic (RETRY_WITH_BACKOFF for TRANSIENT failures). Others require operator intervention (ESCALATE_TO_HUMAN). The specific automation boundaries are UNSPECIFIED.

**[UNSPECIFIED]** Which recovery actions are automatic vs. manual, and the escalation thresholds for manual intervention. Parts 0–14 do not define these boundaries.

### 8.9 Zero-Downtime Rollout Requirements

**[EXISTING]** Part 15 `deployment.md` §"Rollout Strategies": Zero-downtime rollout requirements for collaboration services: rolling deployment, health gate, drain period, automatic rollback, canary for critical path changes.

**[EXISTING]** Part 15 `deployment.md` §"Rollout Strategies": Kernel rollout strategy is IMPLEMENTATION DECISION REQUIRED (IMP-DEC-01).

**[UNSPECIFIED]** Whether zero-downtime rollout applies to all service categories or only collaboration services. Parts 0–14 define zero-downtime requirements for collaboration services but do not extend this to all services.

### 8.10 Rollback Semantics

**[EXISTING]** Part 15 `deployment.md` §"Rollout Strategies": Automatic rollback is part of zero-downtime requirements for collaboration services.

**[EXISTING]** Part 15 `runtime-map.md` §"Runtime Recovery": ROLLBACK is a recovery action.

**[DERIVED]** Inference path: Rollback restores state to a previous checkpoint. It is an explicit architectural action, not an automatic consequence of failure. Workflow state is preserved at recovery boundaries; state rollback is explicit compensation, not implicit recovery.

**[UNSPECIFIED]** Rollback implementation mechanism, checkpoint selection criteria, and rollback validation. Parts 0–14 do not define the rollback implementation.

**[EXISTING]** Part 03 §3.4: ServiceRegistry event consumption contract.

**[EXISTING]** Part 15 `deployment.md` §"Shutdown Sequence": Services unsubscribe and complete pending work during S9+ shutdown phase. Shutdown reverses initialization order.

## 10. EventBus Communication

### 10.1 EventBus as Sole Communication Substrate

**[EXISTING]** Part 15 `deployment.md` §"Deployment Dependencies": EventBus is the sole inter-component communication substrate. ADR-001 establishes this as an active decision.

**[EXISTING]** Part 00 §0.4 Principle 1: All inter-component communication MUST occur via EventBus. No direct service-to-service calls, no synchronous RPC, no shared mutable state outside StateManager.

**[EXISTING]** Part 15 `runtime-map.md` §"Runtime Dependencies": EVENT dependency type — EventBus mediates all component communication.

### 10.2 Event Delivery Guarantees

**[EXISTING]** Part 15 `deployment.md` §"Deployment Dependencies": Event delivery guarantees: at-least-once (default) and at-most-once (configured).

**[EXISTING]** Part 02 §2.6.3: EventBus provides at-least-once delivery by default. At-most-once is configurable per subscription.

**[DERIVED]** Inference path: At-least-once delivery means events may be delivered more than once. Consumers must be idempotent. At-most-once delivery means events may be dropped on failure; consumers must handle missing events.

### 10.3 Event Envelope Requirements

**[EXISTING]** Part 15 `deployment.md` §"Deployment Dependencies": Every event carries correlation_id (UUID) and causation_id (UUID or null). ADR-008 establishes this as an active decision.

**[EXISTING]** Part 15 `observability.md` §"Correlation Semantics": correlation_id traces a logical workflow across event boundaries. causation_id identifies the direct cause event.
