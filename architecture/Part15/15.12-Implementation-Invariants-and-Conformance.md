## §1 Purpose

AI-OS v1.0 is the authoritative architecture specification (Parts 0–14). Those parts establish properties that MUST remain true across implementation changes because the architecture requires them. This document exists to:

- **Define implementation invariants** — properties that must remain true during implementation because authoritative sources require them.
- **Explain why they matter** — each invariant protects a specific architectural property (decoupling, observability, security, recoverability, correctness).
- **Protect architecture during coding** — a code change that violates an invariant is an architecture defect, not merely a style issue (Part 0 §0.3.1, Part 0 §0.5.1 L4).
- **Relate to conformance** — §26/§32 define how conformance is demonstrated and evidenced.
- **Relate to implementation contracts** — `implementation-contracts.md` maps these invariants to implementation; this document defines the *what*, contracts define the *how-checked*.
- **Relate to testing** — `15.11-Testing-and-Conformance-Implementation.md` defines how testing/conformance is performed; this document defines WHAT must remain invariant (Part 14 context.md §13 distinguishes "where architecture is silent" from "where it is silent-then-tested").
- **Relate to Parts 0–14** — every invariant traces to an authoritative source section.

**An invariant constrains implementation behavior without prescribing implementation technology unless the architecture explicitly prescribes that technology.**

Example of the distinction:

- *Invariant (architecture):* "All inter-component communication MUST occur via the EventBus." (Part 0 §0.4 Principle 1)
- *Implementation freedom (not architecture):* the EventBus internal queue implementation, threading model, and storage structure are implementation choices the invariant does not constrain.

## §5 Core Architectural Invariants

These apply to the architecture as a whole. Each is sourced from Part 0 Principles (FROZEN) or Part 1 structural invariants.

### INV-CORE-1 — Event-First Communication

**Statement:** All inter-component communication MUST occur via the EventBus. No direct service-to-service calls, no synchronous RPC, no shared mutable state outside StateManager.

**Source:** Part 0 §0.4 Principle 1; Part 1 §1.15.2 INV-RT-002; Part 14 context.md §13.

**Status:** EXISTING

**Scope:** All components, services, managers.

**Why it exists:** Decouples lifecycle, enables observability, replay, distributed evolution (v2.0) (Part 0 §0.4 Principle 1 Rationale).

**Implementation constraint:** Communication between services/components is via published events only.

**Implementation freedom:** EventBus internal queue, dispatch loop, and storage are implementation choices.

**Violation example:** A service calling `other_service.method()` directly.

**Verification method:** Static analysis lint flagging cross-service direct calls; runtime instrumentation (INV-RT-002).

**Evidence:** Lint gate pass; conformance test.

### INV-CORE-2 — Kernel as Pure Orchestrator

**Statement:** The Kernel MUST own exactly four (4) Core Components and MUST NOT contain domain logic (planning, coding, review, testing, deployment, operations, learning).

**Source:** Part 0 §0.4 Principle 2; Part 1 INV-STR-002.

**Status:** EXISTING

**Scope:** Kernel.

**Implementation constraint:** Kernel source files (`kernel.py`, `kernel_management.py`) MUST NOT import any service module (Part 0 §0.4 Principle 2 Enforcement).

**Implementation freedom:** Kernel internal orchestration primitives.

**Violation example:** Kernel module importing `PlanningService`.

**Verification method:** Static analysis import scan.

**Evidence:** Build-time lint pass.

### INV-CORE-3 — Capability Managers Are Kernel-Owned

**Statement:** The nine (9) Capability Managers are instantiated, owned, and lifecycle-managed by the Kernel; exposed via Global Singleton Accessors. No service may instantiate its own.

**Source:** Part 0 §0.4 Principle 3; Part 1 INV-OWN-001..005.

**Status:** EXISTING

**Scope:** Managers, Services.

**Implementation constraint:** Each manager has exactly one global accessor pair; no service instantiates a manager (INV-OWN-003).

**Violation example:** `PlanningService` constructing its own `RetryManager`.

**Verification method:** Static analysis; accessor registry check (INV-OWN-001, INV-CM-005).

**Evidence:** Build-time check.

### INV-CORE-4 — Services Are Event-Driven Actors

**Statement:** Every Service MUST extend `BaseService`, declare `depends_on`, subscribe in `on_start()`, emit typed Events, and MUST NOT call other services directly.

**Source:** Part 0 §0.4 Principle 5; Part 14 context.md §13.

**Status:** EXISTING

**Implementation constraint:** ServiceRegistry validates `depends_on` DAG; `BaseService` provides `emit()`/`subscribe()`.

**Violation example:** A Service not extending `BaseService`.

**Verification method:** Contract conformance test; `depends_on` DAG validation.

**Evidence:** L2 contract test (Part 0 §0.5.1).

### INV-CORE-5 — Capability Facade Services Bridge Events to Managers

**Statement:** The four (4) Capability Facade Services (`SkillService`, `CouncilService`, `MCPService`, `MemoryService`) MUST translate incoming Events into Manager calls and emit result Events. They MUST NOT contain business logic.

**Source:** Part 0 §0.4 Principle 7; Part 14 context.md §10.3.

**Status:** EXISTING

**Implementation constraint:** Facades are the sole execution path; Engineering Services SHALL NOT reference the manager directly (INV-6.3.1, INV-6.3.2).

**Violation example:** `SkillService` embedding skill execution business logic.

**Verification method:** Static analysis for business-logic presence; facade-only routing check.

**Evidence:** Architectural conformance check.

### INV-CORE-6 — Immutable Events with Correlation & Causation

**Statement:** Every Event MUST carry `correlation_id` and `causation_id`; Events MUST be immutable (frozen dataclass, `kw_only=True`).

**Source:** Part 0 §0.4 Principle 8; Part 2 INV-EVT-001, INV-EVT-004, INV-EVT-005.

**Status:** EXISTING

**Scope:** Event system.

**Implementation constraint:** Event base is immutable; both IDs present on every event.

**Violation example:** A mutable event; an event missing `causation_id`.

**Verification method:** EventBus immutability check on publish (INV-EVT-012); correlation/causation presence check (INV-EVT-004/005).

**Evidence:** EventBus invariant test.

### INV-CORE-7 — Explicit Failure Handling via Events

**Statement:** Failures MUST be communicated via Events (`TaskFailed`, `RetryBudgetExhausted`, `RootCauseAnalyzed`). No exceptions cross service boundaries.

**Source:** Part 0 §0.4 Principle 9; Part 14 context.md §13 (integration failures MUST NOT propagate as exceptions).

**Status:** EXISTING

**Implementation constraint:** `BaseService.on_error()` MUST emit failure event; MUST NOT raise.

**Violation example:** A service raising an exception to a caller in another service.

**Verification method:** Exception-boundary scan; failure-event emission check.

**Evidence:** Behavioral test.

### INV-CORE-8 — Configuration Is Declarative & Layered

**Statement:** Configuration MUST use the four-layer merge (defaults → app.yaml → env.yaml → env vars). No hardcoded defaults in Kernel or Manager code.

**Source:** Part 0 §0.4 Principle 10; Part 14 context.md §13 (configuration authority).

**Status:** EXISTING — four-layer order sourced to Part 0 §0.4 Principle 10 and Part 7.

**Implementation constraint:** All config via ConfigurationAuthority; no direct env/file reads (CC-S-005).

**Violation example:** A manager reading `os.environ` directly.

**Verification method:** Config scan (CC-S-005); config validation at startup.

**Evidence:** Static scan; startup validation.

### INV-CORE-9 — Version & Compatibility Are First-Class

**Statement:** Event schemas, configuration schemas, and APIs MUST carry version identifiers. Breaking changes require major version bump and migration path.

**Source:** Part 0 §0.4 Principle 11; Part 12.12 RI-012/RI-014.

**Status:** EXISTING

**Implementation constraint:** All schemas registered; semantic versioning enforced.

**Violation example:** A schema change that drops a required field without a major bump.

**Verification method:** Schema registry check (RI-014); version-presence check.

**Evidence:** Registry validation.

### INV-CORE-10 — Observability Is Built-In

**Statement:** Every component MUST emit structured logs (JSON, correlation IDs) and Events for state transitions. `StructuredLogger` is the single logging abstraction.

**Source:** Part 0 §0.4 Principle 12; Part 1 §1.15.2 INV-RT-008; Part 12.12 RI-007/RI-009.

**Status:** EXISTING

**Implementation constraint:** All structured logging through `StructuredLogger`; correlation_id on every log.

**Violation example:** A component using raw `print()` for state-transition logging.

**Verification method:** Log-enrichment invariant check; structured-log schema check.

**Evidence:** Observability conformance test.
