## 4. System Purpose and Scope

### 4.1 What AI-OS Is

**EXISTING** — Part 0 §0.2.1, Part 14.1 §8.2

AI-OS (AI Operating System) is the complete engineering operating system encompassing:

- **Hermes Kernel** (`HermesKernel` class) — Orchestration core with exactly 4 Core Components and 9 Core Managers. **Not to be confused with** `hermes-agent(EXT)`, the external hermes-agent system (separate repository, separate authority).
- **Engineering Services** — 8 event-driven SDLC phase services (Planning → Operations → Learning)
- **Capability Facade Services** — 4 thin event-driven bridges (`SkillService`, `CouncilService`, `MCPService`, `MemoryService`)
- **Extension Points** — 7 explicitly permitted variability mechanisms
- **Configuration System** — Four-layer merge architecture
- **Event System** — EventBus as sole communication substrate

### 4.2 Architectural Scope

**EXISTING** — Part 0 §0.2.1; Part 14.1 §8.2, §14.2, §14.3

The system is architecturally scoped to:

- Support autonomous engineering workflows (SDLC pipeline)
- Provide event-driven orchestration for all coordination
- Enable human-governed AI with Council consensus and FinalJudge gates
- Support extensibility through 7 documented extension points
- Provide built-in observability and deterministic recovery
- Maintain vendor independence via ModelRouter abstraction
- Ensure long-term maintainability through clear component boundaries

### 4.3 Non-Goals (Authoritative)

## 5. Architectural Principles

### 5.1 Event-First Communication
**Meaning:** All inter-component communication MUST occur via EventBus. No direct service calls, synchronous RPC, or shared mutable state outside StateManager.

**Architectural Consequence:** Decouples lifecycle, enables observability, enables replay/debugging, enables distributed evolution.

**Source:** Part 0 §0.4 Principle 1

### 5.2 Kernel as Pure Orchestrator
**Meaning:** Kernel owns exactly 4 Core Components and MUST NOT contain domain logic (planning, coding, review, testing, deployment, operations, learning).

**Architectural Consequence:** Kernel stability = system stability. Domain logic evolves rapidly; orchestration primitives evolve slowly.

**Source:** Part 0 §0.4 Principle 2

### 5.3 Capability Managers Are Kernel-Owned
**Meaning:** Nine (9) Capability Managers are instantiated, owned, and lifecycle-managed by Kernel. Exposed via Global Singleton Accessors.

**Architectural Consequence:** Cross-cutting infrastructure owned centrally. Prevents duplication and ensures consistent policy.

**Source:** Part 0 §0.4 Principle 3

### 5.4 Global Singleton Accessors Are Explicit Architecture
**Meaning:** 13 `get_xxx()`/`set_xxx()` accessor pairs are architectural fixtures, not implementation shortcuts.

**Architectural Consequence:** Dependency injection frameworks unnecessary. Accessors are testable, debuggable, auditable.

**Source:** Part 0 §0.4 Principle 4

### 5.5 Services Are Event-Driven Actors
**Meaning:** Every Service extends BaseService, declares `depends_on`, subscribes in `on_start()`, emits Events, and MUST NOT call other services directly.

**Architectural Consequence:** Uniform lifecycle, topological start/stop, health checks, event-only communication.

**Source:** Part 0 §0.4 Principle 5

### 5.6 Engineering Services Implement SDLC Phases
**Meaning:** Eight (8) Engineering Services form linear pipeline: Planning → Coding → Review → Testing → Deployment → Operations → Learning → Memory.

**Architectural Consequence:** Mirrors human SDLC; enables checkpointing, RCA, learning at boundaries.

**Source:** Part 0 §0.4 Principle 6

### 5.7 Capability Facade Services Bridge Events to Managers
**Meaning:** Four (4) Facade Services translate incoming Events into Manager calls and emit result Events. MUST NOT contain business logic.

**Architectural Consequence:** Managers pure (no EventBus dependency); Services thin; enables Manager unit testing without EventBus.

**Source:** Part 0 §0.4 Principle 7

### 5.8 Immutable Events with Correlation & Causation
**Meaning:** Every Event MUST carry `correlation_id` (workflow trace) and `causation_id` (direct cause). Events MUST be immutable (frozen dataclass, `kw_only=True`).

**Architectural Consequence:** Enables distributed tracing, replay debugging, causal analysis without log parsing.

**Source:** Part 0 §0.4 Principle 8

### 5.9 Explicit Failure Handling via Events
**Meaning:** Failures MUST be communicated via Events (`TaskFailed`, `RetryBudgetExhausted`, `RootCauseAnalyzed`). No exceptions cross service boundaries.

**Architectural Consequence:** Exceptions are control flow; events are data. Eventual consistency requires failure as data.

**Source:** Part 0 §0.4 Principle 9

### 5.10 Configuration Is Declarative & Layered
**Meaning:** Configuration MUST use four-layer merge (defaults → app.yaml → env.yaml → env vars). No hardcoded defaults in code.

**Architectural Consequence:** Environment parity; secrets via env vars; reproducible deployments.

**Source:** Part 0 §0.4 Principle 10

### 5.11 Version & Compatibility Are First-Class
**Meaning:** Event schemas, configuration schemas, and APIs MUST carry version identifiers. Breaking changes require major version bump.

**Architectural Consequence:** Production systems evolve. Schema evolution strategy is specified.

**Source:** Part 0 §0.4 Principle 11

### 5.12 Observability Is Built-In, Not Bolted On
**Meaning:** Every component MUST emit structured logs (JSON, correlation IDs) and Events for state transitions. `StructuredLogger` is the single logging abstraction.

**Architectural Consequence:** Debugging distributed event flows requires correlation from the start.

**Source:** Part 0 §0.4 Principle 12

## 10. Runtime Architecture

### 10.1 Runtime States
**EXISTING** — Part 01 §1.11

**Kernel States:** CREATED → INITIALIZING → RUNNING → SHUTTING_DOWN → SHUTDOWN

**Service States:** REGISTERED → INITIALIZING → RUNNING → DEGRADED → FAILED → SHUTTING_DOWN → SHUTDOWN

### 10.2 Startup Process
**EXISTING** — Part 01 §1.10

**Phase 0-3:** Kernel Core Components initialization (EventBus, StateManager, WorkflowManager, ResourceManager)

**Phase 4-8:** Core Managers initialization (Retry, Checkpoint, RCA, Memory, Skill, MCP, Council, AI Agency, ModelRouter)

**Phase 8:** Configuration freeze, Services initialization

**RUNNING State:** Achieved after Phase 8 completion

### 10.3 Execution Model
**EXISTING** — Part 01 §1.12

**Event-Driven:** All coordination via EventBus

**Failure Model:** Four classifications:
- **TRANSIENT:** Retry capable
- **DEGRADED:** Continue with reduced capability  
- **CRITICAL:** Isolate
- **FATAL:** Shutdown

### 10.4 Shutdown Process
**EXISTING** — Part 01 §1.11.2

**Reverse Initialization Order:** Shutdown reverses startup phases

**Service Shutdown:** Reverse topological order

**Kernel Shutdown:** Graceful shutdown with cleanup

### 10.5 Recovery
**EXISTING** — Part 01 §1.12

**Event-Based Recovery:** Failure events trigger recovery actions

**Checkpoint Recovery:** Resume from last successful checkpoint

**Retry Recovery:** Continue with fresh retry budget

### 10.6 Runtime Constraints
**EXISTING** — Part 00 §0.4 Principles 1-12

**Single Instance:** Exactly one HermesKernel per process. This refers to AI-OS's `HermesKernel` class; `hermes-agent(EXT)` is a separate external system that runs in its own process.

**Event-Only Communication:** No direct calls between services

**Immutable Events:** Frozen dataclass with correlation/causation

**Configuration Freeze:** No changes after Phase 1

**Global Accessors:** Explicit architecture for system-wide access
