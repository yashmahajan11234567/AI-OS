## 2. Purpose and Scope

### 2.1 Implementation Purpose

This document answers one question:

> **"How must plugins, extension points, and external integrations be implemented so that AI-OS remains conformant with the authoritative architecture?"**

It does so by extracting the extension model (Part 00 §0.5.2 + ADR-013, translated in Part 14.4), the integration/communication model (Part 14.2), and the external-system model (Part 14.5, 14.10) and expressing them as implementation constraints.

### 2.2 What Is Defined

- The eight explicitly permitted **extension points** (EXISTING — Part 00 §0.5.2).
- The **non-extension points** that MUST NOT vary (EXISTING — Part 00 §0.5.2).
- **Per-domain registration** mechanisms (EXISTING — Part 14.4 §4.1).
- The **seven external system categories** and their kernel entry points (EXISTING — Part 14.5 §1.1).
- Required **contracts** (INT-SEC-AUTH-001, INT-CFS-BRIDGE-001) and extension-point governance constraints (EXISTING — Part 4, Part 14).
- Lifecycle, configuration, observability, and security boundaries that DO apply (EXISTING / DERIVED).
- The explicit set of UNSPECIFIED, GAP, and CONFLICT areas that MUST NOT be invented.

### 2.3 What Is NOT Defined (and MUST NOT Be Invented)

The following are **NOT** established by Parts 0–14 and are recorded as UNSPECIFIED or GAP. They are architectural silences, not implementation requirements:

- A standalone (universal) "plugin registry" (RETRACTED — Part 14.4 §3.2; per-domain registries only).
- Plugin manifest format, plugin discovery mechanism, plugin dependency resolver, plugin hot-load/reload, plugin permission model, plugin semantic versioning, plugin load order/priority (UNSPECIFIED — Part 14.4 §5.2, §7.2).
- Dynamic loading / runtime import of plugins (UNSPECIFIED — see §13).
- Sandboxing technology or isolation mechanism (UNSPECIFIED — Part 14.4 §6.2).
- External system credential-exchange protocols, transport protocols (beyond named MCP transports), API versions, retry/timeout/circuit-breaker/fallback (UNSPECIFIED/GAP — Part 14.5 §12, §13).
- Identity-provider integration contract (GAP-05 — Part 14.10 §11.1).
- External-system runtime isolation (UNSPECIFIED — Part 14.10 §13).

## 4. Extension Architecture Overview

### 4.1 Extensibility Model

**Status:** EXISTING — Part 00 §0.5.2; ADR-013 [Active]; Part 14.4 §2.

AI-OS is extensible **only through explicitly permitted extension points**. The extensibility model is **closed**: anything not in the Part 00 §0.5.2 list is a non-extension point and MUST NOT vary.

### 4.2 Term Distinctions (MUST NOT be conflated)

| Term | Authoritative meaning | Source |
|------|------------------------|--------|
| **Extension Point** | A named, permitted variability site in Part 00 §0.5.2 (e.g., Custom Skill). | EXISTING — Part 00 §0.5.2 |
| **Plugin** | "A dynamically loaded component that extends platform functionality through declared extension points." Classified by which extension point it uses. | EXISTING (glossary) — Part 14.4 §3.1; DERIVED — Part 14.4 §3.3 |
| **Integration** | A crossing from the AI-OS Architectural Domain into a system not owned by HermesKernel. | DERIVED — Part 14.5 §0.1 |
| **Adapter** | A thin translation boundary converting an external interface into a kernel extension-point contract. | DERIVED — Part 14.4 §10.1; Part 08 §8.10 (LLM Adapter Contract) |
| **Provider** | An external system supplying capability (e.g., Model Provider). | EXISTING — Part 14.5 §1.1 |
| **Capability** | A unit of function declared/registered in a per-domain registry (e.g., ModelRouter capability registry). | DERIVED — Part 00 §0.5.2; Part 12.3 |
| **Interface** | A contract surface (e.g., `Skill`, `MemoryBackend` ABC, `MCPTransport`). | EXISTING — Part 00 §0.5.2 |

### 4.3 Architecture Position

**Status:** DERIVED — Part 14.2 §18; Part 14.4 §1.

Integration components attach at the **Extensions/Plugins layer** and communicate via EventBus, consuming kernel services only through documented extension points and Global Singleton Accessors. A plugin is **not** a distinct architectural layer or component class — it is an extension unit connected through one of the eight extension points.

## 5. Plugin Model

### 5.1 Definition

**Status:** EXISTING (glossary) — Part 14.4 §3.1; DERIVED — Part 14.4 §3.3.

> "A dynamically loaded component that extends platform functionality through declared extension points."

DERIVED implication: a plugin's classification depends on its extension point:
- Custom Skill plugin → Skill extension, registered via SkillManager.
- Custom MCP Transport plugin → MCP extension, registered via MCPManager.
- Custom Memory Backend plugin → Memory extension, registered via MemoryManager.

### 5.2 Identity

**Status:** UNSPECIFIED (plugin-specific ID) — Part 14.4 §5.2; DERIVED (registration identity) — Part 14.4 §4.1.

No plugin-specific identifier scheme is defined in Parts 0–14. Identity is established **per-domain** through the host Manager's registration mechanism (e.g., a skill is identified within SkillManager). A universal plugin ID is UNSPECIFIED.

### 5.3 Responsibility

**Status:** EXISTING — Part 00 §0.5.2 governance rows.

Each plugin type carries the contract and governance obligations of its extension point (see §8).

### 5.4 Interface and Capabilities

**Status:** EXISTING — Part 00 §0.5.2 (Mechanism column).

The interface is the extension-point-specific contract (`Skill`, `MemoryBackend` ABC, `MCPTransport`, `ConsensusAlgorithm` enum, base `AIAgent`, `ModelRouter` routing interface, `ResourceType` enum). Capabilities are those exposed by the host Manager domain.

### 5.5 Lifecycle and Ownership

**Status:** EXISTING (Service-type) — Part 14.4 §5.1; UNSPECIFIED (plugin-specific) — Part 14.4 §5.2.

Service-type plugin components follow the BaseService lifecycle (§12). A plugin-specific lifecycle (unload/cleanup/hot-reload) is UNSPECIFIED. Plugin code executes within the kernel process via the host Manager; it MUST NOT introduce new Core Component dependencies.

## 6. Integration Model

### 6.1 Definition

**Status:** DERIVED — Part 14.5 §0.1.

An integration is **external** when it crosses from the AI-OS Architectural Domain into a system not owned, controlled, or governed by HermesKernel.

### 6.2 External Boundary

**Status:** DERIVED — Part 14.5 §0.2.

The integration boundary is an **architectural** boundary (ownership/governance), not automatically a process, network, host, container, or security boundary. A co-located system may still be external if not kernel-owned and reached through the integration boundary.

### 6.3 Identity

**Status:** EXISTING — Part 14.5 §1.1 (external system categories).

External systems are identified by category (MCP Servers, LLM/Model Providers, Identity Providers, Obsidian Vault, Graphify Graph Store, Web Search, External Compliance Frameworks). No per-instance external-system ID scheme is established beyond category.

### 6.4 Responsibility / Interface / Ownership

**Status:** EXISTING — Part 14.5 §1.1, §15; DERIVED — Part 14.5 §2.

Each external system bridges to the kernel via a designated kernel entry point (Facade Service or Core Manager direct bridge). The integration contract on the kernel side (INT-CFS-BRIDGE-001, INT-SEC-AUTH-001) is kernel-owned; the external protocol is externally-owned. The kernel does NOT control external availability, versions, or contracts.

### 6.5 Lifecycle

**Status:** UNSPECIFIED (external connection lifecycle) — Part 14.5 §4.1, §4.2; EXISTING (MCP transport binding responsibility) — Part 14.5 §4.1.

MCPService manages transport binding (stdio, SSE, WebSocket, HTTP) as an architectural responsibility; the specific connection lifecycle, pooling, and retry are UNSPECIFIED. External systems do not participate in the kernel lifecycle.

## 11. Discovery and Resolution

### 11.1 Discovery

**Status:** UNSPECIFIED (plugin discovery mechanism) — Part 14.4 §5.2; DERIVED (per-domain resolution) — Part 14.4 §4.1.

Parts 0–14 define **no** plugin discovery mechanism: no filesystem scanning, no package scanning, no network discovery, no reflection, no dynamic import, no service discovery for plugins.

**Classification:** UNSPECIFIED.

Resolution of which extension implements a capability occurs **within** the per-domain registry (e.g., ModelRouter capability registry resolves a model provider). This is registration-time resolution, not runtime discovery.

### 11.2 Capability Discovery (Part 12.3)

**Status:** EXISTING (concept) / DERIVED — Part 12.3; classification note below.

Part 12.3 describes a Capability Registry and Agent Registry with discovery mechanisms (passive query, active advertisement, event notification, hierarchical lookup) and discovery protocols (REST/HTTP, gRPC, WebSocket, mDNS/DNS-SD, custom binary).

**Classification note:** Part 12.3's discovery protocols (network endpoints, heartbeats, gRPC/REST transports) are NOT established as the v1.0 plugin/extension discovery mechanism. Part 14.4 §5.2 explicitly marks plugin discovery as UNSPECIFIED for v1.0, and Part 14.10 §13 confirms v1.0 is single-process, in-memory only (no network discovery infrastructure). Therefore:
- The **capability registry concept** (capability identifier + version + provider mapping) is EXISTING (Part 12.3; ModelRouter capability registry per Part 00 §0.5.2).
- The **dynamic discovery protocols/transports** described in Part 12.3 are UNSPECIFIED for v1.0 plugin/extension use and MUST NOT be assumed as architecture for the 8 extension points.

This tension is recorded as a GAP (see §34) and is not silently resolved.

## 14. Capability Model

**Status:** DERIVED — Part 00 §0.5.2; Part 12.3; Part 14.4 §4.1.

- **Declaration:** Capabilities are declared by registering an extension in its per-domain registry (e.g., ModelRouter capability registry for model providers).
- **Ownership:** The host Manager owns the capability domain; the kernel owns Core Manager lifecycle (INV-OWN-001, Part 1 §1.8.3).
- **Discovery:** Per-domain registry resolution (registration-time); dynamic capability discovery transports are UNSPECIFIED for v1.0 (§11.2).
- **Access:** Via Facade Services (Engineering Service path) or Core Manager accessors (kernel-internal), never direct external calls (INV-6.3.2, INV-6.4.3).
- **Authorization:** Protected operations route through INT-SEC-AUTH-001 (SecurityManager) — conditioned on CONFLICT-03 (§19).
- **Scope:** Capabilities are scoped to their Manager domain; no cross-domain capability token is defined.

## 15. Adapter and Provider Boundaries

### 15.1 Core ↔ Adapter

**Status:** DERIVED — Part 14.4 §10; Part 08 §8.10.

An adapter translates an external tool/service interface into the kernel's extension-point contract. It MUST be a **thin bridge** (ADR-007): translate events into Manager calls; MUST NOT contain business logic; MUST NOT interpret/transform/enrich Manager return values beyond serialization.

### 15.2 Adapter ↔ External System

**Status:** EXISTING (MCP trust model) — Part 14.5 §4.1; DERIVED (others) — Part 14.5 §5–§9.

- MCP Servers are treated as **untrusted**; MCPService validates all inbound responses, enforces schema conformance, applies size limits, sanitizes errors before entering the trust domain (Part 6 INV-6.4.2, INV-6.4.5).
- LLM Provider adapters conform to the LLM Adapter Contract (Part 08 §8.10); interchange requires zero execution-layer code change (INV-EXEC-RT-010).
- Not every external system requires an adapter; Core Managers bridge directly to LLM Providers, Identity Providers, Obsidian, Graphify, Web Search without Facade mediation (Part 14.5 §1.1 layer distinction).

### 15.3 Provider Contracts

**Status:** EXISTING — Part 14.5 §1.1; Part 08 §8.10.

## 16. External System Boundary

**Status:** DERIVED — Part 14.5 §0, §2; Part 14.10 §3.

- **What crosses:** Capability calls and data, mediated by Facade Services (Engineering Service path) or Core Manager direct bridges. External systems do NOT participate in the EventBus (Part 00 §0.4 Principle 12; ADR-001).
- **Who owns it:** The integration boundary (Facade Services, SecurityManager) is kernel-owned; the external system is externally-owned.
- **Trust:** Three hard external trust boundaries exist where data crosses — Obsidian Vault, Graphify Graph Store, LLM/Model Providers — all credentialed via SecretManager (DERIVED; components.md §7.2).
- **Validation:** Inbound external responses validated at the bridge (MCPService schema/size/error sanitization).
- **Failure boundary:** External failures propagate as EventBus failure events for Facade-mediated paths only (Part 14.5 §12.1).
- **The boundary is architectural, not infrastructural** — does NOT automatically imply process/network/host/container/security isolation (Part 14.5 §0.2).

## 18. Secrets and Credentials

## 22. Event Integration

**Status:** EXISTING — Part 14.4 §10.2; ADR-008/009/012; Part 14.5 §11, §12.

## 26. Retry and Timeout

### 26.1 Retry

**Source tension (preserved, not resolved):** Part 08 §8.10 defines provider-level recovery behavior for the LLM/vendor adapter contract — exponential backoff retry (max 3 attempts), failover to the next healthy provider of the same type, `PROVIDER_UNAVAILABLE` emission, and `healthCheck()` (adapters MUST respond within 5s). This document follows the integration classification (GAP/UNSPECIFIED) because its scope is integration behavior, and records the Part 08 vs Part 14.5 tension as a preserved cross-Part conflict rather than silently reconciling it. Whether integration components MAY rely on the Part 08 adapter retry/failover mechanics is therefore UNSPECIFIED pending ARB reconciliation.

## 31. Implementation Constraints

### 31.1 MUST Preserve

- Implement only via the 8 extension points (§7) and per-domain registries (§10).
- Emit events with `correlation_id`/`causation_id` (ADR-008).
- Route protected operations through INT-SEC-AUTH-001 (SecurityManager) — subject to CONFLICT-03.
- Obtain configuration via ConfigurationManager; never read env vars / local files directly.
- Keep Facade Services thin (ADR-007); no business logic in adapters.
- Treat external systems as untrusted at the bridge (MCP validation/sanitization).
- Respect all trust boundaries (§20); preserve architectural boundary ≠ security boundary.

### 31.2 MUST NOT Violate

- Do NOT modify/override non-extension-point interfaces (EventBus, Kernel lifecycle, BaseService, ServiceRegistry order, StateManager scopes, Checkpoint format, RetryBudget semantics, global accessor signatures).
- Do NOT create a universal plugin registry (RETRACTED).
- Do NOT call external systems directly from Engineering Services (INV-6.3.2).
- Do NOT bypass SecurityManager for protected operations (within applicable scope).
- Do NOT invent sandboxing/isolation/transport/auth/authz/retry/timeout/fallback mechanisms.

### 31.3 SHOULD Preserve

- Prefer event-mediated communication post-initialization.
- Emit structured logs (JSON) for state transitions.
- Respect the EventType catalog and domain naming scheme (no sixth scheme).

### 31.4 Implementation Choices (left to implementer, within bounds)

- The concrete sandboxing technology (UNSPECIFIED).
- The concrete external protocol clients (UNSPECIFIED protocol; adapter contract is fixed).
- Internal code organization of an extension, provided it satisfies the extension-point contract.

### 31.5 UNSPECIFIED Behavior (record, do not invent)

Plugin manifest, plugin discovery, plugin dependency resolver, plugin hot-reload, plugin permission model, plugin semver, plugin load order, dynamic loading mechanism, sandboxing mechanism, external credential exchange/rotation, external transport protocols (except named MCP transports), external API versions, external retry/timeout/circuit-breaker/fallback, external-system configuration schema, identity-provider integration contract, bus-level authn/authz, logger secret-redaction control, external runtime isolation.
