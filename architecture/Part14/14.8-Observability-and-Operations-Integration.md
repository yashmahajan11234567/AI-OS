# 14.8 Observability and Operations Integration

**Status:** DRAFT — Integration Artifact
**Version:** 1.0.0
**Date:** 2026-08-13

> **Scope:** This chapter documents observability and operational relationships established by the AI-OS architecture in Parts 0–13. It does not specify implementation mechanisms, backends, transports, or operational runbooks. Where Parts 0–13 are silent, this chapter records **UNSPECIFIED** and does not invent a value.

---

## 14.8.1 Purpose and Scope

**Status:** DERIVED

This chapter documents the observability and operations integration surface for AI-OS. It covers:

- logging and structured logging;
- metrics and telemetry;
- tracing;
- health;
- correlation and causation;
- event, component, and service observability;
- operational boundaries;
- failure visibility;
- governance observability;
- observability-related security;
- canonical GAPs, conflicts, and UNSPECIFIED items.

This chapter does not specify:

- log aggregation, retention, or shipping;
- metric names, schemas, or exporters;
- telemetry backends or protocols;
- tracing protocols or span formats;
- health-check probes, intervals, or endpoints;
- alerting thresholds, channels, or SLOs.

These are implementation concerns outside Part 14 scope.

## 14.8.2 Logging Integration

### 2.1 StructuredLogger

**Status:** DERIVED / CONFLICT

Part 00 §0.4 Principle 12 establishes a single logging abstraction named `StructuredLogger`. Part 00 §0.4 Principle 12 does not classify `StructuredLogger` as a Core Component.

`StructuredLogger` is referenced in Part 3 §3.6 as the "last Core Component," which conflicts with Part 1 §1.7.1 (which lists `LifecycleManager` as C4). `interfaces.md` §2.1.1 explicitly removes `StructuredLogger` from the Core Component list and sides with Part 1 §1.7.1.

**This conflict is preserved as CONFLICT-02 and is not resolved in this chapter.**

Part 14 MUST NOT classify `StructuredLogger` as a Core Component until ARB resolution.

### 2.2 ObservabilityManager Logging Dependency

**Status:** DERIVED

`ObservabilityManager` consumes `StructuredLogger` for logging.

**Inference path:**
1. Part 1 §1.8.1 defines `ObservabilityManager` (M9).
2. `components.md` §4.9 records `ObservabilityManager` dependencies as `[DERIVED] EventBus; StructuredLogger (logging backend)`.
3. `components.md` §4.9 records `ObservabilityManager` consumption of `StructuredLogger` as a logging backend `[DERIVED]`.

**Result:** `ObservabilityManager` logging flows through `StructuredLogger`.

**Not established:**
- log output destinations;
- log aggregation or shipping;
- log retention policy;
- log formats beyond "structured logs";
- log rotation;
- log indexing.

These are **UNSPECIFIED**.

### 2.3 Logging Ownership

**Status:** UNSPECIFIED

`ObservabilityManager` consumes `StructuredLogger`. This does not establish that `ObservabilityManager` owns:
- log storage;
- log retention;
- log transport;
- log security policy;
- log aggregation.

Only the consumption relationship is established. Ownership of these concerns is **UNSPECIFIED**.

### 4.2 Trace Context Fields in Event Envelope

**Status:** EXISTING

Part 12 event envelope includes trace context fields: `traceId`, `spanId`, `parentSpanId`, `traceFlags`, `baggage`.

Source: `schemas.md` §7.1 — Part 12 trace context schema.

These fields are embedded in events/messages. Their mapping to distributed tracing is **DERIVED**.

**Not established:**

These are **UNSPECIFIED**.

### 4.3 Correlation and Causation IDs

**Status:** EXISTING

Every event **MUST** carry `correlationId` and `causationId`.

Source: ADR-008; `interfaces.md` §2.4.1 INT-EVT-BUS-001 Event contract includes `correlationId` and `causationId` fields; Part 12 event envelope includes `correlationId` / `causationId`.

This is enforced by the EventBus interface (INT-EVT-BUS-001) `[EXISTING]` (`interfaces.md` §2.4.1).

**Correlation ID ≠ distributed tracing.** Correlation IDs enable tracing a logical workflow across event boundaries. They do not establish a distributed tracing system.

**Causation ID ≠ trace propagation.** Causation IDs identify the direct cause event. Propagation semantics beyond event fields are **UNSPECIFIED**.

## 14.8.15 Canonical Conflicts

### CONFLICT-02: StructuredLogger Component Classification

**Parties:** Part 3 §3.6 / `interfaces.md` §2.1 / `dependency-map.md` CC-04 vs Part 1 §1.7.1 / Part 00 §0.4 Principle 12

Part 3 §3.6 and `dependency-map.md` CC-04 reference `StructuredLogger` as a Core Component. Part 1 §1.7.1 defines C4 as `LifecycleManager`. Part 00 §0.4 Principle 12 names `StructuredLogger` as the single logging abstraction but does not classify it as a Core Component. `interfaces.md` §2.1.1 explicitly removes `StructuredLogger` from the Core Component list and sides with Part 1 §1.7.1.

**This chapter preserves CONFLICT-02 and does not resolve it.** Part 14 MUST NOT treat `StructuredLogger` as a Core Component until ARB resolution.

### CONFLICT-03: AuthN/AuthZ Scope

**Parties:** Part 00 §0.2.2 vs Part 13 / `dependency-map.md` / 14.10

Part 00 §0.2.2 defers AuthN/AuthZ to v2.0 ("Kernel assumes trusted single-tenant process"). Part 13 governance architecture and `dependency-map.md` reference governance-level security as active in v1.0. 14.10 documents this as CONFLICT-03.

**This chapter preserves CONFLICT-03.** Manager-level authorization for `ObservabilityManager` is therefore **UNSPECIFIED** pending ARB resolution.
