## 14.11.1 Purpose and Scope

**Status:** DERIVED

### 14.11.1.1 Why Integration Schemas and Contracts Exist

Integration schemas and contracts exist to govern the boundaries through which AI-OS components, extensions, external systems, and domain applications exchange data. They define the shape of events flowing through EventBus, the structure of payloads exchanged across integration boundaries, the versioning rules that permit safe evolution, and the ownership and validation responsibilities that ensure contracts remain trustworthy as the platform evolves.

In AI-OS, every boundary crossing carries a contract: the producer emits an event with a defined envelope and payload; the consumer subscribes to a topic with expectations about that envelope. Schemas make those expectations explicit and verifiable. Contracts make those verifications enforceable.

**DERIVED from:** glossary.md §3.13 (schema definition), §6.11 (contract definition), §6.12 (Schema Registry); Part 00 §0.4 Principles 1, 8, 11; context.md §6.1–6.2.

### 14.11.1.2 What This Chapter Covers

This chapter catalogs and analyzes the schema and contract layer of AI-OS integration architecture as established by Parts 0–13 and the Part 14 support documents. It covers:

1. The conceptual model of integration contracts and schemas, and the distinction between them
2. Schema categories present in the source architecture
3. Event contracts, including envelope specifications, metadata, correlation, causation, and event identity
4. Service and interface contracts, including lifecycle and health contracts
5. Data and state contracts, including ownership and reader/writer relationships
6. Contract ownership distinctions (producer, consumer, owner, validator, publisher, subscriber)
7. Versioning and compatibility rules established by source Parts
8. Validation requirements and mechanisms
9. Immutability and evolution rules
10. Contract compatibility failures
11. Security-relevant contract properties
12. Schema-related GAPs, CONFLICTs, UNSPECIFIED items, and RETRACTED architecture
13. Source traceability for every major claim

### 14.11.1.3 What This Chapter Deliberately Does Not Define

## 14.11.2 Schema and Contract Model

**Status:** DERIVED

This section defines the conceptual vocabulary used throughout this chapter. Where exact definitions are not established in Parts 0–13, the term is marked UNSPECIFIED or DERIVED rather than assigned an invented formal definition.

### 14.11.2.1 Schema vs. Contract — Architectural Distinction

**Status:** DERIVED

This distinction is fundamental to this chapter. The two terms are NOT interchangeable.

**SCHEMA** defines the **structure/shape of information**. It answers: "What does this data look like?" A schema specifies fields, types, constraints, and semantics for data exchanged across an integration boundary. Examples in AI-OS: event envelope schemas, payload schemas, configuration schemas.

**CONTRACT** defines the **expectations/constraints governing interaction or exchange**. It answers: "What must participants do?" A contract specifies obligations, guarantees, versioning rules, compatibility requirements, and validation responsibilities between a provider and its consumers. A contract *references* schemas but is not itself a schema.

In AI-OS, these participate in integration as separate layers:
- The **Schema Registry** (Part 12 schemas.md §46) stores schemas.
- Contracts reference those schemas and add behavioral obligations.
- An event contract specifies the envelope format (schema), the payload schema (schema), the delivery semantics (contract obligation), the processing expectations (contract obligation), and the versioning rules (contract obligation).

**DERIVED:** This distinction follows from glossary.md §6.11 (contract as "machine-enforceable specification of obligations and guarantees") and glossary.md §3.13 (schema as "machine-readable description of the structure, constraints, and semantics of data"). A contract governs interaction; a schema describes data shape. They are complementary but distinct architectural constructs.

**AI-agent safeguard:** When this chapter refers to a "schema," it describes data shape. When it refers to a "contract," it describes interaction obligations. The two must not be conflated. A schema reference does not imply an implementation exists. A contract reference does not imply an API exists.

### 14.11.2.3 Integration Contract

**Status:** EXISTING / DERIVED

An integration contract is a **contract** — a machine-enforceable specification of the obligations and guarantees between a provider and its consumers (glossary.md §6.11). This is a **contract**, not a schema: it governs interaction, not data shape.

**Source / provenance:** glossary.md §6.11; Part 00 §0.4 Principle 11; Part 12 schemas.md §46.

**Purpose:** Govern data exchange across an integration boundary by identifying the provider, the consumers, the schema versions accepted, and the compatibility guarantees.

**Provider / Consumer:** Determined by the specific contract instance.

**Inputs / Outputs:** Determined by the specific contract instance. Where source Parts do not enumerate these, they are UNSPECIFIED.

**Versioning / compatibility:** Semantic versioning is required (Part 00 §0.4 Principle 11: "Event schemas, configuration schemas, and APIs MUST carry version identifiers. Breaking changes require major version bump and migration path.").

**DERIVED:** An integration contract in AI-OS is therefore a versioned, schema-referenced **contract** that governs data exchange across a boundary. The exact contract format (fields, structure, enforcement mechanism) is not defined as a single canonical document type in Parts 0–13.

**UNSPECIFIED:** The canonical contract format (field-level specification, enforcement mechanism, serialization format) is not established in Parts 0–13.

### 14.11.2.4 Schema

**Status:** EXISTING

**Source / provenance:** Part 12 schemas.md §3–142, §196; glossary.md §3.13.

**Purpose:** Describe the structure, constraints, and semantics of data exchanged across an integration boundary.

**Provider / Consumer:** Schema owner is the producing component that registers the schema in the Schema Registry. Consumers reference the schema.

**Inputs / Outputs:** N/A for schemas — schemas describe data shape, not interaction.

**Versioning / compatibility:** Schema immutability — changes require a new version (Part 12 schemas.md §196). Versioning enforced via Schema Registry compatibility rules (Part 12 schemas.md §142, §171–18).

**Existing source-defined behavior:**
- AI-OS schemas use JSON Schema (Part 12 schemas.md §3) — **EXISTING**
- Schemas are immutable once published — changes require a new version (Part 12 schemas.md §196) — **EXISTING**
- Versioning enforced via Schema Registry compatibility rules (Part 12 schemas.md §142, §171–18) — **EXISTING**
- Semantic annotations (units, privacy classification, PII markers) and invariant links as structured schema extensions — **PROPOSED** (not formally established in Parts 1–13)

**Related conflicts:** CONFLICT-04 (envelope field naming affects schema references).

**Related GAPs / UNRES / UNSPECIFIED items:** GAP-UNIVERSE (no unified schema registry); GAP-NAMING; GAP-SPEC-COUNT.

## 14.11.7 Contract Ownership

**Status:** EXISTING / DERIVED / UNSPECIFIED

This section explicitly distinguishes the ownership roles relevant to integration contracts. These roles are NOT interchangeable.

### Producer

**Status:** EXISTING

A component that emits events or serves as the authoritative source for one or more interfaces.

Existing source-defined behavior:
- At-least-once is the default delivery guarantee (Part 12 events.md §34; Part 12 12.7 §9.1) — **EXISTING**
- Best-effort and exactly-once are configurable per message (Part 12 12.7 §9.1) — **EXISTING**
- Exactly-once delivery is NOT a transport-layer guarantee (Part 12 events.md §34) — **EXISTING**
- Producers "declare guarantees in their manifest" — **PROPOSED** (Parts 1–13 define per-message guarantees but do not establish a manifest-driven declaration) (glossary.md §3.17)

**Part 14 implication:** Producer ≠ owner. A component can produce events for a schema it does not own (e.g., a Facade Service produces events based on Manager call results). The schema owner is the component that defines and publishes the schema version in the Schema Registry.

### Consumer

**Status:** EXISTING

A component that consumes events emitted by a producer, or a component that depends on another component's interface for contract compliance.

Existing source-defined behavior:
- Consumers declare dependencies in registration via `dependsOn` (Part 3 §3.4.4) — **EXISTING**
- Consumers declare "requirements" (minimum contract version, required invariants, expected SLIs, fallback behavior) in a manifest — **PROPOSED** (not formalized in Parts 1–13) (glossary.md §3.16)

**Part 14 implication:** Consumer ≠ validator. A consumer validates incoming events against the producer's schema for its own protection, but the consumer does not own the validation authority for the producer's schema.

### Owner

**Status:** EXISTING / DERIVED

The component or entity that has the authority to define, publish, and evolve a schema or contract.

- Core Components and Core Managers: owned exclusively by HermesKernel (Part 01 §1.8.4) — **EXISTING**
- Services: registered in ServiceRegistry (Part 01 §1.7.2) — **EXISTING**
- Custom extensions: registered via documented extension points (Part 00 §0.5.2) — **EXISTING**
- Schema Registry: centralized, versioned repository for all formal schemas (Part 12 schemas.md §46) — **EXISTING**

**DERIVED:** Schema ownership is held by the component that registers the schema in the Schema Registry. The Schema Registry is the authoritative repository, but the registry itself does not own the schemas — it stores them. Schema ownership is implicit in the producing component's registration.

**UNSPECIFIED:** Whether there is a formal "schema owner" role with exclusive publish/update authority (vs. any registered component being able to publish schemas) is not defined in Parts 0–13.

### Validator

**Status:** EXISTING / UNSPECIFIED

The entity responsible for verifying that a contract instance (event, payload, request) conforms to its schema.

- Schema validation via JSON Schema conformance (Part 12 schemas.md §3) — **EXISTING**
- Schema Registry compatibility rules (Part 12 schemas.md §142, §171–18) — **EXISTING**
- Runtime invariant enforcement (Part 12.12 §16) — **EXISTING**

**UNSPECIFIED:** Whether AI-OS establishes a named "validator" component or service (as opposed to validation being an implicit property of Schema Registry and runtime invariant checks) is not defined in Parts 0–13.

**Part 14 implication:** Part 14 MUST NOT invent a "SchemaValidator" or "IntegrationContractVerifier" named component. Validation in AI-OS is performed through Schema Registry compatibility checks and runtime invariant enforcement, not through a dedicated validator service.

### Publisher

**Status:** DERIVED

The entity that publishes a schema or contract definition to the Schema Registry.

**DERIVED:** In AI-OS, the publisher of a schema is the component that defines the schema and registers it in the Schema Registry (Part 12 schemas.md §46). Publishing follows the event type registration pattern: custom event types must register in the EventType catalog (Part 00 §0.5.2).

**UNSPECIFIED:** Whether there is a formal "publisher" role separate from "owner" or "producer" is not defined in Parts 0–13.

### Subscriber

**Status:** EXISTING

A component that subscribes to EventBus topics to receive events.

- EventBus is the sole communication substrate (Part 00 §0.4 Principle 1) — **EXISTING**
- Services subscribe in `on_start()` (Part 00 §0.4 Principle 5) — **EXISTING**
- Integration components subscribe to relevant event topics as part of their integration pattern (context.md §5.2) — **DERIVED**

**Part 14 implication:** Subscribers do not own the schemas they subscribe to. Subscribers must handle schema evolution according to the compatibility rules established by the schema owner in the Schema Registry.

**Status:** EXISTING

**Status:** EXISTING / DERIVED

Contract versioning follows the same SemVer rules as schema versioning (Part 00 §0.4 Principle 11).

**DERIVED:** A contract version encompasses all schemas, interfaces, and behavioral obligations in the contract. When any schema within the contract changes in a breaking way, the contract version must bump its major version.

**UNSPECIFIED:** Whether AI-OS establishes a formal "contract version" field distinct from schema version and interface version is not defined in Parts 0–13. **Status:** EXISTING

Implementation version is the version of the producing component's code, tracked via `ComponentIdentity.version` (Part 2 §2.2.2, semver).

**Part 14 implication:** Implementation version is independent of schema version, event version, and interface version. A component can implement schema v1.0 while its own implementation is at v2.3.1.

**Status:** EXISTING / RETRACTED

## 14.11.10 Immutability and Evolution

**Status:** EXISTING / DERIVED / UNSPECIFIED / PROPOSED

**Status:** EXISTING

**DERIVED:** Contract evolution follows the same rules as schema evolution: new versions for breaking changes, backward-compatible changes for minor/patch versions, migration paths for major version transitions.

**UNSPECIFIED:** The exact migration procedure for contract version transitions (how consumers are notified, how producers deprecate old versions, how long old versions remain supported) is not defined in Parts 0–13.

## 14.11.15 AI-Agent Contract Rules

**Status:** EXISTING

This section establishes explicit rules preventing future AI agents from making unsupported deductions when working with integration schemas and contracts. These rules are derived from the Integrity Rules in context.md §0.6 and the Machine-Agent Safety Rules in MEMORY.md §10.

### Anti-Deduction Rules

The following deductions are PROHIBITED unless explicitly supported by the five permitted files or an accepted ADR:

| Prohibited Deduction | Why It Is Prohibited | Correct Approach |
|---------------------|---------------------|-----------------|
| schema → database table | No database schema implementation is established in Parts 0–13 | Document only the schema as an event/payload contract; do not infer persistence implementation |
| interface → HTTP API | No HTTP API specification is established in Parts 0–13 | Document only the interface as a contract boundary; do not infer transport protocol |
| event → Kafka topic | No Kafka topic specification is established in Parts 0–13 | Document only the event as an EventBus event; do not infer broker implementation |
| contract → OpenAPI | No OpenAPI specification is established in Parts 0–13 | Document only the contract as a versioned obligation set; do not infer OpenAPI format |
| schema → JSON Schema (as implementation) | JSON Schema is the validation *mechanism* (Part 12 schemas.md §3), not a schema *definition format* for all schemas | Distinguish validation mechanism from schema format |
| version → SemVer (universally) | Part 2 uses SemVer; Part 12 uses integer versioning — not universal | Document version format per registry; do not assume one format |
| validation requirement → SchemaValidator | No named "SchemaValidator" component exists in Parts 0–13 | Document validation through Schema Registry compatibility checks and runtime invariant enforcement |
| event version → implementation version | Event version identifies schema version, not producing component version | Keep event version, schema version, interface version, and implementation version as distinct axes |
| producer → owner | Producer emits events; owner defines schemas — not the same role | Document producer and owner as separate roles |
| consumer → validator | Consumer validates for its own protection; does not own validation authority | Document consumer and validator as separate roles |
| interface → network boundary | Interfaces in AI-OS are contract boundaries, not necessarily network boundaries | Document interface as a contract boundary; do not infer network topology |
| payload → transport format | Payload is data content; transport format is not defined in Parts 0–13 | Document payload structure; do not infer transport mechanism |
| contract → implementation | Contracts specify obligations; implementations fulfill them | Document contract obligations; do not prescribe implementation |
| event envelope → single universal format | Two incompatible envelope specifications exist (CONFLICT-04/GAP-ENV) | Document both envelope formats; do not normalize |
| three event registries → unified registry | Three registries are partially disjoint (GAP-UNIVERSE) | Document each registry separately; do not merge |
| StateManager → known integration API | GAP-01: StateManager integration surface is undocumented | Mark as GAP; do not invent API |
| integration security → mandatory v1.0 | CONFLICT-03: Part 00 defers to v2.0; Part 13 assumes active v1.0 | Document both paths; do not resolve |
| BaseService → all services follow same pattern | Engineering Services and Facade Services follow BaseService; integration components follow same pattern only if they register as Services | Distinguish service-type integration components from extension-type components |
| EventType enum → extensible | Part 2 INV-ET-003 prohibits late EventType registration; ADR-013 lists "custom events" as extension point (GAP-EXT) | Document the conflict; do not assume extensibility |
| exactly-once → transport guarantee | Exactly-once is application-layer only (idempotent producer AND consumer) | Document at-least-once as default; exactly-once as application-layer achievement |

### Mandatory Behaviors for AI Agents

When working with this chapter, AI agents MUST:

1. **Read the five permitted control files completely** before making any claim about schemas or contracts.
2. **Label every claim** with its status from the Part 14 taxonomy (context.md §0.1, MEMORY.md §7).
3. **Show inference paths** for every DERIVED claim (context.md §0.6 Integrity Rule 8).
4. **Preserve all CONFLICTs** without silent resolution (context.md §0.6 Integrity Rule 3).
5. **Mark all GAPs and UNSPECIFIED items** without inventing architecture (context.md §0.6 Integrity Rule 4).
6. **Respect RETRACTED architecture** as historical corrections only (MEMORY.md §6, glossary.md §8).
7. **Not cite Part 14 itself** as authority for architectural facts (context.md §0.6 Integrity Rule 2).
8. **Not cite draft ADRs** (P13-ADR-001 through P13-ADR-010) as established architecture (MEMORY.md §3.3).
9. **Escalate CONFLICTs to ARB** rather than resolving them locally (context.md §0.1, MEMORY.md §15).
10. **Propose via ADR** rather than invent — any new schema, contract, interface, or mechanism must be proposed through the ADR process, not introduced directly in Part 14 documentation (context.md §0.6 Integrity Rule 5).
