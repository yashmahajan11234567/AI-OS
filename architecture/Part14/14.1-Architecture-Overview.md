## 1. Purpose

**EXISTING** — Part 14 README §Purpose; Part 00 §0.5.1.

Part 14.1 provides a high-level orientation view of how the AI-OS architecture components from Parts 0–13 integrate into a cohesive system. It serves as the entry-point document for architects, developers, reviewers, integrators, and future AI agents who need to understand the overall composition before diving into domain-specific integration details in Part 14.2–14.13.

Part 14.1 does NOT redesign or reimplement any component from Parts 0–13. It documents how existing architectural elements compose through their documented interfaces, communication pathways, initialization sequences, and boundary contracts. Where source Parts are incomplete for integration use, Part 14.1 records GAPs rather than inventing solutions.

## 2. Conceptual Distinctions

**EXISTING / DERIVED** — Part 14 integrity rules; Part 00 §0.4 Principles 1–12; context.md §0.6 Integrity Rules 1–8.

The following distinctions are foundational to how Part 14 thinks about integration. Confusing any pair leads to architectural invention or overstrong claims.

| Architectural Concept | ≠ | Implementation Concept |
|---|---|---|
| Component existence | ≠ | Integration contract |
| Architectural relationship | ≠ | Implementation mechanism |
| Integration boundary | ≠ | Process boundary |
| Integration boundary | ≠ | Network boundary |
| Integration boundary | ≠ | Security / trust boundary |
| Interface existence | ≠ | Network transport |
| Event existence | ≠ | External message broker |
| Service existence | ≠ | Independent deployment unit |

**Why these matter:** Parts 0–13 establish that components, interfaces, events, and services exist as architectural definitions. They do not, by themselves, specify how those elements communicate across process, network, deployment, or security boundaries. Part 14 documents the architectural relationships. It does not invent the implementation mechanisms that would realize those relationships.

## 3. What "Integration Architecture" Means in AI-OS

**DERIVED** — Part 14 README §Scope; Part 00 §0.2.1, §0.5.2; context.md §1.1.

Integration architecture in AI-OS documents the mechanisms and boundaries through which architectural elements from Parts 0–13 relate to each other and to external entities. It covers:

- **Internal integration:** relationships between Core Components, Core Managers, Engineering Services, Capability Facade Services, and Governance Components within the AI-OS platform boundary. This is an architectural zone concept, not a security or trust boundary — the platform boundary does not automatically imply a security boundary.
- **External integration:** relationships between AI-OS architectural elements and external systems or entities where established. External integration requires crossing the AI-OS integration boundary. Examples of external system categories referenced in Parts 0–13 include: model providers, identity providers, MCP/external capability systems, external knowledge/storage systems, filesystem/disk, human operators, telemetry backends, and regulatory/compliance systems. Specific providers, vendors, or products are not established in Parts 0–13 — only these generic categories.
- **Cross-domain integration:** relationships that span multiple architectural domains simultaneously. Examples referenced in Parts 0–13 include: events carrying data across state and workflow domains, state interacting with workflow and observability, security requirements affecting event propagation, observability consuming integration events, and governance interacting with runtime behavior. Part 14 records these as DERIVED cross-domain relationships where the source establishes the participating elements; Part 14 does not create additional cross-domain mechanisms.

Integration architecture is a *compositional* activity. It connects existing architectural elements. It does not create new elements.

**EXISTING** — Part 14 README "Explicitly excluded from scope"; Part 00 §0.2.2 "Explicitly Out of Scope"; context.md §1.3 Non-Goals.

- Redesign Core Components or Core Managers

Where an integration concern touches an out-of-scope item, Part 14 labels it UNSPECIFIED and defers. It does not fill architectural silence with conventional engineering assumptions.

## 8. Status / Certainty Model

**EXISTING** — Part 14 context.md §0.1 Status Classification Policy; glossary.md §2 Status Taxonomy.

Every normative statement in Part 14 carries exactly one status label. Labels are mutually exclusive.

| Status | Meaning |
|---|---|
| **EXISTING** | Verbatim or field-for-field present in a source Part 0–13 document or accepted ADR, with explicit source citation. |
| **DERIVED** | Logically implied by one or more EXISTING statements. The inference path and source anchors must be stated. |
| **ASSUMPTION** | Adopted for continuity or scoping clarity. Not explicitly stated in source Parts. Must be flagged, reviewed before implementation, and resolved to EXISTING, DERIVED, or GAP. |
| **UNSPECIFIED** | Source Parts and accepted ADRs are silent on this detail. Part 14 must NOT invent a value, schema, or rule to fill the silence. |
| **GAP** | Source Parts partially define a concern but leave required fields, interfaces, or behavior unspecified for integration use. Requires a PROPOSED resolution or explicit deferral. |
| **PROPOSED** | A recommendation for Part 14 chapter authors to resolve a GAP or UNSPECIFIED item. Must NOT be stated as architecture fact or binding requirement. |
| **FUTURE** | Explicitly deferred in source Parts to a named future horizon (e.g., v2.0). Must NOT be introduced as v1.0 behavior. |
| **CONFLICT** | Two or more authoritative sources disagree on this point. Both sources must be preserved. Part 14 must NOT silently resolve, override, or paper over the disagreement. Escalate to ARB. |

**UNRESOLVED** is a *descriptor* applied to CONFLICT and GAP entries, not a standalone status label. A CONFLICT or GAP may be described as "UNRESOLVED — requires ARB decision." This indicates that the disagreement or missing definition remains open. It does not mean Part 14 has selected an interpretation.

**RETRACTED / CORRECTED** is used only for historical documentation of corrections (see Section 11). It is NOT a current architectural status. RETRACTED material must not be treated as current architecture.

## 9. Integration Boundaries

**DERIVED** — Part 00 §0.4 Principles 1, 2, 4, 7; Part 01 §1.2, §1.6.1; context.md §2.2–2.3; glossary.md §3.4 Architectural Boundary, §5.6 Boundary.

### 9.1 Integration Boundary Definition

An **integration boundary** is a logical architectural relationship or contract between two architectural elements or entities. Integration boundaries define where contracts are enforced, translations occur, and invariants are verified.

An integration boundary does **not** automatically imply:
- a network boundary;
- a process boundary;
- a host boundary;
- a container boundary;
- a trust boundary;
- a security boundary;
- a deployment boundary.

If the source architecture does not establish the physical, security, or deployment nature of a boundary, the boundary type is **UNSPECIFIED**. Part 14 does not infer physical boundary semantics from the existence of an integration boundary.

### 9.2 Boundary Types in AI-OS

Where source Parts establish specific boundary types, they are:

| Boundary Type | Source Status | Description |
|---|---|---|
| **Architectural** | DERIVED | Logical separation between AI-OS architectural elements (component-to-component, manager-to-service, event-driven). |
| **Contract** | DERIVED | Separation enforced by interfaces, events, schemas, and documented contracts. |
| **Extension** | EXISTING | Separation enforced by Extension Points (Part 00 §0.5.2). External entities cross only through extension points. |
| **Process/Network/Security/Trust/Deployment** | UNSPECIFIED | Physical boundary types. Source Parts establish architectural boundaries; physical boundary semantics are not explicitly defined for most integration relationships in Parts 0–13. |

### 9.3 Integration Zones

The following zones organize AI-OS integration concerns architecturally. These zones are not physical deployment zones — they are logical integration classifications.

- component-to-component;
- manager-to-service;
- service-to-facade;
- event-driven;
- API/interface;
- external-system;
- model/provider;
- storage/data;
- observability;
- deployment/infrastructure;
- security.

**An integration boundary does not automatically imply a process boundary, network boundary, deployment boundary, or security/trust boundary.** Those details require their own source evidence. Where the implementation mechanism is not established: UNSPECIFIED.

| Zone | Definition | Crossing Mechanism |
|---|---|---|
| **Internal** | Core Components, Core Managers, Engineering Services, Facade Services, Governance Components as defined in Parts 0–13 | N/A — internal composition within the AI-OS platform |
| **Integration Boundary** | Extension points, EventBus publish/subscribe, Facade Service interfaces, Global Singleton Accessors, configuration layer | Documented boundary crossing mechanisms (Part 00 §0.5.2, Part 01 §1.8.4) |

| **Out of Scope** | UI/UX, implementation code structure, persistence schema migration, distributed EventBus, network transport bindings, specific LLM provider SDKs | Part 14 does not specify these; labeled UNSPECIFIED where relevant |

## 10. Integration Contracts

**DERIVED** — Part 14 context.md §6.1–6.2; glossary.md §3.13 Schema, §3.15 Interface, §6.11 Contract.

Integration contracts are the defined obligations and guarantees between architectural elements. They can include:

- interfaces (event schemas, method signatures, accessor contracts);
- event definitions (type, envelope, delivery semantics);
- dependency declarations (registration `dependsOn`, initialization order);
- configuration relationships (four-layer merge, freeze semantics);
- lifecycle relationships (initialization phases, shutdown reversal);
- security requirements (trust model, authorization scope, secret management);
- data relationships (state scopes, context propagation, correlation/causation IDs).

Part 14 distinguishes between:

- **A contract that EXISTS** — established by Parts 0–13 or an accepted ADR, with explicit source citation.
- **A contract that is MISSING or UNSPECIFIED** — not established in source Parts; recorded as GAP or UNSPECIFIED.

Part 14 does not describe missing contracts as implemented. It records the absence and escalates to ARB.

## 11. Integration Dependencies

**DERIVED** — Part 14 context.md §7.1–7.3; glossary.md §5.9 Dependency.

Part 14 records dependencies between architectural elements: which component requires which interface, which service depends on which manager, which event triggers which handler, which configuration parameter affects which subsystem.

A dependency does NOT automatically imply:

- runtime process separation;
- network communication;
- synchronous execution;
- asynchronous execution;
- deployment separation;
- independent scaling.

Those details require their own source evidence. Where that evidence is absent: UNSPECIFIED.

## 12. Cross-Domain Integration

**DERIVED** — Part 14 context.md §4.3 Integration Plane Classification; glossary.md §5.6 Boundary.

Integration often crosses architectural domains. A single integration relationship may have:

- **Component implications** — which components are involved and how they are owned;
- **Interface implications** — what interfaces are consumed or exposed;
- **Event implications** — what events are emitted, subscribed, or transformed;
- **Data implications** — what state is read, written, or propagated;
- **Security implications** — what trust assumptions, authorization checks, or secret management apply;
- **Operational implications** — what observability, health checks, or failure handling apply.

Part 14 exposes these cross-domain relationships without inventing mechanisms for them. Where a cross-domain concern is not addressed by Parts 0–13, it is recorded as GAP or UNSPECIFIED.

### 14.2 Kernel Ownership Boundary

**EXISTING** — Part 00 §0.4 Principle 2; Part 01 §1.6.1; ADR-002 (Active).

The Hermes Kernel owns exactly 13 components (4 Core Components + 9 Core Managers). External components interact with kernel-owned elements ONLY through Global Singleton Accessors, Extension Points, and EventBus.

**Kernel boundary rule:** Kernel-owned interfaces (Core Component interfaces, Core Manager interfaces, Global Singleton Accessor signatures) CANNOT be altered. Extension Points may not be used to redefine non-extension interfaces.

### 14.3 Communication Substrate

**EXISTING** — Part 00 §0.4 Principle 1; ADR-001 (Active); Part 01 §1.7.4.

EventBus is the established event-mediated communication substrate. Asynchronous event emission, delivery, and consumption flow through EventBus. EventBus does NOT mediate synchronous lifecycle, registration, discovery, accessor, or control interactions — those are governed by their respective source contracts.

**ANTI-DRIFT RULE (Retraction Group A):** AI-OS does NOT establish an RPC substrate. Correlation IDs propagate through EventBus ONLY — not through RPC calls.

### 14.4 Initialization Sequence

**EXISTING** — Part 01 §1.10; Part 03 §3.2–3.3; Part 00 §0.4 Principle 10; ADR-010 (Active).

The Hermes Kernel initializes in nine strictly ordered phases. Each phase must complete successfully before the next begins. Failure follows the four-class failure model (TRANSIENT, DEGRADED, CRITICAL, FATAL). Configuration is frozen at the end of Phase 1.

Integration components initialize after Phase 8 (Operational Kernel), once the system reaches RUNNING state.

### 14.5 Lifecycle Management

**EXISTING** — Part 01 §1.11; Part 03 §3.4.9; Part 00 §0.4 Principle 9.

Services transition through seven lifecycle states: REGISTERED → INITIALIZING → RUNNING → DEGRADED → FAILED → SHUTTING_DOWN → SHUTDOWN. The Kernel transitions through five states: CREATED → INITIALIZING → RUNNING → SHUTTING_DOWN → SHUTDOWN. Shutdown reverses initialization order.

### 14.6 Failure Boundaries

**EXISTING** — Part 01 §1.12; Part 00 §0.4 Principle 9; ADR-009 (Active).

Failures propagate via events ONLY. No exception propagation across architectural boundaries. Four failure classifications govern behavior: TRANSIENT (retry), DEGRADED (continue with reduced capability), CRITICAL (isolate), FATAL (shutdown).

**GAP** — No source specification describes retry/DLQ behavior for integration-specific failure scenarios beyond general EventBus retry (Part 02 §2.4).
