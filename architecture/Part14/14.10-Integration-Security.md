## 1. Purpose and Scope

**Status:** EXISTING / DERIVED

### 1.1 Integration Security Defined

**Status:** EXISTING (Part 00 §0.2.2; Part 04 §4.7)

Integration security in AI-OS refers to how security responsibilities and boundaries apply across integration points:

- Component-to-component communication via EventBus
- External system integration (Obsidian, Graphify, LLM providers, MCP servers)
- Extension point integration (custom Skills, custom MCP transports, custom model providers)
- Governance overlay integration (if active)
- Event publication and subscription
- Global Singleton Accessor usage
- External trust boundary crossings

This chapter documents security **requirements** and **boundaries** as established by source Parts 0–13. It does **not** specify implementation mechanisms (TLS, mTLS, OAuth, JWT, IAM, RBAC, ABAC engines, Vault, KMS, etc.) unless those mechanisms are explicitly named by a source Part.

**Part 14 implication:** Integration components MUST respect the security boundaries and requirements documented here. Integration components MUST NOT assume security mechanisms that are not established by source Parts.

### 1.2 Non-Goals

**Status:** EXISTING (Part 14 README §5; context.md §1.3)

This chapter does NOT cover:

- Implementation-level security configurations (cipher suites, certificate formats, key algorithms unless explicitly named by source)
- Business logic security rules
- UI/UX security design
- CI/CD pipeline security
- Incident response runbooks
- Compliance framework mapping implementations
- Threat modeling (attack trees, threat actors, CVEs, exploit chains)

**Part 14 implication:** If a security concern does not trace to a source Part or accepted ADR, it is UNSPECIFIED.

## 2. Integration Security Model

### 2.1 Security Authority

**Status:** EXISTING (Part 13 §8.3; P12-ADR-008; integrations.md §2.6)

| Authority | Scope | Status | Source |
|-----------|-------|--------|--------|
| SecurityManager (M8) | Authorization decision point for all protected operations | EXISTING | Part 1 §1.8.1; Part 4 §4.7; interfaces.md §2.7.3 |
| P12-ADR-008 | Every inter-agent action MUST be authorized via SecurityManager (least-privilege) for multi-agent collaboration domain | EXISTING (Accepted) | adrs.md P12-ADR-008 |

**Part 14 implication:** SecurityManager is the single owner of the security/authorization capability domain. Integration components MUST NOT claim shared ownership of the security capability.

### 2.2 The CONFLICT-03 Boundary

**Status:** CONFLICT (Part 00 §0.2.2 vs Part 13 / dependency-map.md GOV-17)

Part 00 §0.2.2 states:

> "Authentication / Authorization (AuthN/AuthZ): Kernel assumes trusted single-tenant process; multi-tenant auth is v2.0."

Part 13 governance architecture and `dependency-map.md` GOV-17 reference SecurityManager authorization and governance-level authority as if active in v1.0.

**Point of disagreement:** Whether security (authentication and authorization) is a mandatory v1.0 kernel feature or deferred to v2.0 with governance overlay as optional.

**Part 14 position:** MUST NOT silently resolve. Integration security requirements are UNSPECIFIED pending ARB resolution. Two paths documented:

- **Trusted-process path:** Integration components operate in the kernel's trusted single-tenant process (Part 00 §0.2.2). Security enforced at process boundary.
- **Governance overlay path:** Integration components pass SecurityManager authorization for every protected operation (P12-ADR-008, GOV-17) if the governance overlay is active.

**Escalation:** ARB decision required. Part 14 MUST document both paths until resolved (CONFLICT-03).

## 3. Security Boundaries

### 3.1 Architectural Integration Boundary vs Security Boundary

**Status:** EXISTING / DERIVED

An **architectural integration boundary** is the perimeter where external entities cross into the AI-OS platform (Extension Points, Facade Service interfaces, EventBus publication/subscription, Global Singleton Accessors, configuration layer).

A **security boundary** is a trust, process, host, or cryptographic boundary where security controls are applied.

Not every logical boundary is automatically:

- a network trust boundary
- a process boundary
- a host boundary
- a cryptographic boundary

**Part 14 implication:** Integration components MUST NOT assume that crossing an architectural integration boundary implies crossing a security boundary. Security boundaries are source-defined only.

### 3.2 Defined Trust Boundaries

**Status:** EXISTING (components.md §4.8, §5.3, §7.2; glossary.md §5.3)

| Boundary Type | Components | Trust model | Status | Source |
|--------------|------------|-------------|--------|--------|
| **Kernel** | HermesKernel + 4 Core Components + 9 Core Managers | Trusted single-tenant process | EXISTING | Part 00 §0.2.2; Part 1 §1.8.1 |
| **Security** | SecurityManager (M8) | Authorization enforcement point | EXISTING | Part 4 §4.7; integrations.md §2.6 (INT-006) |
| **Governance** | G-00..G-15 | Logical/governance-layer; NOT a deployment boundary | EXISTING (logical concept) | Part 13 components.md §7.2 |
| **External** | Obsidian, Graphify, LLM Providers, MCP servers, Identity Providers | Credentialed via SecretManager; trust varies per provider | EXISTING | Part 6, Part 7, Part 9, Part 10 ADR-005 |

**Part 14 implication:** Integration components cross these trust boundaries through documented mechanisms only (extension points, accessor functions, EventBus publication/subscription, Facade Service events, SecretManager for external credentials). Integration components MUST NOT cross trust boundaries through undocumented channels.

**CONFLICT-03 qualification [EXISTING]:** The "Security" boundary's authority is subject to CONFLICT-03. If the governance overlay is not active, kernel-internal authorization for governance operations follows the trusted-process model (Part 00 §0.2.2). If the governance overlay is active, GOV-17 requires SecurityManager authorization for all governance operations.

### 3.3 Process-Level Trust

**Status:** EXISTING (Part 00 §0.2.2)

v1.0 assumes a single trusted process boundary.

**Source:** Part 00 §0.2.2 — verbatim: "Kernel assumes trusted single-tenant process; multi-tenant auth is v2.0."

**Part 14 implication:** Integration components executing within the AI-OS process inherit the kernel's trusted-process assumption. Integration components executing as external adapters (bridging to Obsidian, Graphify, LLM providers) cross the external trust boundary and MUST obtain credentials via SecretManager. The runtime isolation mechanism for external adapters is UNSPECIFIED.

### 3.4 Kernel Accessor Trust Boundary

**Status:** EXISTING (Part 1 §1.8.4 ADR-004; components.md §4.8; integrations.md §2.3)

Integration components access the kernel via the 13 global singleton accessors only.

| Accessor | Purpose | Trust boundary crossed |
|----------|---------|----------------------|
| `kernel.security` | SecurityManager access | Security boundary |
| `kernel.eventBus` | EventBus access | Integration boundary |
| `kernel.configuration` | ConfigurationManager access | Configuration boundary |
| others | Manager access | Per-manager boundary |

**Part 14 implication:** Integration components MUST access SecurityManager exclusively via `kernel.security` accessor. Integration components MUST NOT instantiate or directly reference SecurityManager internals. The accessor signature is a non-extension point per ADR-013.

## 4. Identity and Authentication

### 4.1 Identity Responsibilities

**Status:** EXISTING (Part 4 §4B; components.md §11.8)

IdentityProvider is classified as an External system, not an internal Core Component.

**Source:** Part 4 §4B; components.md §11.8

**Part 14 implication:** Integration components MUST NOT invent identity provider contracts, authentication protocols, token formats, or credential exchange mechanisms. The Identity Provider integration **interface contract** is GAP (GAP-05) until Parts 0–13 define it.

### 4.2 Authentication Requirements

**Status:** EXISTING / CONFLICT (Part 00 §0.2.2 vs Part 4 §4.7; Part 6 STEP8)

Distinguish:

- **Authentication requirement** — what must be authenticated
- **Authentication mechanism** — how authentication is performed (TLS, JWT, API keys, mTLS, etc.)

**Source:** Part 00 §0.2.2 (kernel assumes trusted single-tenant process; AuthN/AuthZ deferred to v2.0); Part 4 §4.7 (SecurityManager authorization responsibility)

**Part 14 implication:** In v1.0, the trusted-process model means kernel-internal components are not individually authenticated at the process boundary. External boundary crossings (Obsidian, Graphify, LLM providers) require credentials obtained via SecretManager, but the authentication mechanism at each external boundary is UNSPECIFIED.

### 4.3 Authentication Scope Boundary (CONFLICT-03)

**Status:** CONFLICT (Part 00 §0.2.2 vs Part 13 / GOV-17)

Part 00 §0.2.2 defers AuthN/AuthZ to v2.0. Part 13 governance architecture and GOV-17 reference authentication and authorization as active v1.0 governance-layer requirements.

**Point of disagreement:** Whether authentication is required for kernel-internal integration components in v1.0.

**Part 14 position:** Integration components MUST NOT assume internal authentication is required in v1.0 per Part 00 §0.2.2. If the governance overlay is active, P13-ADR-005 (Draft) and P13-ADR-006 (Draft) propose governance event authentication and signing requirements, but these are PROPOSED pending ARB resolution of CONFLICT-03.

**Part 14 implication:** Integration components operating as inter-agent actors in the Part 12 multi-agent collaboration domain MUST have successful prior authentication before SecurityManager authorization (Part 4 §4.7.4; P12-ADR-008 for Part 12 domain scope only). Whether this extends to all kernel-internal components is subject to CONFLICT-03.

## 5. Authorization and Access Control

### 5.1 Authorization Requirement vs Implementation

**Status:** EXISTING (Part 4 §4.7; interfaces.md §2.7.3)

Distinguish:

- **Authorization requirement** — what must be authorized
- **Authorization implementation** — how authorization is performed (RBAC, ABAC, policy engines, IAM, etc.)

An ACL requirement does NOT automatically establish its implementation.

**Source:** interfaces.md §2.7.3 (SecurityManager as Attribute-Based Access Control decision point); Part 4 §4.7 (authorization responsibility)

**Part 14 implication:** Integration components MUST route authorization through SecurityManager via `INT-SEC-AUTH-001` for protected operations. Integration components MUST NOT implement their own authorization logic.

### 5.2 Authorization Interface (INT-SEC-AUTH-001)

**Status:** EXISTING (Part 4 §4.7.4; interfaces.md §2.7.3)

`SecurityManager.authorize(principal, action, resource, context)` → `ALLOW` / `DENY` / `CHALLENGE`

| Property | Value |
|---------|-------|
| **Interface ID** | INT-SEC-AUTH-001 |
| **Status** | EXISTING |
| **Provider** | SecurityManager (M8) |
| **Consumer(s)** | Core Managers, Engineering Services, Capability Facade Services, WorkflowManager |
| **Purpose** | Attribute-Based Access Control decision point for all protected operations |
| **Direction** | Consumer → SecurityManager |
| **Interaction style** | Synchronous authorization decision |
| **Protocol/mechanism** | Direct manager method via singleton accessor (`kernel.security`) |
| **Request contract** | Principal, action, resource, context |
| **Response contract** | Decision: `ALLOW`, `DENY`, or `CHALLENGE` |
| **Error contract** | NOT YET DEFINED — no error types or failure modes specified |
| **Authentication/authorization requirements** | All authorization decisions require successful prior authentication (CONFLICT-03: subject to whether authentication is required in v1.0 per Part 00 §0.2.2 vs Part 13 governance overlay) |
| **Timeout expectations** | NOT YET DEFINED |
| **Retry expectations** | NOT YET DEFINED |
| **Idempotency requirements** | NOT YET DEFINED |

| **Source authority** | Part 4 §4.7.4; interfaces.md §2.7.3 |

**Source:** Part 4 §4.7.4; interfaces.md §2.7.3

**Part 14 implication:** Integration components consuming Core Manager capabilities, Facade Services, or governance functions MUST consult SecurityManager via INT-SEC-AUTH-001 before performing protected operations within the applicable scope. The integration catalog entry INT-006 documents this dependency (integrations.md §2.6).

### 5.3 Authorization Consumption

**Status:** EXISTING (integrations.md §2.6 INT-006; dependency-map.md §1.4; dependency-map.md GOV-17)

All integration attributes that are subject to authorization converge on INT-SEC-AUTH-001 (CONFLICT-03: convergence on SecurityManager authorization is conditional on whether the governance overlay is active in v1.0; under the trusted-process model per Part 00 §0.2.2, kernel-internal authorization follows the process boundary).

| Component | Consumes INT-SEC-AUTH-001 | Access via |
|-----------|--------------------------|------------|
| Core Managers | Yes | `kernel.security` |
| Engineering Services | Yes | `kernel.security` |
| Capability Facade Services | Yes | `kernel.security` |
| WorkflowManager | Yes | `kernel.security` |
| Governance Components (G-00..G-15) | Yes (GOV-17) | `kernel.security` (if overlay active) |

**CONFLICT-03 qualification [EXISTING]:** Governance components (G-00..G-15) MUST consult SecurityManager if the governance overlay is active (GOV-17). If the governance overlay is not active (trusted-process model per Part 00 §0.2.2), the kernel's trusted-process assumption applies. Both paths are valid pending CONFLICT-03 resolution.

**Part 14 implication:** Integration components within the Part 12 multi-agent collaboration domain MUST pass SecurityManager authorization for inter-agent actions. Integration components MUST NOT bypass SecurityManager within the applicable scope. This requirement is subject to CONFLICT-03 for v1.0 kernel scope.

### 5.4 Authorization Enforcement Points

**Status:** EXISTING (Part 6 STEP8 ADR-6.8.2/6.8.3; integrations.md §2.6 INT-006)

Per Part 6 STEP8, authorization ownership belongs exclusively to execution facades; identity ownership belongs exclusively to manager space.

**Part 14 implication:** Integration components acting as facade services MUST route authorization through SecurityManager. Integration components MUST NOT implement their own authorization logic for protected operations.

### 6.3 PII and Secret Redaction in Events

**Status:** EXISTING / CONFLICT (P12-ADR-008 Accepted; Part 00 §0.2.2)

Signed events; PII and secrets redacted in payloads.

**Source:** P12-ADR-008 (Accepted) — verbatim: "Every inter-agent action MUST be authorized via SecurityManager. Agents operate on least-privilege. Signed events; PII and secrets redacted in payloads."

**Scope qualification [EXISTING]:** P12-ADR-008 applies to the **Part 12 multi-agent collaboration domain** specifically. It does NOT extend to all integration components or to the kernel's trusted-process model. Part 00 §0.2.2 remains authoritative for the v1.0 kernel posture.

**Part 14 implication:** Integration components emitting Part 12 domain events within the Part 12 multi-agent collaboration domain redact PII and secrets from payload content, per P12-ADR-008 verbatim ("PII and secrets redacted in payloads"). The redaction is recorded via `metadata.redacted_fields` JSON pointers in the Part 12 envelope. Integration components operating outside the Part 12 collaboration domain are NOT bound by P12-ADR-008's redaction requirement — their event security posture is governed by the trusted-process model (Part 00 §0.2.2). This is subject to CONFLICT-03.

### 6.4 Part 2 Base Event Security

**Status:** GAP (Part 2 §2.2.1; events.md §3.11, §9.6)

Part 2 §2.2.1 base `Event` contract has no `security.*` block.

| Finding ID | Description | Status |
|--------|-------------|--------|
| **GAP-SEC** | Part 2 `Event` has no signing or ACL field. Signing exists only in the Part 12 envelope. Part 2's security posture for events is unspecified at the transport layer. | GAP |

**Part 14 implication:** Integration components emitting Part 2 domain events have NO defined signing or ACL mechanism at the event level. Integration components MUST NOT invent signing or ACL mechanisms for Part 2 events.

### 6.5 Bus-Level Authentication/Authorization

**Status:** GAP (interfaces.md §2.6 INT-EVT-BUS-001; dependency-map.md §12.3)

Bus-level authentication/authorization is not defined in the EventBus interface.

| ID | Description | Status |
|----|-------------|--------|
| **UNRES-05** | Bus-level authentication/authorization — EventBus-level authn/authz NOT YET DEFINED | GAP |

**Part 14 implication:** Integration components MUST NOT assume that the EventBus performs authentication or authorization at the transport layer. The EventBus interface (`INT-EVT-BUS-001`) does not define per-subscriber authentication or per-message authorization. This is a GAP (UNRESOLVED finding ID: UNRES-05) and must not be silently filled.

### 6.6 Secret-Tier Event Handling

**Status:** EXISTING (events.md §3.11)

`secret`-tier events are not broadcast to unauthorized subscribers (verbatim from events.md §3.11).

**Source:** events.md §3.11 — verbatim: "`secret`-tier not broadcast to unauthorized subscribers"

**Part 14 implication:** Integration components emitting or consuming `secret`-classification events MUST respect subscriber authorization. The enforcement mechanism for secret-tier event filtering is **UNSPECIFIED** — events.md §3.11 states the property but does not define how subscriber authorization is checked.

**Do NOT invent:** Encryption-at-rest claims, encryption-in-transit claims, encryption algorithms, KMS mechanisms.

### 8.3 Integrity

**Status:** EXISTING / UNSPECIFIED (Part 12 events.md §4, §20; schemas.md §1.1)

Where integrity requirements are established:

- Events MAY carry Ed25519 signatures over canonicalized envelope payload (Part 12 envelope)
- `security.previous_signature` retained for audit continuity

**Source:** Part 12 events.md §20 — verbatim: `security.signature` is "Ed25519 signature over canonicalized envelope payload"

Integration components MUST NOT invent integrity mechanisms (hashes, checksums, Merkle trees, blockchain, MACs) for domains where they are not established.

**Do NOT invent:** Signing algorithms not named by source Parts. If signing is explicitly required, preserve the signing requirement; do not invent the signing algorithm beyond what source Parts name (Ed25519 per Part 12 events.md §20).

### 8.4 Authenticity

**Status:** EXISTING / UNSPECIFIED (Part 12 events.md §20)

Distinguish:

- **Authenticity requirement** — what must be proven authentic
- **Authentication implementation** — how authenticity is established

**Source:** Part 12 events.md §20 (Ed25519 signature field exists)

**Part 14 implication:** Event signature authenticity is established via Ed25519 signatures in the Part 12 envelope (source-defined). Integration components MUST NOT equate signature with PKI as an architectural requirement. Integration components MUST NOT equate authentication with TLS.

## 9. Secrets and Credentials

### 9.1 Secret Flow

**Status:** DERIVED (Part 00 §0.2.2; adrs.md ADR-010 Active)

Secrets are delivered to the runtime via environment variables within the four-layer configuration merge (defaults → app.yaml → env.yaml → env vars).

**Source:** Part 00 §0.2.2 (AuthN/AuthZ defers to v2.0; secrets via env vars); adrs.md ADR-010 (four-layer merge; Active)

**Inference path [DERIVED]:** Part 00 §0.2.2 states AuthN/AuthZ is deferred to v2.0 and that the kernel assumes a trusted single-tenant process. ADR-010 (Active) defines the four-layer configuration merge. Environment variables are one layer of that merge. The statement that "secrets flow through the configuration merge" is DERIVED by combining Part 00 §0.2.2's env-var secret delivery with ADR-010's four-layer merge — neither source explicitly states secrets "flow through" the configuration merge as a security architecture requirement.

| Layer | Secret handling |
|-------|----------------|
| defaults | No secrets (non-sensitive defaults only) |
| app.yaml | Non-sensitive defaults committed; secrets excluded |
| env.yaml | Environment-specific non-secret config |
| env vars | Secrets injected at runtime via environment variables (Part 00 §0.2.2) |

**Part 14 implication [DERIVED]:** Integration components MAY obtain runtime secrets through the ConfigurationManager four-layer merge, provided the configuration merge is active. Integration components MUST NOT read environment variables or local files directly as a bypass of the configuration model. This is a DERIVED integration constraint.

**Do NOT invent:** Vault, KMS, cloud secret managers, Kubernetes Secrets, password vaults, automatic rotation.
