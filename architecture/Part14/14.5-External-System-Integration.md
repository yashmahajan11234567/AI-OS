## 0. External System Integration Model

**Status:** DERIVED — context.md §2.2 (Integration Boundary), §2.3 (Internal/Boundary/External/Out-of-Scope Zones); components.md §7 (External System Inventory)

An integration is "external" when it crosses from the AI-OS **Architectural Domain** into a system that is not owned, controlled, or governed by the Hermes Kernel.

### 0.1 AI-OS Architectural Domain vs. External System

**Status:** DERIVED — context.md §2.3

The **AI-OS Architectural Domain** consists of:

- Core Components (4) — owned by HermesKernel (Part 01 §1.7.1)
- Core Managers (9) — owned by HermesKernel (Part 01 §1.8.1)
- Engineering Services (8) — owned by the kernel Service layer (Part 00 §0.3.2)
- Capability Facade Services (4) — owned by the kernel Service layer (Part 00 §0.3.2)
- Governance Components (G-00..G-15) — owned by the governance layer (Part 13 §13.2)

An **External System** is any system that:

- Is not owned by HermesKernel
- Does not participate in the kernel EventBus
- Does not share the kernel's lifecycle
- Communicates through the integration boundary (Facade Services, Core Manager bridges, or externally-defined interfaces)
- Has its own availability, lifecycle, schema, and security policy

### 0.2 What External Integration Is NOT

**Status:** EXISTING — context.md §2.3; Part 00 §0.4 Principle 1

An external integration boundary is not automatically:

- a process boundary (multiple processes may exist within the AI-OS domain)
- a network boundary (network topology is UNSPECIFIED in v1.0)
- a host boundary (deployment topology is UNSPECIFIED)
- a container boundary (containerization is UNSPECIFIED)
- a security/trust boundary (trust semantics are defined separately per CONFLICT-03)

The integration boundary is an **architectural** boundary, not an infrastructure boundary. Infrastructure boundaries (network, host, container) may coincide with the integration boundary in implementation but are not the defining characteristic.

> **Layer distinction:** The architectural domain boundary is defined by ownership and governance, not by deployment topology. A system deployed on the same host as the kernel may still be external if it is not owned by HermesKernel and communicates through the integration boundary.

### 1.2 Engineering Service External Access Pattern

**Status:** DERIVED — inference from Part 6 STEP1/STEP3/STEP3_MCP/STEP5 (INV-6.3.2, INV-6.4.3 confirmed in MEMORY.md §1.2; INV-6.3.3 and INV-6.5.3 not verified in allowed sources) + Part 0 §0.4 Principle 12

Engineering Service external capability access follows a common pattern:

1. **Facade translation:** Engineering Services emit EventBus events; Capability Facade Services translate events to Core Manager method calls.
2. **Security mediation:** SecurityManager (M8) evaluates authorization for each external capability invocation from Engineering Services (INT-SEC-AUTH-001).
3. **Failure event emission:** Facade Services emit failure events (`*_FAILED`) per ADR-009.
4. **No direct Engineering Service access:** Engineering Services do NOT invoke external systems directly (INV-6.3.2, INV-6.4.3 — confirmed in MEMORY.md §1.2). INV-6.3.3 and INV-6.5.3 cited in this section are not verified in allowed sources.

> **INTEGRATION CONSTRAINT [DERIVED]:** External systems are NEVER reached directly from Engineering Services (INV-6.3.2, INV-6.4.3). All Engineering Service external capability access transits through Capability Facade Services (SkillService, CouncilService, MCPService, MemoryService) and is gated by SecurityManager.

**Layer distinction [DERIVED]:** The pattern above applies to Engineering Service external capability calls. Core Managers (LLMManager, ToolManager, MemoryManager, SecurityManager) bridge to external systems directly without Facade Service mediation (components.md §7; dependency-map.md §5). The Engineering Service→Facade pattern does not generalize to Core Manager→External System access.

### 2.2 Event Boundary: Internal vs External

**Status:** EXISTING — Part 0 §0.4 Principle 12; ADR-001

- **Internal boundary:** EventBus mediates all kernel-internal communication (Core Components, Core Managers, Services, Facades).
- **External boundary:** Facade Services translate EventBus events to externally-defined calls; external systems do NOT participate in the kernel EventBus.
- **No EventBus extension:** External systems do not receive EventBus events directly; all external communication is via externally-defined calls mediated by Facades.

> **INTEGRATION CONSTRAINT:** The EventBus is a kernel-internal boundary. External systems communicate via externally-defined interfaces translated by Facade Services.

### 2.3 API/Interface Boundary

**Status:** EXISTING — interfaces.md §2.4; Part 6 STEP3

The AI-OS kernel exposes NO direct external APIs. All Engineering Service external interface access is mediated by:

- **Capability Facade Services:** External capability calls from Engineering Services must transit through Facades (INV-6.3.2).
- **SecurityManager:** External capability calls from Engineering Services require SecurityManager authorization (INT-SEC-AUTH-001).

> **NO DIRECT EXTERNAL API:** Engineering Services do NOT call external systems directly. No kernel-level external API surface is exposed to Engineering Services.

## 12. External System Failure Handling

### 12.1 Failure Propagation

**Status:** EXISTING — ADR-009; Part 0 §0.4 Principle 12

External capability call failures propagate through the kernel via EventBus:

- **Facade emits failure events:** When external capability calls (from Engineering Services) fail, Facade Services emit `*_FAILED` events.
- **EventBus mediation:** Failure events flow through EventBus to interested consumers (WorkflowManager, Governance, ObservabilityManager).
- **No direct error propagation to Engineering Services:** Engineering Services do NOT receive direct error returns from external systems; all failure information is event-mediated.

> **Scope limitation:** Failure propagation via EventBus is established for Facade-mediated Engineering Service capability calls only. Core Manager→External System direct bridge call failures (LLMManager, ToolManager, MemoryManager, SecurityManager) are NOT established as propagating via EventBus in Parts 0–13.
