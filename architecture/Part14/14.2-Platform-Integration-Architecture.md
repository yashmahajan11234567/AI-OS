# Part 14.2: Platform Integration Architecture

## Integration Purpose

**Status:** DERIVED

This document describes how the AI-OS platform elements — Hermes Kernel, Core Components, Core Managers, Engineering Services, and integration boundaries — fit together according to the architecture established by Parts 0–13. Capability Facade Services are Service-layer elements (context.md §3.1), not peers to Core Components or Core Managers.

It does NOT redesign, extend, or redefine Parts 0–13. It documents the relationships established by source Parts and records where those relationships are unspecified, conflicting, or represented only as gaps.

Part 14 implication: Integration components attach to the AI-OS platform at the **Extensions/Plugins layer** (context.md §2.1, Part 00 §0.5.2). They communicate via EventBus and consume kernel services through documented extension points and Global Singleton Accessors only.

---

## Integration Scope

Part 14.2 covers:

- The architectural position of the Hermes Kernel as orchestrator
- Core Component integration roles (preserving the Part 01 §1.7.1 enumeration per context.md §3.1)
- Core Manager ownership by the Kernel (preserving the Part 01 §1.8.1 enumeration per context.md §3.1)
- Engineering Services as event-driven actors
- Capability Facade Services as thin bridges
- Event-first communication as the documented communication substrate
- Configuration as a four-layer merge that freezes before Service initialization
- Lifecycle phases and shutdown reversal
- Global Singleton Accessors as kernel-access integration points
- Boundary types: architectural, interface, event, service, configuration, lifecycle, deployment, security — all distinct and not interchangeable
- Dependency vs ownership vs implementation relationships
- Where integration contracts are established, unspecified, or represent known conflicts/gaps

## 1. Hermes Kernel Integration

### 1.1 Kernel Role (Orchestrator)

**Status:** EXISTING

Per context.md §1.1 (citing Part 01 §1.5.2), the Hermes Kernel is responsible for configuration authority, lifecycle orchestration, and failure handling. The Kernel owns Core Components and Core Managers as its internal composition layer.

Part 14 implication: The Kernel is an **orchestration boundary**, not a deployment unit. Integration documents describe what the Kernel orchestrates, not how it is deployed.

> **Do not invent:** Kernel subprocesses, clusters, process boundaries, network boundaries, deployment topology, internal kernel modules, or kernel APIs not established by source Parts.

### 1.2 Kernel Role vs Kernel Implementation

**Status:** DERIVED

The **KERNEL ROLE** — as documented by context.md §1.1 (citing Part 01 §1.5.2) — is to provide initialization sequencing, component ownership, and lifecycle management for Core Components and Core Managers. The Kernel is the orchestrator of the platform foundation.

The **KERNEL IMPLEMENTATION** — how the Kernel is realized in code, what runtime it uses, what process it runs in — is NOT established by source Parts and MUST NOT be inferred.

Part 14 implication: 14.2 describes the Kernel's orchestration role only. Transport, process model, and deployment topology remain UNSPECIFIED.

### 1.3 Kernel Boundary

**Status:** EXISTING

Per context.md §1.1 (citing Part 01 §1.5.3 Non-Responsibilities), the Kernel does not execute step logic, does not invoke capabilities directly, and does not expose internal component references to Services. Access to Core Managers from Services is mediated through Global Singleton Accessors (context.md §3.1 cites Part 01 §1.8.4).

Part 14 implication (context.md §3.1): Integration components MUST NOT access Kernel internals directly. Capability access flows through Facade Services (context.md §3.1 cites Part 00 §0.3.2, Part 06) or Global Singleton Accessors (context.md §3.1 cites Part 01 §1.8.4). The term "CapabilityManager" is NOT traceable from the inspected control files and MUST NOT be invented here.

## 7. Event-First Integration

### 7.1 EventBus as Communication Substrate

**Status:** EXISTING

Per context.md §5.1 (citing Part 00 §0.4 Principle 1):

> All inter-component communication MUST occur via the EventBus. There are no direct service-to-service calls, no synchronous RPC, no shared mutable state outside StateManager.

Post-initialization (Phase 3+), all inter-component communication is event-mediated (context.md §3.1 cites Part 01 §1.15.2 INV-RT-002).

### 7.2 Initialization vs. Runtime Communication

**Status:** EXISTING / DERIVED

During initialization (Phases 0–3), Core Components communicate via constructor injection and explicit dependency definitions (context.md §3.1 cites Part 01 §1.7.4 CC-IR-001). Services in Phase 9+ communicate via EventBus subscriptions.

Part 14 implication: The event-first pattern applies to steady-state (post-initialization) communication. Initialization-time constructor injection is a separate, explicitly-defined pattern for Core Components only.

### 7.3 Event-Driven vs. Direct Interface Access

**Status:** EXISTING

The architectural distinction is:

- **EVENT-DRIVEN COMMUNICATION**: Post-initialization inter-component communication via EventBus. This is the default for Services and integration components.
- **DIRECT INTERFACE ACCESS**: Explicit accessor-based access where source Parts establish it — specifically Global Singleton Accessors for Core Managers (context.md §3.1 cites Part 01 §1.8.4), constructor injection for Core Components (Phase 0–3), and registration via ServiceRegistry.

Part 14 implication: The two patterns coexist intentionally. Not every interaction is asynchronous. Not every interface call is converted to an event. The distinction is source-defined and MUST be preserved.

> **Do not invent** an event broker, Kafka, RabbitMQ, NATS, Redis Streams, cloud messaging, or external queues. The EventBus is the documented communication mechanism; its transport implementation is not established.

> **Do not assume** that every platform interaction is asynchronous. Initialization-time dependencies and singleton accessor calls are synchronous by design per source Parts.

## 10. Lifecycle Integration

### 10.1 Phased Initialization

**Status:** EXISTING

Per context.md §7.2 (citing Part 01 §1.10.2), kernel initialization follows deterministic phases:

```
Phase 0: EventBus Bootstrap (first Core Component)
Phase 1: ServiceRegistry Bootstrap
Phase 2: Configuration Freeze (ConfigurationManager)
Phase 3: Lifecycle Bootstrap (LifecycleManager)
Phase 4-8: Core Managers (parallel within phases)
Phase 9+: Services (topological order per ServiceRegistry)
```

### 10.2 Shutdown Reversal

**Status:** EXISTING

Per context.md §7.2 (citing Part 01 §1.11.2), shutdown reverses initialization order:

- Services shutdown in reverse dependency order
- Core Managers shutdown reverse phase order (Phase 8 → 4)
- Core Components shutdown reverse initialization order (Phase 3 → 0)

### 10.3 Lifecycle Boundary

**Status:** EXISTING / UNSPECIFIED

- The lifecycle phase model is EXISTING (context.md §7.2: Phase 0–3 Core Components, Phase 4–8 Core Managers, Phase 9+ Services)
- Specific lifecycle event names are UNSPECIFIED — the inspected control files do NOT establish a canonical lifecycle event-name taxonomy
- Transport mechanisms (systemd, supervisor, Kubernetes lifecycle, restart policies, signal handlers, process managers) are NOT established

Per context.md §7.2: Integration components initialize after Phase 9+ (Service initialization). They MUST NOT publish events before EventBus is operational (Phase 0). Lifecycle management is coordinated by LifecycleManager (context.md §10.2), not self-managed.

> **Do not invent:** systemd, supervisor, Kubernetes lifecycle, restart policies, signal handlers, or process managers. If exact lifecycle ordering is not established: UNSPECIFIED.

## 13. Dependency Discipline

### 13.1 Distinguishing Dependency from Ownership

**Status:** EXISTING / DERIVED

- **DEPENDENCY**: A relationship where one component requires another component's interface to fulfill its obligations (context.md §3.1 cites Part 03 SR-REG-003). A documented dependency does NOT automatically mean a direct function call, network call, runtime process, synchronous call, asynchronous event, or deployment dependency.

- **OWNERSHIP**: The Kernel exclusively owns Core Components and Core Managers (context.md §3.1 cites Part 01 §1.8.3 INV-OWN-001). Integration components do NOT own kernel infrastructure.

- **IMPLEMENTATION**: How a dependency is realized at runtime (process, network, in-memory) is not established by source Parts and is UNSPECIFIED for most integration relationships.

Part 14 implication: When 14.2 describes dependencies, it MUST distinguish dependency, ownership, and implementation. A documented dependency relationship does NOT automatically establish a direct method call unless source Parts explicitly define it as such.

## 14. Failure Integration

### 14.1 Event-First Failure Communication

**Status:** EXISTING

Per context.md §5.1 (citing Part 00 §0.4 Principle 1, Principle 9):

> Failures MUST be communicated via Events, never via exceptions across architectural boundaries.

Per context.md §10.1 (citing Part 00 §0.4 Principle 9; Part 01 §1.12), failure classification is:

- TRANSIENT → retry with exponential backoff (max 3)
- DEGRADED → ComponentDegraded event; continue
- CRITICAL → ComponentFailed event; isolate; restart (max 2)
- FATAL → emergency shutdown

Per context.md §10.2 (citing Part 01 §1.12.1), retry semantics are source-established (max 3 transient, max 2 critical).

### 14.2 Failure Event Propagation

**Status:** DERIVED

Integration component failures propagate via EventBus events, carrying correlation/causation IDs (context.md §3.1 cites Part 00 §0.4 Principles 8 and 9).

Part 14 implication: Integration failures MUST NOT propagate as exceptions across architectural boundaries. Failure events are data, not control signals (context.md §4.1).

> **Do not invent** automatic infrastructure recovery. Event-based failure communication does NOT mean automatic restart, automatic retry, automatic failover, or automatic rollback. Retry budgets and recovery actions are governed by source Parts where established; otherwise UNSPECIFIED.

### 14.3 Retry and Backoff

**Status:** EXISTING / UNSPECIFIED

Per context.md §10.2 (citing Part 01 §1.12.1), TRANSIENT failures retry with exponential backoff (max 3). CRITICAL failures restart (max 2).

**UNSPECIFIED**: Whether integration components share the kernel's RetryBudget or have independent retry policy. Whether dead-letter queues exist for integration events. Whether reconciliation jobs trigger on persistent failures.

Part 14 implication: Do not invent retry/DLQ/recovery semantics. Where not established by source Parts: UNSPECIFIED.

## 18. Integration Architecture Summary

### 18.1 How Platform Elements Fit Together

The AI-OS platform architecture, as documented by Parts 0–13, composes as follows:

1. **Hermes Kernel** (context.md §3.1, citing Part 01 §1.5.2) owns and orchestrates Core Components and Core Managers. It is the platform foundation and orchestration boundary.

2. **Core Components** (context.md §3.1, citing Part 01 §1.7.1: EventBus, ServiceRegistry, ConfigurationManager, LifecycleManager) provide the initialization substrate, configuration authority, registration, and lifecycle sequencing.

3. **Core Managers** (context.md §3.1: 9 managers per Part 01 §1.8.1) provide the core architectural capabilities. They are instantiated exclusively by the Kernel (context.md §3.1 cites Part 01 §1.8.3 INV-OWN-001) and accessed via Global Singleton Accessors (context.md §3.1 cites Part 01 §1.8.4).

4. **Engineering Services** (context.md §3.1, citing Part 00 §0.3.2) are event-driven actors. They participate in the SDLC chain via EventBus events (context.md §5.2).

5. **Capability Facade Services** (context.md §3.1, citing Part 00 §0.3.2) are Service-layer elements. Their specific bridge-to-manager mappings are UNSPECIFIED from the inspected control files; see §6.

6. **Extensions/Plugins** attach at the Extensions/Plugins layer (context.md §2.1) through documented extension points (Part 00 §0.5.2 per context.md §1.1). Integration components are consumers of the EventBus and kernel services.

7. **Event-First Communication** (context.md §5.1, citing Part 00 §0.4 Principle 1) is the documented communication substrate for all inter-component communication post-initialization. Initialization-time constructor injection and singleton accessors remain valid where source Parts establish them.
