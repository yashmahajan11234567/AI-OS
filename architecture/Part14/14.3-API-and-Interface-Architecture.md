## Interface Architecture Model

**Status:** DERIVED from Part 00 §0.4 Principles 1/2/3/4/7/11, Part 00 §0.5.2, glossary §3.15 / §6.11, context.md §0.5, and MEMORY.md §10 (Safety Rule 6: never infer implementation from terminology alone).

AI-OS integration is mediated by **architectural contracts**, not by network plumbing. The following six concepts are distinct; Part 14 does not silently collapse them:

| Concept | Meaning in AI-OS | Status |
|---------|-----------------|--------|
| **INTERFACE** | A named, versioned surface a component exposes for consumption by others — expressed through events (EventBus), schemas, invariants, and SLIs (glossary §3.15). It is a *contract surface*, not an implementation. | EXISTING (glossary §3.15) |
| **API** | One expression of an interface — a defined way to read from or call into it. In AI-OS an "API" is an **architectural contract**; it does NOT automatically mean HTTP, REST, gRPC, RPC, WebSocket, or any network protocol. | DERIVED |
| **CONTRACT** | A machine-enforceable specification of the obligations and guarantees between a provider and its consumers (glossary §6.11); references schemas (Part 12 schemas.md) and carries a version (Part 00 §0.4 Principle 11). | EXISTING (glossary §6.11) |
| **IMPLEMENTATION** | The code or component that fulfills a contract. A service may expose an interface without being a remote microservice; a contract may define behavior without defining implementation. | DERIVED |
| **TRANSPORT** | The mechanism by which an interaction moves. EventBus is the established event-mediated substrate (Part 00 §0.4 Principle 1; Part 1 §1.7.4 CC-IR-001). Where a transport is not established by source, it is **UNSPECIFIED**. | EXISTING for EventBus; UNSPECIFIED elsewhere |
| **DEPLOYMENT BOUNDARY** | Whether components share a process or are distributed. v1.0 is single-process, in-memory only (Part 00 §0.2.2). AI-OS does NOT establish a network deployment boundary for its interfaces by default. | EXISTING (Part 00 §0.2.2) |

**Core rule (preserved throughout this document):** An interface existing architecturally does NOT automatically mean HTTP, REST, gRPC, RPC, WebSocket, TCP, Unix socket, message broker, remote API, or network service. A defined interface can exist without a defined network transport. A contract can define behavior without defining implementation. An event interface can exist without an external message broker. AI-OS establishes **EventBus as the sole communication substrate** (Part 00 §0.4 Principle 1); no RPC mechanism exists (glossary §4.7 RETRACTED; MEMORY.md §6 Group A). Where the architecture does not establish a transport or deployment behavior, this document records it as **UNSPECIFIED** rather than inventing one.

This model governs every interface cataloged below. Each entry is tagged with a status from the Part 14 taxonomy and, where applicable, a GAP or CONFLICT identifier.

## Provider / Consumer Model

**Status:** DERIVED from glossary §3.15 / §3.16 / §3.17 / §3.18, context.md §3.2–§3.3, and MEMORY.md §10 (Safety Rule 6: never infer implementation from terminology alone).

An interface is an architectural contract positioned between a **provider** (the component that implements the contract and fulfills its obligations) and one or more **consumers/clients** (the components that depend on or consume the contract). The relationship is represented as:

```text
Provider
   │  implements
   ▼
Interface / Contract
   │  consumed through
   ▼
Consumer
```

Documented relationship shapes (where the control files establish them):
- component → component (e.g., ServiceRegistry ↔ services via ServiceRegistration, Part 3 §3.4);
- manager → service / service → manager (Facade Services bridge Events into Manager calls, Part 00 §0.4 Principle 7; ADR-007);
- architectural subsystem → external entity (integration adapters at extension points, Part 00 §0.5.2; context.md §2.2).

The following non-equivalences are preserved and not inferred:
- **Provider ≠ owner.** Implementing an interface does not make the provider its architectural owner unless source establishes it. (Example: a service may *implement* `BaseService` without *owning* the BaseService contract, which Part 0/Part 5 establish.)
- **Consumer ≠ operator.** Consuming an interface does not make the consumer its operator or deployer.
- **Interface ≠ deployment boundary.** An interface between A and B does not imply A and B are separate processes, containers, machines, or independently deployed. v1.0 is single-process, in-memory only (Part 00 §0.2.2); no network/deployment boundary is implied by an interface.
- **Interface ≠ transport.** No interface in this chapter implies HTTP, REST, gRPC, RPC, WebSocket, TCP/UDP, a message queue, or remote execution unless the source explicitly establishes it (see Interface Architecture Model core rule; RPC RETRACTED per glossary §4.7 / MEMORY.md §6 Group A).

Only concrete provider/consumer relationships established by the control files are documented. Ownership, where unclear, is marked **UNSPECIFIED** (see §Architectural Interface Disciplines → Interface Ownership).

```python
    # NOTE: `metadata` is NOT a base Event field in Part 2 §2.2.1. Part 14 glossary §3.14
    # DOES list `metadata` among the Event base-contract fields — this is a genuine

    # source names are toJson/toDict/fromJson/fromDict (NOT to_dict/from_dict/is_valid):

    #   toDict(): Record<string, unknown>
    #   static fromJson(json: string): IEvent
    #   static fromDict(dict: Record<string, unknown>): IEvent
```

## Architectural Interface Disciplines

The following disciplines govern how the interfaces in this chapter are interpreted. They are derived from the Part 14 brief, glossary.md, context.md, and MEMORY.md safety rules; they introduce **no new interface, API, event, or contract**.

### Capability Facade Interfaces  —  [DERIVED; INT-CFS-BRIDGE-001 EXISTING]

The four Capability Facade Services (`SkillService`, `CouncilService`, `MCPService`, `MemoryService`; Part 00 §0.3.2) are **integration boundaries**, not new architecture. Their interface role (INT-CFS-BRIDGE-001) is to translate incoming Events into Manager calls and emit result Events (Part 00 §0.4 Principle 7; ADR-007). They MUST NOT contain business logic, and this document does not treat them as:
- an orchestration engine;
- a business-logic authority;
- an API gateway;
- a security gateway;
- a deployment unit.

No facade endpoint is invented here. Where the bridge contract is not fully specified, it is marked UNSPECIFIED / GAP — not fabricated.

### Synchronous vs Asynchronous Interaction  —  [DERIVED; do not guess]

EventBus event publication is asynchronous by default (Part 00 §0.4 Principle 1; `publish()` is async by default per Part 2 §2.4.7). However, the existence of EventBus does NOT make every AI-OS interaction asynchronous (glossary §4.1). Source-established **synchronous** interfaces also exist:
- `BaseService.on_start()` / `on_stop()` lifecycle hooks (Part 0 Principle 5; Part 5 CONF-ENG-ST-009);
- `healthCheck()` synchronous probe (Part 5 INV-CSI-010; Part 4 §4.10);
- `SecurityManager.authorize(...)` synchronous ABAC decision (Part 4 §4.7.4; INT-SEC-AUTH-001);
- `WorkflowManager` synchronous control command interface (INT-WF-CTRL-001; Part 4 §4.6.3/§4.6.11);
- Global Singleton Accessors — synchronous read-only getters (ADR-004; Part 1 §1.8.4).

Where the authority material does NOT establish an interaction pattern (blocking, concurrency, callbacks, scheduling), this document records it as **UNSPECIFIED** rather than inferring it. The default delivery guarantee for events is at-least-once (Part 12 events.md §34); exactly-once is NOT a transport-layer guarantee (MEMORY.md §6 Group D; glossary §3.14).

### Interface Ownership  —  [DERIVED; UNSPECIFIED where unclear]

For each interface, the following roles are distinguished and not conflated:
- **interface owner** — the component/authority responsible for the contract's definition;
- **interface provider** — the component that implements the contract;
- **interface consumer** — the component that depends on / consumes the contract;
- **interface caller** — the component that invokes it in a given interaction;
- **interface implementation** — the fulfilling code.

Consuming an interface does NOT make the consumer its owner; implementing an interface does NOT automatically make the implementer the architectural owner unless source establishes it. Where ownership is unclear, it is marked **UNSPECIFIED**. Example preserved: ServiceRegistry owns service registration/discovery topology computation (Part 3 SR-R-004/005) but does NOT own service lifecycles (execution is LifecycleManager's, INV-SR-OWN-003) — this split ownership is preserved, not merged.

### API vs Internal Interface / Exposure Scope  —  [DERIVED; UNSPECIFIED where not established]

Not every interface is public. The authority material distinguishes, where established:
- **internal architectural interface** — consumed within the kernel trust boundary;
- **service contract** — a registered service's obligations (BaseService, ServiceRegistry);
- **external API** — a boundary surface for external systems (Part 11 §9.3 adapters; UNSPECIFIED for most);

Where exposure scope is not established, this document records it as **UNSPECIFIED** and does not invent public APIs. The 13 Global Singleton Accessors are a fixed internal kernel surface (INV-CM-004; ADR-004), not a public API.

## Interface Certainty & Discipline Summary

This section consolidates where the brief requires interface-discipline preservation. Each item is recorded at the level established by the authority material; nothing is invented.

### Event Contract Discipline  —  [EXISTING / UNSPECIFIED where not defined]

The Event base contract (§EventBus Integration APIs) separates: event existence, envelope (`Event` base fields), payload (typed per eventType, immutable), delivery semantics (at-least-once default; exactly-once NOT a transport guarantee — MEMORY.md §6 Group D), and transport (EventBus; UNSPECIFIED network transport). This document does NOT invent delivery semantics: no exactly-once transport guarantee, no invented retries beyond Part 2 §2.5.1 `retryPolicy` source field, no invented ordering guarantees beyond per-correlation ordering (INV-EVT-004), no invented dead-letter handling (GAP-DLQ preserved). Where delivery details are not established, they remain GAP/UNSPECIFIED.

### Correlation and Causation  —  [EXISTING; propagation mechanism NOT invented]

`correlationId` (REQUIRED per INV-EVT-004) and `causationId` (INV-EVT-005) are EXISTING Event fields (Part 2 §2.2.1; Part 00 §0.4 Principle 8). Propagation is via EventBus only (glossary §4.5 RETRACTED RPC propagation). This document does NOT assume distributed tracing, HTTP headers, W3C Trace Context, OpenTelemetry, or middleware propagation — those are implementation mechanisms requiring source support (GAP-07 preserved).

### Lifecycle Interfaces  —  [EXISTING members; UNSPECIFIED methods]

Lifecycle concepts established: initialization/startup (`on_start()`), shutdown (`on_stop()`), deregistration, kernel state machine (UNINITIALIZED → INITIALIZING → RUNNING → SHUTTING_DOWN → TERMINATED, Part 1 §1.9.1), registration (`ServiceRegistry.register`). LifecycleManager owns execution of lifecycle batches (INV-SR-OWN-003); ServiceRegistry computes the plans (Part 3 SR-R-004/005). This document does NOT invent process supervisors, Kubernetes lifecycle, systemd, restart policies, or orchestration controllers. Where ordering/transition semantics are not established, they are UNSPECIFIED.

### Health Interfaces  —  [UNSPECIFIED / GAP]

`healthCheck()` returning `HealthStatus{ ready: boolean; details: object }` is EXISTING (Part 5 INV-CSI-010). The full `HealthStatus` schema, formal method signature, and probe mechanism are NOT established in Parts 0–13 (INT-HEALTH-001 UNSPECIFIED). No HTTP `/health`, `/ready`, `/live` endpoints, Kubernetes probes, or Prometheus metrics are invented — these are implementation mechanisms left UNSPECIFIED by the allowed control material. Health contract is distinct from monitoring implementation.

### Configuration Interfaces  —  [EXISTING read; UNSPECIFIED schema/API]

Configuration **read** interface is EXISTING (INT-CONFIG-READ-001; ADR-010; Part 1 §1.10.2; Part 3 §3.5). The four-layer merge is declarative (Part 00 §0.4 Principle 10). No configuration server, REST configuration API, environment-variable contract, remote configuration, hot reload, or configuration watcher is invented — a configuration relationship does not imply a network API (GAP-02 preserves the unspecified integration schema).

### Registration / Discovery Interfaces  —  [EXISTING; transport UNSPECIFIED]

`ServiceRegistry` registration/discovery is EXISTING (INT-SVC-REG-001; Part 3 §3.4). Discovery returns `BaseService` / `BaseService[]` / `null` (Part 3 §3.4.5). No DNS, Consul, Eureka, Kubernetes service discovery, or network registry endpoint is invented; registration architecture does not imply a particular implementation (MEMORY.md Group C: Topology Manager RETRACTED).

### Security and Interfaces  —  [EXISTING authz interface; conflict preserved; no invented mechanisms]

`SecurityManager.authorize(principal, action, resource, context)` is an EXISTING synchronous ABAC decision point (INT-SEC-AUTH-001; Part 4 §4.7.4). CONFLICT-03 (AuthN/AuthZ scope for v1.0: Part 00 §0.2.2 defers to v2.0 vs Part 13 governance overlay) is preserved, not resolved. This document does NOT invent authentication, authorization, API keys, OAuth, JWT, mTLS, TLS, RBAC, or policy engines. Genuine source authz requirements (INT-SEC-AUTH-001) are preserved; where security behavior is not defined it is UNSPECIFIED / GAP-SEC.

### Versioning  —  [EXISTING principle; no invented scheme]

Version identifiers are required (Part 00 §0.4 Principle 11; ADR-011): component version (`ComponentIdentity.version`), schema version (`eventVersion`), interface version. Event versioning is via `eventVersion`/`schema_ref`, NOT type-string versioning (RETRACTED `TASK_CREATED_v1`). No `/v1` path versioning, semantic API-versioning scheme, compatibility rule, deprecation period, or backward-compatibility guarantee is invented beyond what ADR-011 / Part 2 §2.10 establish.

### Error / Failure Contracts  —  [EXISTING fragments; UNSPECIFIED]

Operational recovery (circuit breaker RI-028, rollback WI-011) is NOT inferred from interface failure (MEMORY.md §6 Groups F). Where failure semantics are undefined, they remain UNSPECIFIED / GAP.
