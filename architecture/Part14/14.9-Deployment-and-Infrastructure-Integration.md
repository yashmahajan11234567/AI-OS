## 0. Status Taxonomy Reference

| Status | Meaning |
|--------|---------|

## 1. Deployment Boundaries

### 1.1 Process Boundary

**[EXISTING]** Part 00 §0.2.2: *"v1.0 runs as a single-process, in-memory system. The EventBus is in-process and in-memory."*
**[EXISTING]** Part 00 §0.2.2: *"Multi-process and distributed deployment are v2.0 features."*
**[CONFLICT]** Part 00 §0.3.2 / §0.7 lists `ResourceManager` as a Core Component, while Part 01 §1.7.1 lists `LifecycleManager` as the 4th Core Component. (CONFLICT-01, tracked in `context.md` §9)

**[EXISTING]** Per `adrs.md` Rule 0.2, Part 01 §1.7.1 (frozen architecture spec) is authoritative for Core Component enumeration. Part 00 §0.3.2 uses older naming and is superseded for kernel composition purposes.

**[DERIVED]** Inference path: Part 00 §0.2.2 establishes single-process v1.0 scope. The Hermes Kernel (Part 01 §1.1) is the internal orchestration layer. All Core Components and Core Managers operate within a single OS process. No multi-process deployment topology is established by Parts 0–13.

**[UNSPECIFIED]** Part 00 §0.2.2: The specific mechanism for external runtime isolation (e.g., process sandboxing, container boundaries, OS-level isolation) is not defined. Source Part: `dependency-map.md` GAP-08.

**[GAP]** External runtime isolation mechanism. Parts 0–13 do not specify how the single-process runtime is isolated from the host operating system or how extension code is sandboxed at the process level (ADR-013 permits extension points but does not define isolation mechanism — see `adrs.md` §2.13).

### 1.2 Architectural Boundaries

**[EXISTING]** Part 00 §0.5.2: Extension points are the only permitted boundary for external components to connect. Non-extension interfaces (Core Component interfaces, Core Manager interfaces, Kernel lifecycle, BaseService contract, StateManager scopes, Checkpoint format, global accessor signatures, EventBus interface) MUST NOT vary.

**[EXISTING]** Part 01 §1.1: *"The Kernel is an internal implementation detail; external boundaries are defined by extension points and accessors."*

**[EXISTING]** Part 01 §1.8.4: The 13 global singleton accessors (`get_eventBus`, `get_serviceRegistry`, `get_configuration`, `get_lifecycle`, `get_memory`, `get_llm`, `get_tools`, `get_storage`, `get_context`, `get_agent`, `get_workflow`, `get_security`, `get_observability`) are the sole kernel access surface. No additional accessors may be added or removed.

### 1.3 Trust Boundaries

**[EXISTING]** Part 00 §0.2.2: *"Authentication / Authorization: Kernel assumes trusted single-tenant process; multi-tenant auth is v2.0."*
**[CONFLICT]** Part 00 §0.2.2 defers bus-level authN/authz to v2.0, but `dependency-map.md` §4.3 and Part 12 ADR-008 (Accepted) mandate per-agent authorization via SecurityManager for multi-agent operations. (CONFLICT-03, tracked in `context.md` §9)

**[UNSPECIFIED]** Bus-level authentication and authorization for v1.0. Source Part: `interfaces.md` §2.6 — "Bus-level authn/authz is Unspecified (UNRES-05)."

**[GAP]** AuthN/AuthZ model for v1.0 integrations (GAP-06). Parts 0–13 do not establish a v1.0 authorization model for bus-level or inter-component authentication. Part 12 ADR-008 mandates per-agent authorization but no enforcement schema is defined in inspected source documents.

### 1.4 Deployment Topology

**[EXISTING]** Part 00 §0.2.2: v1.0 is single-process, in-memory only. No distributed orchestration, no network protocols, no cross-instance coordination.

**[FUTURE]** Distributed EventBus transport deferred to v2.0 (UNRES-EVT-DIST-001, tracked in `interfaces.md` §4.3 and `adrs.md` §2.1).

**[FUTURE]** Multi-instance coordination, cross-instance synchronization deferred to v2.0 (Part 00 §0.2.2; Part 02 §2.1.4).

**[UNSPECIFIED]** Deployment topology beyond single-process. Parts 0–13 do not specify container orchestration, cloud provider constraints, network topology, load balancing, service mesh, or deployment pipeline mechanisms.

**[GAP]** Configuration schema for integration components (GAP-02). Parts 0–13 do not define a schema for integration-specific configuration beyond the four-layer merge model.

## 2. Runtime Boundaries

### 2.1 Single-Process Constraint

**[EXISTING]** Part 00 §0.2.2: *"The EventBus is the sole communication substrate. It is in-process and in-memory for v1.0."*
**[EXISTING]** ADR-001 (Active): *"All inter-component communication MUST occur via the EventBus. There are no direct service-to-service calls, no synchronous RPC, and no shared mutable state outside StateManager."*

**[DERIVED]** The single-process constraint means all runtime components share the same OS process boundary. No inter-process communication (IPC), no remote procedure calls (RPC), no network sockets for component-to-component traffic. Inference path: Part 00 §0.2.2 + Part 01 §1.1 (Kernel is single-process orchestrator).

**[EXISTING]** Part 2 §2.2–2.4: EventBus provides publish/subscribe, routing, ordering, priority lanes, retry/dead-letter queues, event history, and schema validation as in-process mechanisms.

### 2.2 Kernel Runtime State

**[EXISTING]** Part 01 §1.10: The Hermes Kernel transitions through a defined lifecycle: NOT_INITIALIZED → PREPARE → INITIALIZING → RUNNING → SHUTTING_DOWN → TERMINATED.

**[EXISTING]** Part 01 §1.8.4: Global Singleton Accessors throw `KernelNotReadyError` before the RUNNING state. Accessors are available only after Phase 3 (ServiceRegistry) completes.

**[DERIVED]** Integration components must not assume kernel availability before `kernel.lifecycle.getState()` returns `RUNNING`. Inference path: Part 01 §1.8.4 (accessors throw before RUNNING) + Part 01 §1.10.2 (Phase 8 = Operational Kernel, RUNNING state).

### 2.3 External System Access

**[EXISTING]** Part 01 §1.1: External systems (MCP servers, model providers, identity providers, Obsidian, Graphify, web search) are reached through the EventBus mediated by Facade Services and Core Managers.

**[EXISTING]** ADR-007 (Active): *"Four Capability Facade Services (SkillService, CouncilService, MCPService, MemoryService) translate incoming Events into Manager calls and emit result Events. They MUST NOT contain business logic."*

**[EXISTING]** Part 00 §0.5.2: Extension points include "custom MCP transports, custom model providers" — these connect to external systems through documented mechanisms.

**[GAP]** External system adapter isolation semantics (see `interfaces.md` §4.4, UNRES-PLUGIN-001). Parts 0–13 do not define the exact sandboxing or resource isolation model for external system adapters.

## 5. Service Startup and Shutdown

### 5.1 Nine-Phase Initialization

**[EXISTING]** Part 01 §1.10.2: The Hermes Kernel initializes through nine phases (0–8):

| Phase | Name | What Initializes |
|-------|------|-----------------|
| Phase 0 | EventBus Bootstrap | EventBus initializes (C1, no dependencies) |
| Phase 1 | Registry Bootstrap | ServiceRegistry initializes (C2, depends: EventBus) |
| Phase 2 | Configuration Freeze | ConfigurationManager loads 4-layer merge, freezes (C3, depends: EventBus) |
| Phase 3 | Lifecycle Bootstrap | LifecycleManager initializes (C4, depends: EventBus, ServiceRegistry, ConfigurationManager) |
| Phase 4 | Memory & LLM | MemoryManager, LLMManager initialize (parallel, depends: EventBus, ConfigurationManager) |
| Phase 5 | Tools & Storage | ToolManager, StorageManager initialize (parallel, depends: Phase 4 managers) |
| Phase 6 | Context & Agents | ContextManager, AgentManager initialize (parallel, depends: Phase 4–5 managers) |
| Phase 7 | Workflows & Security | WorkflowManager, SecurityManager initialize (parallel, depends: Phase 4–6 managers) |
| Phase 8 | Observability | ObservabilityManager initializes (depends: all prior managers) |
| Phase 9+ | Service Initialization | Registered services initialize in dependency order |

> **Source-fidelity note:** Part 01 §1.10.2 states Phase 9+ as "Service Initialization" but does not explicitly name Engineering Services, Capability Facade Services, and Extensions as separate categories within Phase 9+. The table above reflects the source text. Part 14 does not further subdivide Phase 9+ into deployment units because source Parts do not establish deployment topology beyond initialization ordering.

**[EXISTING]** Part 01 §1.10.2: Each phase emits completion events and failures cascade to subsequent phases.

### 5.2 Shutdown Sequence

**[EXISTING]** Part 01 §1.11.2: *"Shutdown reverses initialization order with failure handling."*

The shutdown sequence reverses initialization order (shutdown phases S9+→S8→S7→S6→S5→S4→S3→S2→S1→S0):
- Phase S9+: Services unsubscribe and complete pending work (reverse dependency topology)
- S8: ObservabilityManager flushes metrics
- S7: WorkflowManager + SecurityManager shutdown
- S6: ContextManager + AgentManager shutdown
- S5: ToolManager + StorageManager shutdown
- S4: MemoryManager + LLMManager shutdown
- S3: LifecycleManager teardown
- S2: ConfigurationManager archives final config
- S1: ServiceRegistry teardown
- S0: EventBus drains in-flight events and shuts down (last)

**[EXISTING]** Part 01 §1.11.2: Integration events propagate shutdown status.

### 5.3 Service Lifecycle Contract

**[EXISTING]** ADR-005 (Active): *"Every Service MUST extend BaseService, declare depends_on for its dependencies, subscribe to events in on_start(), emit typed Events, and MUST NOT call other services directly."*
**[EXISTING]** Part 04 §4.2; Part 05 §5.2.5: BaseService provides standard lifecycle hooks: `on_start()`, `on_stop()`, `on_error()`, `health_check()`.

**[EXISTING]** `dependency-map.md` SC-28: ServiceRegistry event consumption contract — status: UNSPECIFIED. Source: `interfaces.md` §2.5.

**[GAP]** Integration failure event taxonomy (GAP-04). Parts 0–13 define failure classifications (TRANSIENT/DEGRADED/CRITICAL/FATAL, Part 01 §1.12) but do not define a taxonomy of failure events specifically for integration components. The kernel failure events are: `ComponentDegraded`, `ComponentFailed`, `CoreManagerFailed`, `KernelFatalError`. No integration-specific failure event types are established.

### 5.4 Extension Initialization

**[EXISTING]** Part 00 §0.5.2: Extensions connect only through documented Extension Points.
**[EXISTING]** Part 01 §1.10.2 Phase 6: *"Extensions load and register."*
**[EXISTING]** ADR-013 (Active): *"Specific extension points are explicitly permitted (custom Skills, custom MCP transports, custom model providers, custom resource types, custom memory backends, custom consensus algorithms, custom AI Agency agents)."*

**[EXISTING]** `dependency-map.md` CF-04: Extension point registration and event subscription — status: DEFINED. Source: Part 00 §0.5.2.

### 11.1 CONFLICT-01: Core Component Naming

**[CONFLICT]** Part 00 §0.3.2 / §0.7 names the four Core Components as: `EventBus, StateManager, WorkflowManager, ResourceManager`. Part 01 §1.7.1 names them as: `EventBus, ServiceRegistry, ConfigurationManager, LifecycleManager`.

**Conflicting parties:** Part 00 (general principles document) vs Part 01 (frozen architecture spec for Hermes Kernel).

**Specific disagreement:** The 2nd, 3rd, and 4th Core Component names differ. Part 00 uses older/higher-level naming; Part 01 uses implementation-specific naming.

**Part 14 stance:** Per `adrs.md` Rule 0.2, Part 01 §1.7.1 (frozen architecture spec) takes precedence over Part 00 §0.3.2 for kernel composition. This conflict is escalated to the ARB. Part 14 records both but does not merge or rename.

### 11.2 CONFLICT-02/04: Fourth Core Component

**[CONFLICT]** Three sources contradict each other on what constitutes the 4th Core Component:

1. **Part 00 §0.4 Principle 12**: References a logging abstraction (no component name specified)
2. **Part 01 §1.7.1 / §1.8.1**: `LifecycleManager` — 4th Core Component
3. **`dependency-map.md` CC-04, `interfaces.md` §2.1, Part 03 §3.6**: `StructuredLogger` — "the last Core Component"

**Conflicting parties:** Part 00 / Part 01 vs Part 03 §3.6 / `dependency-map.md` / `interfaces.md`.

**Specific disagreement:** Whether StructuredLogger or LifecycleManager is the 4th Core Component.

**Part 14 stance:** Per `adrs.md` Rule 0.2 (frozen architecture spec > other sources), Part 01 §1.7.1 naming of LifecycleManager is followed. StructuredLogger is classified as a logging substrate (Part 00 §0.4 Principle 12), not a Core Component. Conflict escalated to ARB.

### 11.3 CONFLICT-03: AuthN/AuthZ Scope

**[CONFLICT]** Part 00 §0.2.2 states: *"Authentication / Authorization: Kernel assumes trusted single-tenant process; multi-tenant auth is v2.0."* Part 12 ADR-008 (Accepted) mandates: *"Every inter-agent action MUST be authorized via SecurityManager."*

**Conflicting parties:** Part 00 (v1.0 scope) vs Part 12 ADR-008 (Accepted, multi-agent authorization).

**Specific disagreement:** Whether v1.0 has an active authorization model or defers entirely to v2.0.

**Part 14 stance:** The conflict is preserved. Part 00 §0.2.2 defers AuthN/Authz to v2.0; Part 12 ADR-008 mandates per-agent authorization. The reconciliation is UNSPECIFIED. Escalated to ARB.

### 11.4 CONFLICT-07: Core Manager Set

**[CONFLICT]** Part 01 §1.8.1 enumerates the canonical 9 Core Managers: MemoryManager, LLMManager, ToolManager, StorageManager, ContextManager, AgentManager, WorkflowManager, SecurityManager, ObservabilityManager. **Conflicting parties:** Part 01 (kernel specification) vs Part 04 (Part 4 architecture).

**Specific disagreement:** The set of Core Managers and whether StateManager, CapabilityManager, ResourceManager, and HealthManager are Core Managers.

**Part 14 stance:** Per `adrs.md` Rule 0.2 and `components.md` §1.4, Part 01 §1.8.1 is authoritative for the kernel's 9-manager set. Part 04-exclusive managers are surfaced, not merged into the canonical 9. Conflict escalated to ARB.
