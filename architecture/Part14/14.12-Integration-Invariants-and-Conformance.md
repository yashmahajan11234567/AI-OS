## 1. Purpose and Scope

**Status:** EXISTING

### 1.1 What This Chapter Does

Part 14.12 establishes the invariants that AI-OS integration architecture is explicitly required to preserve and defines what conformance means at the architectural level.

**Source:** context.md §0.2 ("Part 14 is derived integration documentation"); glossary.md §6.3 ("Invariant"), §6.7 ("Conformance"); README.md (Part 14 purpose).

### 1.2 Integration Invariants Defined

**Status:** DERIVED

An integration invariant is a property that must remain true across AI-OS integration boundaries — across the Extension Points (Part 00 §0.5.2), Facade Service interfaces (Part 00 §0.4 P7; Part 06), EventBus publish/subscribe (Part 00 §0.4 P1; Part 02), Global Singleton Accessors (Part 00 §0.4 P4; Part 01 §1.8.4), and configuration layer (Part 00 §0.4 P10; Part 07).

**Derivation path:**
- Part 00 §0.4 Principles establish source-defined invariants (event immutability, correlation/causation IDs, EventBus-only communication, version identifiers).
- glossary.md §6.3 defines "Invariant" as a condition that must hold true across all valid states.
- context.md §0.5.1 documents conformance levels L1–L4 that verify invariants.
- Therefore Part 14 integration components MUST conform to the same invariant set as Core Components and Services (**DERIVED** from the integration-boundary rules in context.md §2.2 and §1.3; not an independent EXISTING mandate). The status of this statement is DERIVED, not EXISTING — it is an inference from source boundary rules, not a new principle.

### 1.3 Conformance Defined

**Status:** EXISTING

Conformance is "the property that an implementation satisfies its declared contract, schema, and invariants" (glossary.md §6.7). At the architectural level, conformance means an integration component does not violate source-defined principles, does not bypass EventBus, and honors its declared versioned contract.

**Source:** glossary.md §6.7; context.md §14.3; Part 00 §0.5.1.

### 1.4 Architectural Compliance vs Implementation Test

**Status:** EXISTING / DERIVED

This chapter is **not** an implementation test specification. It does not define test harnesses, CI gates, or runtime enforcement agents. It documents the architectural conformance model so that future implementers and reviewers can assess whether an integration design preserves source invariants.

**Source:** context.md §0.5.1 (conformance model is conceptual, not an implementation spec); review-checklist.md §9.2 (Part 14 excludes testing frameworks/CI/CD).

### 1.5 What This Chapter Does NOT Define

**Status:** EXISTING

Part 14.12 does NOT:
- Define new invariants, conformance rules, or verification mechanisms (context.md §0.2.2, Integrity Rule 4).
- Introduce automated compliance tooling (context.md §0.6; MEMORY.md §10.9).
- Specify implementation-level code structure (context.md §1.3).
- Define deployment topology (context.md §2.3 Out-of-Scope; review-checklist.md §3.1).
- Redesign Core Component interfaces, Kernel boundaries, or principle semantics (context.md §0.5.5; Integrity Rule 5).

## 2. Definition of an Integration Invariant

**Status:** EXISTING / DERIVED

### 2.1 Invariant (Canonical Definition)

**Status:** EXISTING

> A condition that must hold true across all valid states of a system or component. Invariants are executable assertions organized by domain (Collaboration Invariants CI-, Communication Invariants CM-, Workflow Invariants WI-, Security Invariants SeI-, Resource Invariants RI-, Knowledge Invariants KI-).

**Source:** glossary.md §6.3; Part 12.12 (Runtime Invariants and Conformance).

### 2.2 Invariant vs Other Classifications

**Status:** EXISTING / DERIVED

The following distinctions prevent mis-classification:

| Classification | What it is | Source |
|----------------|-----------|--------|
| **Invariant** | A condition that MUST hold true across all valid states | glossary.md §6.3; Part 12.12 |
| **Implementation preference** | A recommended coding choice, not architecturally mandated | NOT source-established as invariant |
| **Design recommendation** | A PROPOSED pattern; not binding | context.md §0.1 (PROPOSED); MEMORY.md §7 |
| **Best practice** | Industry convention; only authoritative if sourced to a Part | glossary.md §1.2 |
| **Assumption** | Adopted for continuity; flagged, not source-established | context.md §0.1 (ASSUMPTION); MEMORY.md §7 |
| **Proposal** | Part 14 recommendation to resolve a GAP | context.md §0.1 (PROPOSED) |

**Part 14 implication:** Only classify a statement as EXISTING invariant if a source Part or accepted ADR establishes it. Do NOT promote a recommendation, best practice, or assumption to an EXISTING invariant (Integrity Rule 1, 2; MEMORY.md §10.2).

### 2.3 Status Taxonomy for Invariants

**Status:** EXISTING

Every invariant in this chapter carries exactly one status from the Part 14 taxonomy (context.md §0.1; glossary.md §2; review-checklist.md Appendix A):

| Marker | Meaning |
|--------|---------|
| **EXISTING** | Verbatim or field-for-field present in Parts 0–13 or accepted ADR, with explicit citation |
| **DERIVED** | Logically implied by one or more EXISTING statements; inference path shown |
| **ASSUMPTION** | Adopted for continuity; flagged for pre-implementation review |
| **UNSPECIFIED** | Named in source but no detail provided; Part 14 MUST NOT invent |
| **GAP** | Required for integration but undefined in Parts 0–13 |
| **PROPOSED** | Recommendation for chapter authors; not architecture fact |
| **FUTURE** | Explicitly deferred in source Parts |
| **CONFLICT** | Sources disagree; both preserved, escalate to ARB |

### 2.4 Invariant vs Conformance Criterion vs Verification Evidence

**Status:** EXISTING / DERIVED

These three concepts are distinct. Conflating them lets an AI agent assume conformance — or even implementation — that the architecture does not establish. Part 14 keeps them separate.

| Concept | What it is | What it is NOT |
|---------|-----------|----------------|
| **Invariant** | A property that MUST remain true across the relevant integration relationship or architectural condition (glossary.md §6.3; Part 12.12) | Not an implementation detail, preferred implementation, API specification, test case, deployment configuration, operational SLO, or architectural proposal |
| **Conformance Criterion** | What must be demonstrated to show the invariant is satisfied | Not the invariant itself; not the verification evidence |
| **Verification Evidence** | The evidence that demonstrates the criterion is met | Not the criterion; not an invented test/framework/tool |

Conceptual example (illustrative, not an invented requirement):

- **Invariant:** Event correlation identity is preserved where the source contract requires it.
- **Conformance criterion:** The implementation demonstrates that the required correlation identity is preserved.
- **Verification evidence:** The relevant event contract/schema/test/evidence demonstrates preservation.

Where the architecture does NOT define the verification mechanism, the verification method is **UNSPECIFIED**, not an invented test suite, CI pipeline, or runtime enforcer (context.md §0.5.1; review-checklist.md §9.2; MEMORY.md §10.9). Part 14 records the silence; it does not fill it.

**Source:** glossary.md §6.3, §6.7; context.md §0.5.1; review-checklist.md §9.2; MEMORY.md §10.2, §10.9.

## 3. Conformance Model

**Status:** EXISTING / DERIVED

### 3.1 Architectural Conformance (Conceptual)

**Status:** EXISTING

Source Parts establish a four-level conformance model (context.md §14.3; Part 00 §0.5.1):

| Level | Focus | Source |
|-------|-------|--------|
| L1: Structural | Compiles, imports resolve, base classes implemented | Part 00 §0.5.1 |
| L2: Contract | Event schemas match spec; interfaces honor signatures | Part 00 §0.5.1 |
| L3: Behavioral | Runtime invariants hold | Part 00 §0.5.1 |
| L4: Architectural | No principle violations | Part 00 §0.5.1 |

**Part 14 implication:** Integration components must pass all four conformance levels (context.md §14.3). Part 14 does not define the tests; it records the model.

### 3.1b Conformance-Level Boundary (Explicit)

**Status:** DERIVED

Architectural conformance levels describe conformance to Part 14 integration contracts and invariants. They do **not** independently establish:

- production readiness;
- deployment readiness;
- performance adequacy;
- security certification;
- availability (HA) guarantees;
- operational SLO/SLA compliance;

unless those properties are explicitly established by authoritative source material (MEMORY.md §6 Group A–K; context.md §2.3, §12.1; review-checklist.md §13.5).

A passing L1–L4 conformance assessment is a statement about contract/invariant preservation, **not** a statement that the component is safe, performant, deployed, or secure in operation. Where the source is silent on a property (e.g., availability — §10.5 UNSPECIFIED), no conformance level can certify it.

**Source:** context.md §0.5.1, §2.3; review-checklist.md §13.5; MEMORY.md §6, §10.9.

### 3.2 Conformance Dimensions

**Status:** DERIVED

The following conformance dimensions are derived from source-defined integration surfaces (context.md §2.2; glossary.md §3.10–3.15):

| Dimension | Established By | Status |
|-----------|---------------|--------|
| Interface conformance | Events/schemas/interfaces honor signatures (Part 00 §0.5.1 L2; glossary.md §3.15) | EXISTING |
| Schema conformance | JSON Schema conformance, version identifiers (Part 12 schemas.md §3–46; Part 00 §0.4 P11) | EXISTING |
| Event conformance | Event envelope fields, immutability, correlation/causation (Part 00 §0.4 P8; Part 02 §2.2.1) | EXISTING |
| Security conformance | Authorization where established; signed governance events (Part 13 governance; Part 00 §0.4 P8) | EXISTING / CONFLICT (CONFLICT-03) |
| Lifecycle conformance | Subscription in `on_start()`, `healthCheck()`, heartbeat (Part 00 §0.4 P5; Part 01 §1.9.1) | EXISTING |
| Deployment conformance | NOT established for integration topology (context.md §2.3 Out-of-Scope) | UNSPECIFIED |

**Part 14 implication:** Deployment conformance is UNSPECIFIED because deployment topology is out of Part 14 scope (context.md §2.3). Part 14 MUST NOT invent deployment conformance levels.

### 3.3 No Invented Compliance Tooling

**Status:** EXISTING

Part 14 does NOT define automated compliance scanners, CI gates, or conformance enforcement agents. Verification approaches are referenced as source-established concepts (static analysis, runtime assertions, policy checks — glossary.md §6.7) but are NOT specified as Part 14 mechanisms.

**Source:** context.md §0.6 (Integrity Rule 4 — anti-invention); review-checklist.md §9.2 (no CI/CD definitions); MEMORY.md §10.9.

## 4. Canonical Integration Invariants

**Status:** EXISTING / DERIVED

The following invariants are supported by the five permitted files. Each is classified per the Part 14 status taxonomy. No new invariant IDs are invented; IDs are only cited where the source assigns them (e.g., Part 00 §0.4 Principle numbers; Part 12.12 invariant prefixes CI-/CM-/WI-/RI-/SeI-/KI-).

### 4.1 EventBus-Only Communication

**Status:** EXISTING

- **ID/name:** Part 00 §0.4 Principle 1 (Event-First Communication); ADR-001 (Active)
- **Statement:** All inter-component communication MUST occur via the EventBus. No direct service-to-service calls, no synchronous RPC, no shared mutable state outside StateManager.
- **Scope:** All integration boundaries (Extension Points, Facade Services, EventBus, Global Accessors).
- **Source:** Part 00 §0.4 P1; Part 01 §1.15.2 INV-RT-002; ADR-001 (Active).
- **Implications:** Integration components communicate with AI-OS only via EventBus. No direct method calls to Core Components, Core Managers, or Engineering Services.
- **What is NOT implied:** Does NOT require every boundary interaction to be asynchronous (glossary.md §4.2); external-system adapters may use synchronous patterns (glossary.md §4.3; Part 11 §9.3). RPC is RETRACTED as a platform mechanism (glossary.md §4.7; MEMORY.md §6 Group A).

### 4.2 Immutable Events with Correlation and Causation IDs

**Status:** EXISTING

- **ID/name:** Part 00 §0.4 Principle 8; ADR-008 (Active); Part 00 §0.3.2 (`correlation_id`, `causation_id` mandatory)
- **Statement:** Every event MUST be immutable and carry `correlation_id` and `causation_id`. Events are immutable after emission.
- **Scope:** All events crossing integration boundaries.
- **Source:** Part 00 §0.4 P8; Part 00 §0.3.2; ADR-008 (Active); Part 02 §2.2.1.
- **Implications:** Integration events MUST carry correlation and causation IDs. Integration components MUST NOT mutate events after emission.
- **What is NOT implied:** Does NOT establish cryptographic signing of events (context.md §12.3 UNSPECIFIED; Part 13 may define). Does NOT establish exactly-once delivery (glossary.md §6.1; MEMORY.md §6 Group D).

### 4.3 Explicit Failure Handling via Events

**Status:** EXISTING

- **ID/name:** Part 00 §0.4 Principle 9; ADR-009 (Active)
- **Statement:** Failures MUST be communicated via events, not exceptions, across architectural boundaries.
- **Scope:** All integration failure communication.
- **Source:** Part 00 §0.4 P9; Part 01 §1.12; ADR-009 (Active).
- **Implications:** Integration failures MUST emit failure events via EventBus. Failures MUST NOT propagate as exceptions across boundaries.
- **What is NOT implied:** Does NOT establish automatic recovery, circuit breaker, or rollback triggered by conformance violations (glossary.md §6.4, §6.5; MEMORY.md §6 Group F). Retry/backoff for integration adapters is GAP-03 (context.md §15.2).

### 4.4 Configuration Declarative and Layered

**Status:** EXISTING

- **ID/name:** Part 00 §0.4 Principle 10; ADR-010 (Active)
- **Statement:** Configuration MUST use the four-layer merge (defaults → app.yaml → env.yaml → env vars). No hardcoded defaults in Kernel or Manager code. Configuration frozen before Service initialization.
- **Scope:** Integration component configuration.
- **Source:** Part 00 §0.4 P10; Part 01 §1.10.2 Phase 2/3; ADR-010 (Active).
- **Implications:** Integration components MUST obtain configuration through the kernel configuration authority. No direct env-var or local-file reads. No runtime reload after freeze.
- **What is NOT implied:** Integration configuration schema is GAP-02 (context.md §15.2). Part 14 MUST NOT invent the schema.

### 4.5 Version and Compatibility First-Class

**Status:** EXISTING

- **ID/name:** Part 00 §0.4 Principle 11; ADR-011 (Active)
- **Statement:** Event schemas, configuration schemas, and APIs MUST carry version identifiers. Breaking changes require major version bump and migration path.
- **Scope:** All integration schemas, APIs, and contracts.
- **Source:** Part 00 §0.4 P11; ADR-011 (Active); Part 12 schemas.md §18–19, §26.
- **Implications:** All integration event schemas, API contracts, configuration schemas MUST be versioned. Breaking changes require new major versions with migration paths.
- **What is NOT implied:** "Three versioning axes" is PROPOSED/derived, not source-established (glossary.md §6.8; MEMORY.md §6 Group H). "Four compatibility modes" is RETRACTED (glossary.md §6.9; MEMORY.md §6 Group G).

### 4.6 Observability Built-In

**Status:** EXISTING

- **ID/name:** Part 00 §0.4 Principle 12; ADR-012 (Active)
- **Statement:** Every component MUST emit structured logs (JSON, correlation IDs) and events for state transitions. StructuredLogger is the single logging abstraction.
- **Scope:** All integration components.
- **Source:** Part 00 §0.4 P12; Part 01 §1.8.1 M9; ADR-012 (Active).
- **Implications:** Integration components MUST emit structured logs and state-transition events. MUST participate in health checks.
- **What is NOT implied:** Integration observability metric names/dimensions are GAP-05 (context.md §15.2). Part 14 MUST NOT invent them.

### 4.7 Services Are Event-Driven Actors

**Status:** EXISTING

- **ID/name:** Part 00 §0.4 Principle 5; ADR-005 (Active)
- **Statement:** Every Service MUST extend BaseService, declare `depends_on`, subscribe in `on_start()`, emit typed events, and MUST NOT call other services directly.
- **Scope:** Service-type integration components.
- **Source:** Part 00 §0.4 P5; ADR-005 (Active); Part 05/Part 06.
- **Implications:** Service-type integration components follow BaseService contract.
- **What is NOT implied:** Does NOT require all integrations to be Services; extension-point integrations may be non-Service (context.md §2.2).

### 4.8 Capability Facade Services Bridge Only

**Status:** EXISTING

- **ID/name:** Part 00 §0.4 Principle 7; ADR-007 (Active)
- **Statement:** The four Capability Facade Services MUST translate incoming Events into Manager calls and emit result Events. They MUST NOT contain business logic.
- **Scope:** Facade Service integration surfaces (SkillService, CouncilService, MCPService, MemoryService).
- **Source:** Part 00 §0.4 P7; ADR-007 (Active); Part 06.
- **Implications:** Integration adapters that use Facade Services interact via EventBus events only. Integration adapters MUST NOT embed domain logic in facades.
- **What is NOT implied:** Facade Service responsibilities MUST NOT be expanded (context.md §5.4). Part 14 does not add business logic to facades.

### 4.9 Global Singleton Accessors Fixed Set

**Status:** EXISTING / DERIVED

- **ID/name:** Part 00 §0.4 Principle 4; Part 01 §1.8.4; INV-CM-004
- **Statement:** Core Components and Core Managers are exposed via a fixed set of 13 Global Singleton Accessors. Accessor signatures cannot be altered.
- **Scope:** Kernel access for integration adapters.
- **Source:** Part 00 §0.4 P4; Part 01 §1.8.4; INV-CM-004; context.md §14.1.
- **Implications:** Integration components access kernel via existing accessors only. MUST NOT add, remove, or rename accessors.
- **What is NOT implied:** Does NOT establish that every integration needs all 13 accessors. Hidden coupling via 13 global accessors is FIND-RISK-01 (review-checklist.md §11.3) — documented, not resolved by Part 14.

### 4.10 Extension Points Only

**Status:** EXISTING

- **ID/name:** Part 00 §0.5.2 (Extension Points); ADR-013 (Active)
- **Statement:** Custom skills, MCP transports, model providers, resource types, consensus algorithms, AI Agency agents connect only through documented Extension Points. Extension points are non-extension for Core Component/Manager interfaces (Part 00 §0.5.2).
- **Scope:** All extension-type integrations.
- **Source:** Part 00 §0.5.2; ADR-013 (Active); context.md §14.2.
- **Implications:** Integration extensions MUST register via applicable extension point. MUST NOT extend non-extension interfaces.
- **What is NOT implied:** Does NOT establish a universal "plugin registry" — RETRACTED (glossary.md §3.11; MEMORY.md §6 Group B). Does NOT establish "Topology Manager" — RETRACTED (glossary.md §3.18; MEMORY.md §6 Group C).

### 4.11 Kernel Initialization Order Compliance

**Status:** EXISTING / DERIVED

- **ID/name:** Part 01 §1.10.2 (initialization phases)
- **Statement:** EventBus initializes Phase 0; ServiceRegistry Phase 1; Configuration Freeze Phase 2; LifecycleManager Phase 3; Core Managers Phases 4–8; Services Phase 9+. Integration components initialize after Phase 9+.
- **Scope:** Integration component lifecycle startup.
- **Source:** Part 01 §1.10.2; context.md §7.2, §14.1.
- **Implications:** Integration components MUST NOT initialize before EventBus is operational (Phase 0) or before configuration freeze (Phase 2/3).
- **What is NOT implied:** Does NOT establish process/host/container mapping for integrations (context.md §2.3 Out-of-Scope; review-checklist.md §3.1).

### 4.12 No Invented Invariant Disclaimer

**Status:** DERIVED

Part 14 does NOT convert ordinary source statements into MUST-level invariants. Each invariant above carries a source citation that establishes it as a principle or runtime invariant. Where the source states a recommendation without MUST, Part 14 labels it PROPOSED or DERIVED, not EXISTING.

**Source:** context.md §0.5.1 (Integrity Rule 1); MEMORY.md §10.2.

## 5. Event Invariants

**Status:** EXISTING / UNSPECIFIED / CONFLICT

### 5.1 Event Identity

**Status:** EXISTING

- **Statement:** Every event carries a unique event identifier (`eventId` UUIDv7 per Part 2 §2.2.1; `event_id` ULID per Part 12 §4).
- **Scope:** All events.
- **Source:** Part 02 §2.2.1; Part 12 §4; context.md §16 (Provenance Index).
- **Conflict:** Field naming and ID format differ between Part 2 (PascalCase, UUIDv7) and Part 12 (snake_case, ULID) — CONFLICT (MEMORY.md §5 CONFLICT-04; glossary.md Conflict Log "Event field naming"). Both preserved.

### 5.2 Correlation and Causation

**Status:** EXISTING

- **Statement:** `correlation_id` and `causation_id` are mandatory on every event (Part 00 §0.3.2; Part 00 §0.4 P8).
- **Scope:** All cross-boundary events.
- **Source:** Part 00 §0.3.2; Part 00 §0.4 P8; Part 02 §2.2.1 (INV-EVT-004); glossary.md §4.5, §4.6.
- **Implications:** Integration events MUST carry both IDs. Propagation is via EventBus only (RETRACTED: not via RPC — glossary.md §4.5 Retraction).
- **Correlation/causation ≠ distributed tracing (explicit separation):** `correlation_id` / `causation_id` are established event-fields (Part 00 §0.3.2; P8). Distributed tracing (`trace_id`/`span_id`/`parent_span_id`, W3C-style) is a SEPARATE concern. glossary.md §6.13 records distributed tracing as enabled by correlation/causation propagation (Part 12.12 RI-010) — but the tracing *fields* themselves are NOT established as canonical event fields. Part 14 MUST NOT infer trace propagation, span creation, OpenTelemetry, or `traceparent` from the correlation/causation requirement (GAP-07, context.md §15.2; MEMORY.md §9). If Part 02 confirms tracing fields as canonical, integration MUST propagate them; if not, Part 14 MUST NOT introduce them (context.md §13.2; review-checklist.md §16.2).
- **What is NOT implied:** The correlation/causation requirement does NOT establish a distributed tracing protocol, span model, or sampling policy (UNSPECIFIED/GAP-07).

### 5.3 Ordering

**Status:** EXISTING / UNSPECIFIED

- **Statement:** Per-correlation ordering is guaranteed (INV-EVT-004, Part 02 §2.2.1). At-least-once is the default delivery guarantee (Part 12 events.md §34).
- **Scope:** Event delivery.
- **Source:** Part 02 §2.2.1 (INV-EVT-004); Part 12 events.md §34; glossary.md §3.14, §4.4.
- **UNSPECIFIED:** Event ordering guarantees *across* correlation families / partition keys — GAP-ORDER (review-checklist.md Appendix C).
- **Conflict:** Part 12 §4 adds `partition_key`; Part 2 §2.2.1 does not — GAP-ENV (review-checklist.md Appendix C).

### 5.4 Naming

**Status:** CONFLICT

- **Statement:** Five event naming schemes exist across authoritative sources (MEMORY.md §5 CONFLICT-04; glossary.md §3.14).
- **Schemes:** A. SCREAMING_SNAKE_CASE (Part 2 §2.3.1, 118 types); B. lowercase-dotted (Part 12 §22, 104 types); C. PascalCase+Event (Part 4 §4.3.10); D. verb-object PascalCase (Part 12 component docs — contradicts §22); E. PascalCase no-suffix lifecycle (Part 3 §3.4 FROZEN — contradicts Part 2).
- **Scope:** All event type references.
- **Conflict:** These are NOT normalized. Part 14 records all five; does NOT select one (MEMORY.md §5 CONFLICT-04, CONFLICT-06, CONFLICT-07; review-checklist.md §10.2).
- **GAP:** Three registries (118 + 104 + 51 = ~273) are NOT a single unified set — GAP-UNIVERSE (MEMORY.md §9; review-checklist.md Appendix C).

### 5.5 Envelope

**Status:** CONFLICT / UNSPECIFIED

- **Statement:** Two coexisting envelope specifications (GAP-ENV):
  - Part 2 §2.2.1: `eventId` (UUIDv7), `eventType`, `eventVersion` (SemVer), `timestamp`, `correlationId`, `causationId`, `source`, `target`, `priority` (5-level), `category`, `payload`, `checksum`.
  - Part 12 §4 / schemas.md §1.1: `event_id` (ULID), `event_type`, `event_version` (integer), `produced_at`, `produced_by`, `partition_key`, `correlation_id`, `causation_id`, `tenant_id`, `priority` (P0–P3), `trace`, `schema_ref`, `payload`, `metadata`, `security`.
- **Scope:** Event envelope structure.
- **Conflict:** Field names, ID format, priority encoding, and envelope fields diverge — GAP-ENV (MEMORY.md §11.2; review-checklist.md §10.4, §12.1). Both authoritative within their domain; Part 14 does NOT invent a unified envelope.

## 11. Conformance Levels

**Status:** EXISTING

### 11.1 Four Conformance Levels (Source-Established)

**Source:** Part 00 §0.5.1; context.md §14.3; glossary.md §6.7.

The four conformance levels are a *conceptual model*. Each level below states: what CAN be verified, what EVIDENCE is required, and what it does NOT prove. Part 14 does NOT claim implementation, runtime, or production conformance merely because documentation exists.

| Level | Focus | What CAN be verified | Required EVIDENCE | What it does NOT prove |
|-------|-------|----------------------|-------------------|------------------------|
| **L1: Structural** | Compiles, imports resolve, base classes implemented | That integration code builds and implements the required base classes/accessor signatures | Build output; source inspection of base-class implementation | That the component behaves correctly at runtime; that invariants hold (L3); that no principle is violated in operation (L4) |
| **L2: Contract** | Event schemas match spec; interfaces honor signatures | That declared event schemas, interface signatures, and version identifiers match the source registry | Schema/interface diff against Part 2 §2.2.1, Part 12 schemas.md §46, Part 00 §0.4 P11 | That events are emitted correctly at runtime (L3); that the component is authorized (CONFLICT-03); that behaviors are sound |
| **L3: Behavioral** | Runtime invariants hold | That the component preserves source-defined invariants during execution (e.g., EventBus-only, immutability, correlation/causation, idempotent handling where required) | Runtime assertions / observed behavior / test evidence against the invariant set | Production-grade reliability, availability, or recovery (those remain UNSPECIFIED/operational); that the component is deployed or operated correctly |
| **L4: Architectural** | No principle violations | That the integration does not bypass EventBus, does not add kernel domain logic, does not alter accessor signatures | Design review against Part 00 §0.4 Principles 1, 4, 7; component source | That the code runs; that a GAP or CONFLICT is resolved; that security is satisfied (blocked by CONFLICT-03) |

**Integration implication (DERIVED from context.md §14.3):** Integration components must pass all four levels conceptually. Part 14 records the model; it does not define the tests. Where a level depends on an unresolved GAP or CONFLICT, that level CANNOT be conclusively verified (see §11.4).

### 11.5 GAP-Aware Conformance

**Status:** DERIVED

A GAP does NOT automatically mean "non-conformant." Part 14 distinguishes the conformance state of each invariant:

| Conformance state | Meaning | Example |
|-------------------|---------|---------|
| **Conformant** | Invariant is EXISTING/DERIVED and verifiable at the relevant level | EventBus-only communication (P1) |
| **Violated** | An explicitly established invariant is breached | Direct service-to-service call (P1 breach) |
