# 14.4 Plugin and Extension Architecture

## Status

**DRAFT** — Integration documentation. Builds exclusively from Parts 0–13 and approved ADRs.

## Purpose

This chapter documents the integration architecture for how extensions, plugins, and customization mechanisms attach to the AI-OS platform. It composes the extension point governance established in Parts 0–13; it does not redesign, extend, or redefine those mechanisms. This chapter itself is a Part 14 integration document; its status taxonomy, conflict register, and gap register follow the Part 14 authority model defined in context.md.

## Scope

This chapter covers ONLY:
- Extension points as defined in source Parts
- Extension registration boundaries and per-domain registries
- Extension lifecycle as constrained by source Parts
- Security and sandboxing boundaries as stated in source Parts
- Version compatibility obligations imposed by source Parts
- Governance implications of extension mechanisms

This chapter explicitly does NOT design:
- A plugin registry as a standalone distribution mechanism
- Plugin lifecycle phases beyond those constrained by source Parts
- Plugin API surface beyond extension-point signatures
- Sandbox technology, process isolation mechanism, or permission model
- Plugin manifest format, dependency resolver, or discovery mechanism
- Hot-loading infrastructure or extension registry API
- Semantic-version rules for plugins

Where Parts 0–13 do not define a mechanism, this chapter records it as UNSPECIFIED or GAP. It does not invent a mechanism.

Every mechanism, boundary, and claim in this chapter carries exactly one status label. Labels are defined in Part 14 README §Status Taxonomy and reproduced here for convenience:

| Status | Meaning |
|--------|---------|

| **ASSUMPTION** | Adopted for continuity; not explicitly stated in source Parts. Must be flagged and reviewed before implementation. |

## 2. Extension Points

### 2.1 Extension Point Inventory

**Status:** EXISTING — Source: Part 00 §0.5.2 (verbatim table)

Part 00 §0.5.2 defines the following explicitly permitted extension points:

| Extension Point | Mechanism | Governance |
|-----------------|-----------|------------|
| **Custom Event Types** | Subclass `Event` with new `EventType` enum value | MUST follow Part 2.1/2.2; register in EventType catalog |
| **Custom Memory Backend** | Implement `MemoryBackend` ABC | MUST satisfy Part 4.6 contract; register via `MemoryManager` |
| **Custom Skill** | Implement `Skill` interface; register via `SkillManager` | MUST be sandboxed; MUST emit `SkillExecuted`/`SkillFailed` |
| **Custom MCP Transport** | Implement `MCPTransport` for new protocol | MUST satisfy `MCPManager` contract (Part 4.8) |
| **Custom Consensus Algorithm** | Add to `ConsensusAlgorithm` enum; implement in `CouncilManager` | MUST satisfy liveness/safety properties (Part 4.9) |
| **Custom AI Agency Agent** | Subclass base `AIAgent`; register via `AIAgencyService` | MUST emit audit `*Requested`/`*Completed` event pairs (Part 4.10) |
| **Custom Model Provider** | Register in `ModelRouter` capability registry | MUST implement capability-based routing interface (Part 4.11) |
| **Custom Resource Type** | Extend `ResourceType` enum; register quota in `ResourceManager` | MUST implement allocation/wait-queue/TTL semantics (Part 4.12) |

**Part 14 implication:** Integration components using any of these extension points MUST satisfy the governance constraints listed above. Integration components MUST NOT use non-extension-point interfaces as extension targets.

---

### 2.2 ADR-013 Integration Impact

**Status:** EXISTING — Source: ADR-013 [Active]; Part 14 adrs.md §2.2 (P14-ADR-003)

ADR-013 (Active) explicitly enumerates the permitted extension points and the non-extension points. Its verbatim text lists **six** items:

> Specific extension points are explicitly permitted (custom Skills, custom MCP transports, custom model providers, custom resource types, custom memory backends, custom consensus algorithms). Non-extension points (Core Component interfaces, Core Manager interfaces, Kernel lifecycle, BaseService contract, StateManager scopes, Checkpoint format, RetryBudget semantics, global accessor signatures, EventBus interface) MUST NOT vary.

**Boundary consequence:** Integration components that touch a non-extension-point interface fall outside the ADR-013 boundary.

**Note:** ADR-013 lists six extension points in its verbatim text. Part 00 §0.5.2 lists eight (the six above plus Custom Event Types and Custom AI Agency Agents). Both enumerations are EXISTING. The two items in Part 00 §0.5.2 that ADR-013 does not list are "Custom Event Types" and "Custom AI Agency Agents." ADR-013's set is a shorter enumeration, not a capability-domain subset. Part 14 does not resolve this enumeration discrepancy; both are preserved. Integration components MAY use any extension point listed in Part 00 §0.5.2, subject to its governance constraints.

**CONFLICT-EXT-04:** The prose in prior versions of this chapter stated "ADR-013 lists seven permitted extension points," while the verbatim quote lists six items, and the three-way count variance (prior prose: 7; ADR-013 verbatim: 6; Part 00 §0.5.2: 8) has been corrected to reflect the verbatim enumeration accurately.

---

### 2.3 Non-Extension Points

**Status:** EXISTING — Source: Part 00 §0.5.2 (verbatim blockquote)

> **Non-Extension Points (MUST NOT vary):** EventBus interface, Kernel lifecycle, BaseService contract, ServiceRegistry topological order, StateManager scopes, Checkpoint disk format, RetryBudget semantics, RCA keyword lists (extensible via config only), global accessor signatures.

**Part 14 implication:** Integration components MUST NOT attempt to extend, override, replace, or wrap any non-extension-point interface. Violation of this boundary is an architectural violation, not a configuration error.

### 2.4 Custom Events Extension Point

**Status:** EXISTING / CONFLICT / GAP

**EXISTING basis:** Part 00 §0.5.2 lists "Custom Event Types" as an explicitly permitted extension point: "Subclass `Event` with new `EventType` enum value; MUST follow Part 2.1/2.2; register in EventType catalog."

**CONFLICT:** Part 2 INV-ET-003 prohibits late EventType registration in v1.0 (closed enum). ADR-013 lists "custom events" as a permitted extension point. These two statements are in apparent contradiction.

**Part 14 position:** Part 14 preserves both statements and escalates to ARB. It does NOT silently resolve the conflict by choosing one source over the other. Integration components requiring custom event types MUST verify which constraint applies in their domain before registering events.

**GAP:** Even if custom events are permitted, the specific registration mechanism, the catalog mutation API, and the validation rules for new EventType values are not fully specified in inspected Parts 0–13 for v1.0 integration use. This is recorded as GAP-EXT.

## 3. Plugin Term Classification

### 3.1 Definition

**Status:** EXISTING — Source: Part 14 glossary.md §3.11

The Part 14 glossary defines "Plugin" as:

> A dynamically loaded component that extends platform functionality through declared extension points.

This definition is EXISTING in the Part 14 glossary, sourced from Part 00 §0.5.2 (Extension Points) and Part 06 §6.7 (failure isolation) and Part 07 §7 (capability isolation).

### 3.2 "Plugin Registry" — RETRACTED

**Status:** RETRACTED — Source: Part 14 glossary.md §3.11 (correction note)

The Part 14 glossary previously referenced "plugin registry" as an existing distribution mechanism. That wording was incorrect. Parts 1–13 establish **per-domain registries** and extension points; a standalone universal "plugin registry" is NOT established in Parts 1–13.

**Corrected classification:**
- "Plugin registry" (standalone distribution mechanism): **DERIVED/PROPOSED** — not established in Parts 1–13.
- Per-domain registries: **EXISTING** — SkillRegistry, MemoryBackendRegistry, MCPTransportRegistry, ModelRouter capability registry, and similar per-domain registration mechanisms exist within their respective managers.

**Part 14 implication:** Integration components MUST register through the per-domain registry applicable to their extension point. They MUST NOT assume a universal plugin registry exists.

### 3.3 Plugin as Integration Category

**Status:** DERIVED — Source: Part 14 components.md §9 (Module Category); Part 14 glossary.md §3.11

Part 14 components.md §9 classifies "Module" as **NOT** a first-class architectural component in Parts 1–13. Modular extension units (skills, MCP servers, agents, memory backends, plugins) are inventoried under their real category.

**DERIVED implication:** A "plugin" in AI-OS is an extension unit that connects through one of the eight extension points in Part 00 §0.5.2. It is not a distinct architectural layer or component class. Its classification depends on which extension point it uses:
- A custom Skill plugin → classified as a Skill extension, registered via SkillManager
- A custom MCP transport plugin → classified as an MCP extension, registered via MCPManager
- A custom memory backend plugin → classified as a Memory extension, registered via MemoryManager
- etc.

## 4. Per-Domain Registration Mechanisms

### 4.1 Existing Per-Domain Registries

**Status:** DERIVED — Source: Part 00 §0.5.2 (each extension point lists its registration mechanism); Part 14 interfaces.md; Part 14 components.md

Parts 0–13 do not define a single unified "plugin registry." Instead, each capability manager maintains its own registration surface:

| Extension Domain | Registration Mechanism | Registry/Surface |
|-----------------|----------------------|------------------|
| Custom Skill | Implement `Skill` interface; register via `SkillManager` | SkillManager |
| Custom MCP Transport | Implement `MCPTransport`; register via `MCPManager` | MCPManager |
| Custom Memory Backend | Implement `MemoryBackend` ABC; register via `MemoryManager` | MemoryManager |
| Custom Model Provider | Register in `ModelRouter` capability registry | ModelRouter |
| Custom Consensus Algorithm | Add to `ConsensusAlgorithm` enum; implement in `CouncilManager` | CouncilManager |
| Custom AI Agency Agent | Subclass base `AIAgent`; register via `AIAgencyService` | AgentManager / AIAgencyService |
| Custom Resource Type | Extend `ResourceType` enum; register quota in `ResourceManager` | ResourceManager |

**DERIVED from:** Each extension point's governance row in Part 00 §0.5.2 specifies the registration mechanism. No universal registry is mentioned.

**Part 14 implication:** Integration components MUST identify the correct per-domain registry for their extension type and register through that registry only. Cross-registry registration is not permitted.

> **CONFLICT-07 note:** Manager names in this table follow Part 01 §1.8.1 (canonical 9-manager set). Part 04 §4.2.1 enumerates a different manager set that includes different managers. Manager numbering schemes (M1–M9) are contested; this table uses plain manager names, not M-number labels.

## 5. Extension Lifecycle Boundaries

### 5.1 What Source Parts Define

**Status:** EXISTING / DERIVED

Parts 0–13 constrain extension lifecycle in the following ways:

**EXISTING constraints:**
- **BaseService contract** (non-extension point): All Service-type components, including integration services, MUST extend BaseService, declare `depends_on`, subscribe in `on_start()`, and emit typed Events (ADR-005 [Active]; Part 5 §5.2).
- **ServiceRegistry registration**: All Services are registered in ServiceRegistry (C2) and initialized by LifecycleManager in the topological order (Part 1 §1.10.2).
- **Event-mediated lifecycle**: Service lifecycle transitions emit events. Part 2 includes `SERVICE_STARTED`, `SERVICE_STOPPED`, `SERVICE_DEGRADED`, `SERVICE_FAILED`. The PascalCase variants `ServiceRegistered`, `ServiceInitialized`, `ServiceShutdown`, `ServiceHealthChanged`, `ServiceDegraded`, `ServiceFailed` are DERIVED aliases from `interfaces.md` and Part 3 (FROZEN); see CONFLICT-07 and 14.1 §6.1.
- **Kernel initialization phases**: Service-type components initialize in Phase 4 (Engineering Services) after Core Components (Phase 1), Core Managers (Phase 2), and ServiceRegistry (Phase 3) (Part 1 §1.10.2; 14.1 §5.1).
- **Shutdown ordering**: Services shut down in reverse initialization order with failure handling (Part 01 §1.11.2).

**DERIVED constraints:**
- Integration components that are Service-type MUST follow the same lifecycle as Engineering Services: register in ServiceRegistry, declare dependencies, subscribe in `on_start()`, emit lifecycle events.
- Integration components that are Service-type load during Phase 4 (Engineering Services) per Part 01 §1.10.2.

---

### 5.2 What Source Parts Do NOT Define

**Status:** UNSPECIFIED / GAP

Parts 0–13 do NOT define the following lifecycle mechanisms for extensions:

| Mechanism | Status | Reason |
|-----------|--------|--------|
| Dedicated extension initialization phase | **UNSPECIFIED** | Parts 0–13 do not define a separate "Phase 6" for extensions; Phase 6 in Part 1 is for ContextManager and AgentManager (Core Managers) |
| Plugin manifest format | **UNSPECIFIED** | No manifest schema defined in Parts 0–13 |
| Plugin discovery mechanism | **UNSPECIFIED** | No discovery protocol or directory scanning defined |
| Plugin dependency resolver | **UNSPECIFIED** | No dependency resolution between plugins defined |
| Plugin hot loading / reloading | **UNSPECIFIED** | No hot-reload mechanism for extensions defined in v1.0 |
| Plugin unload / cleanup lifecycle | **UNSPECIFIED** | Extension shutdown is governed by Manager/Service lifecycle, not a plugin-specific lifecycle |
| Plugin permission model | **UNSPECIFIED** | No plugin-specific permission model beyond the sandboxing requirement for Skills |
| Plugin API version negotiation | **UNSPECIFIED** | No plugin API versioning scheme defined |
| Extension ordering / priority | **UNSPECIFIED** | No mechanism for ordering multiple extensions within the same domain |

**Part 14 implication:** These items MUST NOT be invented by Part 14 or its chapters. They are recorded as UNSPECIFIED. If an integration use case requires any of these mechanisms, the requirement MUST be raised as an ADR or gap resolution before implementation.

## 7. Version Compatibility

### 7.1 Versioning Obligations

**Status:** EXISTING — Source: ADR-011 [Active]; ADR-013 [Active]

ADR-011 [Active] requires that all event schemas, configuration schemas, and APIs carry version identifiers. Breaking changes require a major version bump and migration path.

ADR-013 [Active] requires that non-extension-point interfaces MUST NOT vary. Extension-point interfaces MAY evolve, but their contracts are governed by the versioning requirements of the host Manager's domain.

**Part 14 implication:** Extension implementations MUST carry version identifiers on their schemas and APIs. Changes to extension-point contracts MUST follow the versioning rules of the host Manager's domain.

**Part 14 implication:** Part 14 MUST NOT invent plugin semver rules. If version compatibility between plugins and the platform needs to be managed, this is a GAP requiring ADR resolution.

## 7.3 Plugin Configuration

**Status:** EXISTING / UNSPECIFIED — Source: Part 00 §0.4 Principle 10; Part 01 §1.10.2; Part 14 context.md §9

Part 00 §0.4 Principle 10 establishes the kernel's four-layer configuration model:
> Configuration MUST use the four-layer merge (defaults → app.yaml → env.yaml → env vars). No hardcoded defaults in Kernel or Manager code.

Part 01 §1.10.2 defines Configuration Freeze as Phase 2 of kernel initialization, after which configuration is immutable.

**EXISTING applicability:** Extensions that are Service-type components receive configuration through the same four-layer merge. Extension-specific configuration values, if any, flow through `ConfigurationManager` and are frozen after Phase 2/3. Extensions MUST NOT read environment variables or local files directly for configuration.

**UNSPECIFIED:** Parts 0–13 do not define:
- A plugin-specific configuration schema or section
- How extension-specific configuration keys are namespaced
- Whether extensions can declare configuration requirements declaratively
- Configuration reload semantics for extensions

**Part 14 implication:** Integration components obtain configuration through the kernel's `ConfigurationManager`. Configuration is immutable after freeze; reload requires lifecycle restart. Integration components MUST NOT bypass `ConfigurationManager` or read configuration directly from environment variables or local files. If an integration use case requires extension-specific configuration semantics, this is a GAP requiring ADR resolution.

### 8.1 Extension Points as Governance Surface

**Status:** DERIVED — Source: Part 00 §0.5.2; ADR-013 [Active]; Part 13 governance architecture

DERIVED: Every extension point is a governance surface because:
1. Extensions execute code within the kernel process or with kernel-adjacent privileges
   - Inference path: ADR-013 requires extensions connect only through extension points; extension points are hosted by Core Managers; Core Managers operate within the kernel process; therefore extensions execute within the kernel process.
2. Extensions emit events that enter the governance event stream (governance.* events, Part 13)
   - Inference path: Part 13 defines governance components that subscribe to EventBus; extensions emit events via EventBus; therefore extension events are visible to governance components.
3. Extensions MAY be subject to SecurityManager authz checks as native components
   - Inference path: ADR-013 requires extensions satisfy the governance constraints of their extension point; those governance constraints include SecurityManager authorization IF the Part 13 governance overlay is active in v1.0. This is conditioned on CONFLICT-03 (Part 00 §0.2.2 defers AuthN/AuthZ to v2.0). Therefore SecurityManager authz for extensions is DERIVED/CONDITIONAL, not EXISTING.
4. Extensions that emit audit-relevant events (SkillExecuted, MCPServerConnected, etc.) contribute to the audit trail
   - Inference path: ADR-009 requires event-mediated failure communication; Part 13 defines audit trail via EventBus; extension events flow through the same EventBus; therefore extension events contribute to the audit trail.

**Part 14 implication:** Integration components using extension points are subject to the governance overlay IF the Part 13 governance architecture is active in v1.0. Their events flow through the EventBus, which Part 13 governance components subscribe to. Their actions are subject to the same policy evaluation IF the governance overlay is active. Their audit records are stored in the same audit log IF G-09 is active. All of these are conditioned on CONFLICT-03 (Part 00 §0.2.2 defers AuthN/AuthZ to v2.0). Part 13 governance components (G-00 through G-15) are logical architecture concepts, not deployment units, per P13-ADR-010 [Draft].

### 8.2 Part 13 Governance and Extensions

**Status:** DERIVED / GAP / CONFLICT (CONFLICT-03 — see §8.3)

Part 13 defines governance components G-00 through G-15. Per P13-ADR-010 [Draft], these are logical architecture concepts (not deployment units). Their relationship to extensions is:

- **EXISTING:** Governance components G-00 through G-15 are named in Part 13 components.md §1. Their dependency on EventBus and SecurityManager is stated in Part 13 components.md §2, §6.
- **DERIVED:** Extensions that emit events are observed by governance components through the EventBus — IF the governance overlay is active.
- **GAP:** The specific governance policy rules that apply to extensions (e.g., which extensions require policy evaluation before loading, which extensions are subject to G-05 Decision Authority Manager approval) are not specified in inspected Parts 0–13

**Part 14 implication:** Integration components using extension points operate under the governance overlay, but the specific policy rules for extension governance are a GAP. Part 14 does not invent these rules.

## 9. Integration with Capability Facade Services

### 9.1 Facade Services as Extension Consumers

**Status:** EXISTING — Source: Part 06 §6.1; Part 06 §6.2–6.5

The four Capability Facade Services are thin bridges between the EventBus (Execution Plane) and the Core Managers (Definition Plane):

| Facade Service | Bridges to | Consumes Events |
|----------------|-----------|----------------|
| SkillService | SkillManager (M3) | Skill execution requests |
| CouncilService | CouncilManager (M5) | Council convening requests |
| MCPService | MCPManager | MCP tool call requests |
| MemoryService | MemoryManager (M1) | Memory store/retrieve requests |

**Part 14 implication:** Integration components that extend Skill, Council, MCP, or Memory capability domains interact with the kernel through the corresponding Facade Service. They do NOT call the Manager directly. They emit events consumed by the Facade Service, which calls the Manager.

---

### 9.2 Facade Service Constraints on Extensions

**Status:** EXISTING — Source: Part 06 §6.1 (INV-CFS-* invariants)

Facade Services enforce the following constraints on any capability consumer, including extensions:

- **INV-CFS-MGR-001:** Facade Services call exactly one Core Manager per event handler invocation.
- **INV-CFS-MGR-002:** Core Manager method signatures and behavior MUST NOT change to accommodate Facade Services.
- **INV-CFS-MGR-003:** Facade Services MUST NOT access Core Managers outside event handler execution.
- **INV-CFS-BRIDGE-001:** Exactly four Facade Services, one per bridged domain.
- **INV-CFS-BRIDGE-002:** No Facade Service bridges more than one Manager domain.

**Part 14 implication:** Extension implementations that consume capability through Facade Services MUST NOT assume they can call multiple Managers from a single event handler or access Managers outside event handler context. Adding Facade Services for new capability domains is outside the extension-point model defined by ADR-013.

---

### 9.3 MemoryService Dual-Role

**Status:** CONFLICT — Source: Part 14 components.md §11.6; Part 14 integrations.md

MemoryService (ES-08) is classified as both an Engineering Service (Part 5 §5.2) and a Capability Facade Service (Part 6). This is CONFLICT-06.

**Part 14 implication:** Integration components that extend the Memory domain via custom Memory Backend MUST register via MemoryManager and interact through the MemoryService facade. The dual classification does not change the extension registration path.

## 10. Adapter Pattern for External Tool Integration

### 10.1 Thin Bridge Requirement

**Status:** EXISTING — Source: Part 06 §6.1; ADR-007 [Active]

ADR-007 [Active] states:
> Facade Services MUST translate Events into Manager calls. They MUST NOT contain business logic. Facades enforce execution monopoly: all capability invocations MUST transit the Facade.

**Part 14 implication:** Integration adapters that wrap external tools or services through a permitted extension point MUST be thin bridges. They translate external tool interfaces into the kernel's extension-point contract. They MUST NOT contain business logic that interprets, transforms, or enriches Manager return values beyond serialization.

---

### 10.2 Event Emission Requirements

**Status:** EXISTING — Source: ADR-008 [Active]; ADR-009 [Active]; ADR-012 [Active]; Part 00 §0.5.2

All integration components that emit events MUST satisfy:
- Every event MUST carry `correlation_id` (UUID) and `causation_id` (UUID or null) (ADR-008)
- Events MUST be immutable value objects (ADR-008)
- Failures MUST be communicated via Events, not exceptions crossing architectural boundaries (ADR-009)
- Every component MUST emit structured logs (JSON, correlation IDs) and Events for state transitions (ADR-012)

Extension-specific event requirements from Part 00 §0.5.2 governance rows:
- Custom Skills governance row: "MUST emit `SkillExecuted`/`SkillFailed`"
- Custom AI Agency Agents governance row: "MUST emit audit `*Requested`/`*Completed` event pairs"

**Part 14 implication:** Integration adapters for these extension points MUST emit the required event pairs. They MUST NOT swallow failures silently or propagate exceptions across architectural boundaries.

## 12. CONFLICT Register for Extension Architecture

**Party B:** Part 00 §0.5.2 lists "Custom Event Types" as an explicitly permitted extension point; ADR-013 [Active] lists "custom events" as permitted.

### 12.2 CONFLICT-EXT-02: Extension Point Enumeration — Part 00 vs ADR-013

**Status:** CONFLICT

**Party A:** Part 00 §0.5.2 lists 8 extension points (Custom Event Types, Custom Memory Backend, Custom Skill, Custom MCP Transport, Custom Consensus Algorithm, Custom AI Agency Agent, Custom Model Provider, Custom Resource Type).
**Party B:** ADR-013 [Active] lists 6 permitted extension points in its verbatim text (custom Skills, custom MCP transports, custom model providers, custom resource types, custom memory backends, custom consensus algorithms).

**Disagreement:** Whether "Custom Event Types" and "Custom AI Agency Agents" are explicitly enumerated in ADR-013.

**Part 14 position:** Both sources are EXISTING. The Part 00 §0.5.2 enumeration is the more complete list (8 items vs. 6 in ADR-013). ADR-013's set omits "Custom Event Types" and "Custom AI Agency Agents." Part 14 does not resolve which enumeration controls; both are preserved. Integration components MAY use any extension point listed in Part 00 §0.5.2, subject to its governance constraints. Flagged for ARB awareness.

## 13. Observability Requirements for Extensions

### 13.1 Structured Logging

**Status:** EXISTING — Source: ADR-012 [Active]; Part 00 §0.4 Principle 12

Every component, including integration extensions, MUST emit structured logs (JSON, correlation IDs) and Events for state transitions (ADR-012).

**Part 14 implication:** Extension implementations MUST emit structured logs through the kernel's logging infrastructure. They MUST NOT use unstructured logging or omit correlation IDs.

---

### 13.2 Extension Observability Isolation

**Status:** GAP — Source: None in Parts 0–13; inference path from ADR-013 [Active] sandboxing requirement

Parts 0–13 require sandboxing for custom Skills (§6.2) but do not specify observability isolation for extensions. ADR-013 requires extensions connect only through extension points; that boundary implies observability separation but does not define a contract name, precondition/postcondition format, or verification method.

**What Parts 0–13 establish:**
- Extensions execute through per-domain Manager extension points (SkillManager, MCPManager, etc.)
- Structured logging is required (ADR-012 [Active])
- Event emission for state transitions is required (ADR-012 [Active])

**What Parts 0–13 do NOT establish:**
- A named observability-isolation contract for extensions
- Observability data isolation between extension execution and core runtime observations
- Cross-extension data-leakage prevention mechanism
- Verification method for extension observability isolation

**Classification:** GAP. The desired property (observability isolation) is inferable from ADR-013's extension-point boundary, but no source in Parts 0–13 defines a contract, mechanism, or verification approach.

**Part 14 implication:** Integration extensions SHOULD emit observability data in isolated compartments. The isolation mechanism is UNSPECIFIED.

## 14. AI Agent Guidance for Extension Development

### 14.1 Inspection Requirement

**Status:** EXISTING — Source: Part 14 README §For Future AI Agents; Part 00 §0.5.2

Future AI agents developing or integrating extensions MUST:
1. Inspect Part 00 §0.5.2 before assuming any extension point exists
2. Inspect the specific Part governing the target domain (Part 4 for Memory, Part 4.8 for MCP, Part 4.9 for Consensus, etc.) before implementing an extension
3. Verify the extension point is in the Part 00 §0.5.2 list — if it is not, it is NOT a permitted extension point

### 14.2 PROPOSED/FUTURE Distinction

**Status:** EXISTING — Source: Part 14 README §Status Taxonomy

AI agents MUST distinguish:
- **EXISTING** extension points: The 8 listed in Part 00 §0.5.2, governed by ADR-013 [Active]
- **DERIVED** extension behavior: Inferred from EXISTING statements with visible inference path
- **PROPOSED** mechanisms: Recommendations for resolving GAPs (e.g., plugin semver rules, hot loading)
- **FUTURE** mechanisms: Explicitly deferred to v2.0 (e.g., distributed EventBus)
- **UNSPECIFIED** mechanisms: Source Parts are silent (e.g., plugin manifest, discovery, dependency resolver)
- **GAP** items: Partially defined (e.g., GAP-EXT: custom event registration mechanism)

AI agents MUST NOT:
- Promote PROPOSED mechanisms to EXISTING status
- Treat FUTURE mechanisms as v1.0 architecture
- Invent UNSPECIFIED mechanisms
- Silently resolve CONFLICTs
- Create new extension points not in Part 00 §0.5.2

### 14.3 Traceability Requirement

**Status:** EXISTING — Source: Part 14 README §Source-of-Truth Rules

Every claim about extension mechanisms MUST cite a source Part or approved ADR. If no source exists, the claim MUST be labeled UNSPECIFIED or GAP.

Future AI agents consuming this chapter MUST:
- Read every mechanism's status label before assuming it is available

- Resolve CONFLICT-EXT-01 by choosing one source over the other

Future AI agents MUST propose changes via ADR, not by modifying this chapter directly. All changes to extension architecture MUST go through the ADR process (Part 00 §0.5.3) and ARB review.
