## 1. Agent Governance Model

**Agent governance** is the system of rules, processes, and authorities that ensure AI-OS agents operate within defined boundaries of authority, capability, and behavior. It encompasses the full lifecycle of agents — from registration and capability issuance to operation, monitoring, and decommissioning.

### 1.1 Scope

Agent governance covers:

- **Agent identity**: Registration, provisioning, and lifecycle management of agent identities.
- **Capability issuance**: Granting, revoking, and auditing capabilities available to agents.
- **Capability usage**: Monitoring and controlling how agents use their capabilities.
- **Behavioral governance**: Ensuring agent behavior conforms to policies and governance invariants.
- **Authority delegation**: Managing authority delegation to agents and between agents.
- **Accountability**: Binding agent actions to accountable principals.

### 1.2 Governance Principles

| Principle | Description |
|-----------|-------------|
| **Identity-First** | Every agent must have a verifiable identity before any capability is granted. |
| **Least Capability** | Agents receive only the capabilities necessary for their function, no more. |
| **Explicit Authority** | Every agent action must be traceable to an explicit authority grant. |
| **Behavioral Bounds** | Agent behavior is governed by policies evaluated before action execution. |
| **Continuous Monitoring** | Agent activities are continuously monitored for governance conformance. |
| **Immutable Audit** | All agent governance actions produce immutable audit events. |
| **Accountability Binding** | Every agent action has a responsible principal, traceable through delegation. |

## 3. Agent Identity Governance

### 3.1 Agent Registration

Every agent must be registered before it can operate within AI-OS:

1. **Agent Registration Request**: An authorized principal submits an agent registration request.
2. **Identity Verification**: The agent's identity is verified and bound to a principal (Part 1, Part 5).
3. **Authority Grant**: The registering authority grants initial operational authority to the agent.
4. **Capability Assignment**: Initial capabilities are assigned (may be empty for new agents).
5. **Registry Record**: G-03 records the agent as a registered entity.
6. **Audit Event**: G-09 records the registration with full attribution.

### 3.2 Agent Identity Schema

Agent identity is defined through the integration of:

- **Part 1 Principal Model**: Agent identity is a principal with unique identifier.
- **Part 5 Principal Allocation**: Agent is allocated to appropriate groups and hierarchies.
- **G-05 Authority Grant**: Agent receives operational authority via an authority grant.
- **G-10 Accountability Binding**: All agent actions are bound to the registering principal.

### 3.3 Agent Identity Lifecycle

```text
CREATED → PROVISIONED → ACTIVE → SUSPENDED → REVOKED → ARCHIVED
                    ↘ FAILED (terminal)
```

| State | Description |
|-------|-------------|
| **CREATED** | Registration request submitted; identity pending verification. |
| **PROVISIONED** | Identity verified; initial authority granted; capabilities pending. |
| **ACTIVE** | Agent is fully operational with granted capabilities and authority. |
| **SUSPENDED** | Agent temporarily non-operational (e.g., during investigation). |
| **REVOKED** | Agent identity permanently removed; all capabilities and authority revoked. |
| **ARCHIVED** | Retention-only state; identity and governance metadata preserved. |
| **FAILED** | Registration failed; terminal state. |

### 3.4 Agent Identity Revocation

Agent identity revocation triggers a cascade:

1. All active capabilities are revoked.
2. All authority grants are suspended.
3. Active sessions are terminated.
4. Delegation chains referencing the agent are invalidated.
5. Audit events record the revocation with full attribution.

## 4. Capability Governance

### 4.1 Capability Definition

**Capabilities** are discrete operational abilities that agents can exercise. They are the fundamental units of agent operational authority.

### 4.2 Capability Schema

Capabilities are defined through:

| Field | Type | Description |
|-------|------|-------------|
| `capabilityId` | string (UUID v4) | Unique identifier. |
| `name` | string | Human-readable name. |
| `version` | string | Semantic version. |
| `description` | string | Detailed description of what the capability enables. |
| `category` | string | Capability category (data_access, model_execution, system_operation, etc.). |
| `scope` | string | `global`, `system`, `workflow`, `agent_group`, `agent`. |
| `requiredApprovals` | array[string] | Approval requirements for issuance. |
| `riskLevel` | string | `low`, `medium`, `high`, `critical`. |
| `constraints` | array[string] | Usage constraints and limitations. |
| `dependencies` | array[string] | Other capabilities required. |
| `effectiveFrom` | string (ISO 8601) | When the capability becomes effective. |
| `effectiveUntil` | string (ISO 8601) or null | When the capability expires. |
| `createdBy` | string | Principal that defined the capability. |
| `createdAt` | string (ISO 8601) | Creation timestamp. |
| `updatedAt` | string (ISO 8601) | Last update timestamp. |

### 4.3 Capability Issuance

Capability issuance is the process of granting a capability to an agent:

1. **Request**: Agent or principal requests capability issuance.
2. **Authority Check**: G-05 validates that the requesting principal has authority to issue the capability.
3. **Approval**: If the capability requires approval, G-12 routes and records the approval.
4. **Grant Creation**: G-05 creates a capability authority grant for the agent.
5. **Registry Update**: G-03 records the capability grant.
6. **Audit Evidence**: G-09 records the issuance with full attribution.

### 4.4 Capability Types

| Type | Description | Risk Level | Approval Required |
|------|-------------|------------|-------------------|
| **Read** | Read-only access to resources. | Low | No |
| **Write** | Modify or create resources. | Medium | Yes |
| **Execute** | Execute operations or workflows. | Medium | Yes |
| **Configure** | Modify system or agent configuration. | High | Yes |
| **Administer** | Full administrative control. | Critical | Yes (supermajority) |
| **Specialized** | Domain-specific capabilities (e.g., model deployment). | Variable | Per charter |

### 4.5 Capability Revocation

Capabilities can be revoked through:

- **Explicit revocation**: Authority holder revokes the capability.
- **Expiration**: Capability's `effectiveUntil` is reached.
- **Agent suspension**: Agent identity suspended invalidates all capabilities.
- **Policy violation**: A governance violation triggers automatic capability revocation.
- **Risk escalation**: A risk escalation triggers precautionary capability revocation.

## 5. Agent Lifecycle Governance

### 5.1 Lifecycle Overview

Agent lifecycle governance ensures agents progress through defined states with appropriate governance checks at each transition:

```text
Registration → Provisioning → Activation → Operation → Monitoring → 
  Decommissioning → Archival
```

### 5.2 Lifecycle Phases

| Phase | Description | Key Governance Checks |
|-------|-------------|----------------------|
| **Registration** | Agent identity creation and verification. | Identity verification, principal binding, initial authority grant. |
| **Provisioning** | Capability and authority assignment. | Authority validation, capability approval routing. |
| **Activation** | Agent becomes operational. | Final policy evaluation, capability validation, audit record. |
| **Operation** | Agent performs tasks. | Continuous policy evaluation, authority resolution per action. |
| **Monitoring** | Ongoing governance assessment. | Behavior monitoring, compliance checking, risk assessment. |
| **Decommissioning** | Agent is taken out of service. | Capability revocation, session termination, final audit. |
| **Archival** | Governance metadata preserved. | Audit trail preservation, identity retention. |

### 5.3 Lifecycle Governance Events

Each lifecycle transition produces governance events:

- `AgentCreated` / Agent registration
- `AgentProvisioned` / Capability and authority assigned
- `AgentActivated` / Agent becomes operational
- `AgentSuspended` / Temporary non-operation
- `AgentReactivated` / Resumes operation
- `AgentRevoked` / Permanent removal
- `AgentDecommissioned` / Clean shutdown
- `AgentArchived` / Retention-only

## 6. Agent Authority and Delegation

### 6.1 Authority Model for Agents

Agents hold authority through the same hierarchical model as governance bodies (see [13.4](./13.4-Decision-Authority-and-Delegation.md)):

| Level | Source | Agent Role |
|-------|--------|-----------|
| **Supreme** | Organization leadership | Reserved for system-wide agent governance policy. |
| **System** | Governance framework, Security Council | Defines agent capability categories and risk levels. |
| **Domain** | Domain stewards | Domain-specific agent authority and capabilities. |
| **Operational** | Agent operators | Individual agent authority grants. |
| **Emergency** | Incident commanders | Emergency override for agent control. |

### 6.2 Authority Validation

Every agent action undergoes authority validation:

1. **Action Request**: Agent requests to execute an action.
2. **Authority Resolution**: G-05 resolves whether the agent has authority for the action.
3. **Delegation Check**: G-06 validates any delegation chain supporting the authority.
4. **Policy Evaluation**: G-02 evaluates applicable policies given the agent's authority.
5. **Decision**: Action permitted or denied based on combined authority and policy results.

### 6.3 Agent-to-Agent Delegation

Agents can delegate authority to other agents under specific constraints:

- **Explicit grant**: Delegation must be explicitly authorized by the agent's principal.
- **Scope limitation**: Delegation cannot exceed the delegating agent's scope.
- **Temporal limitation**: Delegation must have defined start and end times.
- **Audit requirement**: All delegations are recorded as immutable events.
- **Revocation**: Delegations can be revoked, invalidating downstream chains.

### 6.4 Delegation Schema for Agents

Agent-to-agent delegation uses the Delegation Schema (see [schemas.md §Delegation Schema](./schemas.md)):

| Field | Type | Description |
|-------|------|-------------|
| `delegatorId` | string | The delegating agent's ID. |
| `delegatorType` | string | Must be `agent`. |
| `delegateeId` | string | The receiving agent's ID. |
| `delegateeType` | string | Must be `agent`. |
| `authorityId` | string (UUID v4) | The specific authority being delegated. |
| `scope` | string | Applicability scope of the delegation. |
| `limitations` | array[string] | Specific constraints. |
| `effectiveFrom` | string (ISO 8601) | Start of delegation validity. |
| `effectiveUntil` | string (ISO 8601) or null | End of delegation validity. |

## 7. Agent Behavior Governance

### 7.1 Behavioral Policies

Agents' behavior is governed by policies that are evaluated before action execution:

- **Ethical policies**: Ensure agent behavior aligns with ethical standards.
- **Security policies**: Prevent unauthorized access and data exposure.
- **Operational policies**: Ensure agent actions conform to operational procedures.
- **Compliance policies**: Ensure agent behavior meets regulatory requirements.

### 7.2 Behavior Monitoring

Continuous monitoring of agent behavior includes:

- **Action logging**: Every agent action is logged with full context.
- **Policy evaluation auditing**: Evaluation results are recorded for compliance.
- **Anomaly detection**: Deviations from expected behavior patterns are flagged.
- **Risk assessment**: Agent behavior is assessed for risk implications.

### 7.3 Behavioral Enforcement

When an agent's behavior violates governance requirements:

1. **Policy Evaluation**: G-02 detects a policy violation.
2. **Violation Recording**: G-09 records the violation as an audit event.
3. **Risk Identification**: G-07 may identify a risk from the violation.
4. **Authority Impact**: G-05 may suspend the agent's authority.
5. **Remediation**: The agent's behavior is corrected or the agent is decommissioned.

## 8. Agent Accountability

### 8.1 Accountability Model

Every agent action is attributable to a principal through the accountability model:

| Element | Description |
|---------|-------------|
| **Actor** | The agent performing the action. |
| **Principal** | The human or system principal the agent acts on behalf of. |
| **Evidence** | The authority grant or delegation that supports the action. |
| **Bound At** | The timestamp when the binding was established. |

### 8.2 Accountability Binding

Accountability bindings are managed by G-10 (Accountability Manager):

1. **Binding Request**: When an agent acts, G-10 binds the action to the responsible principal.
2. **Evidence Verification**: G-10 verifies that evidence (authority grant, delegation) supports the action.
3. **Binding Record**: The binding is recorded as an immutable audit event.
4. **Chain Verification**: If delegation is involved, G-10 verifies the full delegation chain.

### 8.3 Accountability Gaps

An **accountability gap** occurs when an agent action cannot be bound to a principal:

- **Detection**: G-10 flags the action as having no accountable principal.
- **Escalation**: G-00 escalates the issue for investigation.
- **Remediation**: The agent's authority is suspended pending resolution.
- **Audit Finding**: The gap is recorded as an audit finding in G-09.

Every governance action MUST have at least one bound principal — accountability gaps are governance violations.

| **L1-L3** | Individual Agent | Agent self-monitoring, local policy evaluation. |

| **L8** | Domain/System | System-wide agent capabilities, cross-domain authority. |
| **L9-L11** | Governance | Full agent lifecycle governance, capability issuance standards. |

### 9.1 Conformance Levels

| Level | Name | Agent Governance Application |

| **L10** | Self-Healing | Agents can autonomously remediate governance violations. |
| **L11** | Self-Adaptive | Agents adapt their behavior based on governance feedback. |

| Event | Purpose | Producer |
|-------|---------|----------|
| `governance.agent.action` | Agent performed an action. | Agent Runtime |
| `governance.agent.action.denied` | Agent action was denied by policy. | Policy Evaluation Engine |

## 12. Risk and Compliance in Agent Governance

### 12.1 Agent-Related Risks

Key risks in agent governance include:

| Risk | Category | Owner | Mitigation |
|------|----------|-------|------------|
| Unauthorized capability usage | Security | Security Council | Capability usage monitoring, policy enforcement. |
| Capability escalation | Security | Security Council | Least capability principle, approval workflows. |
| Agent behavior violation | Operational | Agent Governance Lead | Policy evaluation per action, anomaly detection. |
| Authority chain failure | Operational | Agent Governance Lead | Delegation chain validation, audit trails. |
| Accountability gaps | Compliance | Audit Lead | Mandatory principal binding, gap detection. |
| Credential compromise | Security | Security Council | Credential rotation, agent identity revocation. |

### 12.2 Compliance Obligations

Agent governance must satisfy compliance obligations:

- **GDPR**: Agent handling of personal data must be auditable and revocable.
- **SOC 2**: Agent access controls must be logged and monitored.
- **ISO 27001**: Agent behavior must conform to security policies.
- **Internal policies**: Agents must operate within defined capability and authority bounds.

### 12.3 Risk Treatment

Agent-related risks are treated through:

- **G-07 Risk Manager**: Risk identification, assessment, and treatment tracking.
- **G-08 Compliance Manager**: Compliance obligation tracking and evidence collection.
- **G-13 Control Manager**: Control design and testing for agent governance controls.
- **G-15 Conformance Manager**: Conformance evaluation against agent governance standards.

## 13. Governance Constraints

### 13.1 Capability Constraints

- **No implicit capabilities**: Agents must have explicit capability grants; implicit capabilities are prohibited.
- **No self-grant**: Agents cannot grant capabilities to themselves; all grants require explicit authority.
- **No escalation**: Agents cannot escalate their capabilities beyond their authority.
- **No orphan capabilities**: Capabilities must trace to a valid authority grant; orphaned capabilities are automatically revoked.
- **Temporal bounds**: All capabilities have a defined lifetime; perpetual capabilities require explicit renewal.

### 13.2 Authority Constraints

- **No self-authority**: Agents cannot validate their own authority grants.
- **Chain of custody**: Every authority grant must be traceable to a trusted root via immutable delegation chains.
- **Scope fidelity**: Authority grants cannot exceed the scope of their source.
- **Maximum lifetime**: Authority grants have maximum lifetimes defined by governing policy.

### 13.3 Accountability Constraints

- **Mandatory binding**: Every governance action MUST have at least one bound principal.
- **Immutable records**: Accountability bindings are immutable once recorded.
- **Gap detection**: Accountability gaps MUST be detected and escalated.
- **Principal validity**: Bound principals must be valid (not suspended or revoked) at the time of action.

### 13.4 Compliance Constraints

- **Evidence authenticity**: All governance evidence MUST be verifiable (hash-chained or signed).
- **RTBF compliance**: Right to be forgotten requests MUST be honored within agent governance scope.
- **Audit retention**: Agent governance audit records MUST be retained per compliance requirements.

## 15. Cross-Part Integration

Agent and capability governance integrates across AI-OS parts:

| Part | Integration |
|------|-------------|
| **Part 1** | Principal identity model — agents are principals with unique identifiers. |
| **Part 5** | Principal allocation model — agents are allocated to groups and hierarchies. Authority grants reference Part 5 allocations. |
| **Part 6** | Governance committees — Agent Governance Committee and Capability Governance Committee charter definitions. |
| **Part 8** | Agent management — agent lifecycle hooks for governance integration. |
| **Part 10** | AI runtime — workload scheduling and isolation boundaries governed by capability constraints. |
| **Part 12** | Audit model — agent governance records are audit artifacts. |

### 15.1 Bootstrap Agent Governance

During system bootstrap, agent governance is initialized through a declared root principal (platform authority) with artifact backing in G-03. Initial setup includes:

- Bootstrap agent authority grants (minimal capabilities for system initialization).
- Capability category definitions (read, write, execute, configure, administer).
- Agent behavior policy package.
- Accountability binding rules.

No delegation occurs during bootstrap — all initial grants are direct authority grants.

### 15.2 Part 5 Principal Allocation

Part 5 defines the hierarchy of principals and groups. Agents are registered as principals in Part 5, with group memberships and role assignments that determine their governance context. G-05 records the runtime expression of these allocations — it does not create them, it enforces them.
