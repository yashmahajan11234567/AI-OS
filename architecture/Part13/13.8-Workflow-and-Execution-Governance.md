## 1. Workflow Governance Model

**Workflow governance** is the system of rules, processes, and authorities that ensure AI-OS workflows are defined, configured, executed, and governed in alignment with organizational policies, security requirements, and compliance obligations.

### 1.1 Scope

Workflow governance covers:

- **Workflow definition**: Policy compliance and approval for workflow structures and configurations.
- **Workflow execution**: Governance enforcement during workflow runtime.
- **Governance session management**: The orchestration and lifecycle of governance sessions that wrap workflow operations.
- **Approval integration**: Routing workflow-related decisions through formal approval processes.
- **Authority enforcement**: Ensuring only authorized principals can define, modify, or execute workflows.
- **Auditability**: Immutable records of all workflow governance actions.
- **Risk management**: Identification and treatment of workflow-related risks.

### 1.2 Governance Principles

| Principle | Description |
|-----------|-------------|
| **Pre-Execution Governance** | All workflow executions must pass through a governance session before action. |
| **Policy Alignment** | Workflow definitions must conform to organizational policies. |
| **Explicit Authority** | Every workflow action must be traceable to an explicit authority grant. |
| **Continuous Monitoring** | Workflow execution is continuously monitored for governance conformance. |
| **Immutable Audit** | All workflow governance events produce immutable audit records. |
| **Accountability Tracing** | Every workflow action has a responsible principal, traceable through accountability bindings (G-10). |
| **Least Privilege** | Workflows operate with minimum necessary privileges and capabilities. |

## 3. Workflow Definition Governance

### 3.1 Workflow Definition Lifecycle

Workflow definitions pass through a governed lifecycle:

```text
DRAFT → REVIEW → APPROVED → PUBLISHED → DEPRECATED → RETIRED
               ↘ REJECTED (terminal)
```

| State | Description |
|-------|-------------|
| **DRAFT** | Workflow definition created but not yet submitted for review. |
| **REVIEW** | Workflow definition under review by governance bodies. |
| **APPROVED** | Workflow definition approved for publication. |
| **PUBLISHED** | Workflow definition is active and can be executed. |
| **DEPRECATED** | Workflow definition marked for retirement; no new executions. |
| **RETIRED** | Workflow definition withdrawn; existing executions must complete. |
| **REJECTED** | Workflow definition denied approval; terminal state. |

### 3.2 Definition Approval Process

1. **Creation**: Workflow author creates a draft definition (G-01).
2. **Submission**: Draft is submitted for governance review; G-01 routes approval request to G-12.
3. **Policy Evaluation**: G-02 evaluates the definition against applicable policies (called by G-00 or G-01).
4. **Authority Check**: G-05 validates the author's authority to define workflows (called by G-00).
5. **Review**: Governance body (G-04) reviews the definition.
6. **Decision**: Approval or rejection is recorded via G-12.
7. **Publication**: Approved definition is published to G-03 by G-01 (via `publishPackage`).
8. **Audit**: All steps are recorded in G-09 (via G-14 events).

### 3.3 Definition Constraints

- **Policy conformance**: Workflow definitions must conform to governance policies (e.g., data handling, security controls).
- **Authority validation**: Only authorized principals can submit workflow definitions.
- **Capability bounds**: Workflow definitions must specify required capabilities; these must be within the workflow owner's authority.
- **Temporal bounds**: Workflow definitions have effective dates and review cycles.
- **Compliance alignment**: Workflow definitions must satisfy applicable compliance obligations.

## 4. Workflow Execution Governance

### 4.1 Governance Session Architecture

Every workflow execution is wrapped in a **governance session** orchestrated by G-00 (Governance Manager). Synchronous interfaces are used for required real-time decisions (G-00→G-02 `requestEvaluation`, G-00→G-05 `resolveAuthority`, G-05→G-06 `checkDelegationChain`); all session events are emitted asynchronously through G-14:

```text
Workflow Trigger → G-00 (open session) → 
  Policy Evaluation (G-02, synchronous: requestEvaluation) → 
  Authority Resolution (G-05, synchronous: resolveAuthority) → 
  Delegation Validation (G-06, synchronous: checkDelegationChain via G-05) → 
  Exception Check (G-11, read) → 
  Approval Routing (G-12 if required, synchronous) → 
  Decision → 
  G-00 (close session) → 
  Audit Evidence (G-09, via G-14 event emission)
```

### 4.2 Governance Session Lifecycle

```text
SESSION_OPENED → POLICY_EVALUATED → AUTHORITY_RESOLVED → DELEGATION_VALIDATED → 
  EXCEPTION_CHECKED → (APPROVAL_ROUTED if required) → DECISION_MADE → SESSION_COMPLETED
  ↘ SESSION_FAILED (on any stage failure)
  ↘ SESSION_ESCALATED (on authority resolution failure)
```

### 4.3 Session Components

| Component | Role in Governance Session |
|-----------|----------------------------|
| **G-00 Governance Manager** | Orchestrates the session; maintains session context. |
| **G-02 Policy Evaluation Engine** | Evaluates applicable policies for the workflow action. |
| **G-05 Decision Authority Manager** | Resolves whether the actor has authority for the action (called by G-00 via `resolveAuthority`). |
| **G-06 Delegation Authority Manager** | Validates delegation chains (query from G-05 via `checkDelegationChain`; G-06 exposes `validateChain` for read queries). |
| **G-11 Exception Manager** | Checks for applicable exceptions to policy violations. |
| **G-12 Approval Manager** | Routes for approval if required by policy. |
| **G-09 Audit Manager** | Records the complete session as an immutable audit trail. |
| **G-10 Accountability Manager** | Binds the session to accountable principals (binds actor identity to session). |
| **G-14 Governance Event Manager** | Routes all session events for monitoring and audit persistence. |

### 4.4 Execution Governance Flow

```text
┌─────────────────┐
│Workflow Trigger │
│(from Part 10)   │
└────────┬────────┘
         │
         ▼
┌─────────────────┐ ──openSession──▶ G-03 Registry (get policy snapshot)

┌─────────────────┐ ──readPolicy──▶ G-03 Registry
```

## 5. Governance Authority and Decision Rights

### 5.1 Authority Hierarchy

Workflow governance authority follows the hierarchical authority model (see [13.4](./13.4-Decision-Authority-and-Delegation.md)):

| Level | Source | Workflow Governance Role |
|-------|--------|--------------------------|
| **Supreme** | Organization leadership | Set workflow governance strategy, approve major workflow frameworks. |
| **System** | Governance framework, Workflow Governance Lead | Define workflow governance policies, approval workflows. |
| **Domain** | Domain stewards | Domain-specific workflow authority and capability definitions. |
| **Operational** | Workflow operators, team leads | Individual workflow execution authority. |
| **Emergency** | Incident commanders | Emergency workflow execution and override authority. |

### 5.2 Decision Rights

| Decision Type | Authority Level | Approval Required |
|---------------|-----------------|-------------------|
| **Workflow Definition Approval** | Domain/System | G-12 (via G-04) |
| **Workflow Execution** | Operational | G-00 (session-level) |
| **Workflow Exception** | Operational/Domain | G-12 |
| **Workflow Deprecation** | Domain/System | G-12 |
| **Workflow Emergency Override** | Emergency | G-11 (exception) + G-00 |

### 5.3 Authority Validation

Every workflow execution requires authority validation (preserving the governance session flow):

1. **Actor Identification**: The actor initiating the workflow is identified (via G-10).
2. **Policy Evaluation**: G-02 evaluates applicable policies for the workflow action (called by G-00 via `requestEvaluation`).
3. **Authority Resolution**: G-05 resolves the actor's authority for the workflow action (called by G-00 via `resolveAuthority`).
4. **Delegation Validation**: G-06 validates any delegation chain (G-05 queries G-06 via `checkDelegationChain`).
5. **Policy Violation Resolution**: G-11 checks for applicable exceptions to policy violations.
6. **Decision**: Execution permitted or denied.

## 6. Approval Workflow Integration

### 6.1 Approval Triggers

Workflow governance triggers approval through G-12 (Approval Manager) under these conditions:

| Condition | Approval Required | Routing Target |
|-----------|-------------------|----------------|
| Policy requires approval | Yes | Policy-defined approver |
| Authority threshold exceeded | Yes | Authority-defined approver |
| High-risk workflow | Yes | Risk Committee |
| New workflow definition | Yes | G-04 review |
| Workflow modification | Yes | G-04 review |
| Emergency execution | Yes (post-facto) | Emergency review (see §6.4) |

### 6.2 Approval Process

The approval process for workflow governance:

1. **Request**: G-00 submits an approval request via G-12 for workflow execution when policy requires it; G-01 submits approval requests for workflow definition policies via G-12.
2. **Routing**: G-12 identifies the approval role from G-05.
3. **Notification**: Approver is notified with context and rationale.
4. **Decision**: Approver grants, rejects, or returns with conditions.
5. **Recording**: Decision is recorded in G-03 and G-09.
6. **Execution**: If approved, the workflow proceeds; if rejected, it is halted.

### 6.3 Approval Schema

Approvals are recorded using the Approval Schema (see [schemas.md §Approval Schema](./schemas.md)):

| Field | Type | Description |
|-------|------|-------------|
| `approvalId` | string (UUID v4) | Unique identifier for the approval. |
| `name` | string | Human-readable name for the approval. |
| `version` | string | Semantic version of the approval record. |
| `description` | string | Detailed description of what is being approved. |
| `approvalType` | string | `policy`, `decision`, `delegation`, `exception`, `override`, `audit_finding`, `risk_assessment`. |
| `approvedEntityId` | string | Identifier of the entity being approved. |
| `approvedEntityType` | string | `policy`, `decision`, `delegation`, `exception`, `override`, `audit_finding`, `risk_assessment`. |
| `approverId` | string | Identifier of the approving authority or agent. |
| `approverType` | string | `authority`, `agent`, `governance_body`, `role`. |
| `approvalDecision` | string | `approved`, `denied`, `conditionally_approved`. |
| `conditions` | array[string] | Approval conditions (required if `conditionally_approved`). |
| `justification` | string | Reasoning for the approval decision. |
| `effectiveFrom` | string (ISO 8601) | Timestamp when the approval becomes effective. |
| `effectiveUntil` | string (ISO 8601) or null | Timestamp when the approval expires. |
| `createdBy` | string | AgentId or userId that created the approval record. |
| `createdAt` | string (ISO 8601) | Timestamp when the approval was recorded. |
| `updatedAt` | string (ISO 8601) | Timestamp when the approval was last updated. |
| `tags` | array[string] | Tags for categorization and discovery. |
| `metadata` | object | Arbitrary key-value pairs for approval-specific metadata. |

**Required fields:** `approvalId`, `name`, `version`, `approvalType`, `approvedEntityId`, `approvedEntityType`, `approverId`, `approverType`, `approvalDecision`, `justification`, `effectiveFrom`, `createdBy`, `createdAt`, `updatedAt`.
**Optional fields:** `description`, `conditions`, `effectiveUntil`, `tags`, `metadata`.

### 6.4 Emergency Execution

Emergency execution allows authorized principals (incident commanders) to bypass certain governance requirements during critical incidents, subject to post-facto review:

1. **Authorization**: Emergency authority must be declared by an incident commander with emergency role (G-11 exception type `emergency`).
2. **Bypass**: During emergency execution, policy evaluation and approval routing may be skipped, but authority resolution (G-05) still applies.
3. **Audit**: All emergency executions are recorded as `governance.policy.exception.approved` with emergency flag.
4. **Review**: Emergency executions require post-facto review by the relevant governance committee.
5. **Revocation**: Emergency authority is automatically revoked after a defined time window or when the incident is resolved.

Emergency execution transitions the governance session to `SESSION_SUSPENDED` state (skipping standard policy and approval gates), with the emergency exception recorded through G-11 and audited through G-09.

## 7. Execution Governance Lifecycle

### 7.1 Workflow Execution States

Workflow executions pass through governed states. The governance session (§4.2) occurs within the `GOVERNANCE_REVIEW` state. Terminal states use the `SESSION_` prefix when they refer to session termination:

```text
SUBMITTED → GOVERNANCE_REVIEW → EXECUTION_STARTED → COMPLETED
  ↘ SESSION_FAILED (at any stage)
  ↘ SESSION_ESCALATED (on authority resolution failure)
  ↘ SESSION_SUSPENDED (on emergency)
```

Within `GOVERNANCE_REVIEW`, the governance session lifecycle (§4.2) proceeds:

```text
SESSION_OPENED → POLICY_EVALUATED → AUTHORITY_RESOLVED → DELEGATION_VALIDATED → 
  EXCEPTION_CHECKED → (APPROVAL_ROUTED if required) → DECISION_MADE → SESSION_COMPLETED
```

### 7.2 State Transitions

| State | Transition To | Trigger | Governance Action |
|-------|---------------|---------|-------------------|
| `SUBMITTED` | `GOVERNANCE_REVIEW` | Workflow request received | G-00 opens session (`SESSION_OPENED`) |
| `GOVERNANCE_REVIEW` | `EXECUTION_STARTED` | Governance session completed | Proceeds to execution |
| `EXECUTION_STARTED` | `COMPLETED` | Workflow execution finished | G-09 records final audit |
| `SUBMITTED` | `SESSION_FAILED` | Structural validation failure | Session not opened; recorded as failure |
| Within `GOVERNANCE_REVIEW` (governance session lifecycle per §4.2) | | | |
| `SESSION_OPENED` | `POLICY_EVALUATED` | Policy evaluated | G-02 evaluation via `requestEvaluation` |
| `POLICY_EVALUATED` | `AUTHORITY_RESOLVED` | Authority resolved | G-05 resolution via `resolveAuthority` |
| `AUTHORITY_RESOLVED` | `DELEGATION_VALIDATED` | Delegation chain validated | G-05 calls G-06 via `checkDelegationChain` |
| `DELEGATION_VALIDATED` | `EXCEPTION_CHECKED` | Exception checked | G-11 lookup |
| `EXCEPTION_CHECKED` | `APPROVAL_ROUTED` | Approval required by policy | G-12 routing via G-00 |
| `APPROVAL_ROUTED` | `DECISION_MADE` | Approval granted | Proceeds to decision |
| `EXCEPTION_CHECKED` | `DECISION_MADE` | No approval required, action permitted | Proceeds to decision |
| `AUTHORITY_RESOLVED` | `SESSION_ESCALATED` | Authority unresolved | G-00 escalation |
| `SESSION_COMPLETED` | `EXECUTION_STARTED` | Session closed successfully | Proceeds to execution |
| Any state | `SESSION_SUSPENDED` | Emergency override applied | G-11 emergency exception |
| `SESSION_SUSPENDED` | `SESSION_COMPLETED` | Emergency resolved | Session resumes to completion |
| `POLICY_EVALUATED` | `SESSION_FAILED` | Policy denial | Execution denied; session terminated |
| `AUTHORITY_RESOLVED` | `SESSION_FAILED` | Authority denied | Execution denied; session terminated |
| `APPROVAL_ROUTED` | `SESSION_FAILED` | Approval denied | Execution denied; session terminated |
| Any state | `SESSION_FAILED` | System failure | Governance halt if critical |
| `SESSION_FAILED` | — | Terminal state | Execution denied; audit record complete |

### 7.3 Failure Handling

- **Policy denial**: Session transitions to `SESSION_FAILED`; execution is denied.
- **Authority denial**: Session transitions to `SESSION_FAILED`; execution is denied.
- **Authority unresolved**: Session transitions to `SESSION_ESCALATED`; escalation to G-00.
- **Approval denial**: Action denied; requester notified.
- **System failure**: Session transitions to `SESSION_FAILED`; governance halt if critical.

## 8. Policy Enforcement in Workflows

### 8.1 Policy Evaluation Points

Policy evaluation occurs at multiple points in the workflow lifecycle:

| Point | Policies Evaluated | Component |
|-------|-------------------|-----------|
| **Pre-execution** | Workflow execution policies, security policies, data handling policies | G-02 |
| **During execution** | Behavioral policies, capability usage policies | G-02 |
| **Post-execution** | Output validation policies, audit policies | G-02 |
| **Definition time** | Workflow definition policies, capability policies | G-02 |

### 8.2 Enforcement Modes

Workflow governance supports multiple enforcement modes (see [13.3 Policy Architecture](./13.3-Policy-Architecture.md) §Policy Enforcement):

| Mode | Description | Workflow Application |
|------|-------------|---------------------|
| **Blocking** | Action denied if policy not satisfied. | High-security workflow actions. |
| **Advisory** | Warning issued; action permitted. | Development and testing workflows. |
| **Logging** | Action permitted; logged for audit. | Low-risk monitoring workflows. |
| **Conditional** | Action permitted with conditions. | Approval-required workflows. |

### 8.3 Policy Precedence

Policy precedence in workflow governance follows the defined hierarchy (see [13.3 §4](./13.3-Policy-Architecture.md)):

1. **Explicit override** flag
2. **Scope specificity**
3. **Precedence weight**
4. **Policy type priority**
5. **Version recency**
6. **Deterministic tiebreak**

## 9. Workflow Authority and Delegation

### 9.1 Authority for Workflow Operations

Workflow authority is managed through G-05 and G-06:

| Operation | Authority Level | Required |
|-----------|-----------------|----------|
| Define workflow | Domain | Role-based (workflow designer) |
| Execute workflow | Operational | Role-based (workflow executor) |
| Modify workflow | Domain | Role-based + approval |
| Approve workflow | System/Domain | Committee-designated |
| Emergency override | Emergency | Emergency authority |

### 9.2 Workflow Delegation

Workflows can delegate execution rights to other principals:

1. **Workflow-level delegation**: The workflow defines what capabilities can be delegated.
2. **Execution delegation**: Authority to execute is delegated via G-06.
3. **Scope limitation**: Delegation is scoped to the workflow's defined boundaries.
4. **Temporal limitation**: Delegation has defined start/end times.
5. **Audit requirement**: All delegations are audited.

### 9.3 Delegation Constraints

- Delegation cannot exceed the delegating principal's authority.
- Delegation must be within the workflow's defined scope.
- Delegation chains must be validated by G-06.
- Delegation must be recorded in G-03.

## 10. Workflow Accountability

### 10.1 Accountability Model

Every workflow execution is attributable through the accountability model:

| Element | Description |
|---------|-------------|
| **Actor** | The principal initiating the workflow. |
| **Agent** | The agent (if any) executing workflow steps. |
| **Session** | The governance session wrapping the execution. |
| **Authority** | The authority grant supporting the execution. |
| **Evidence** | Immutable records of all actions and decisions. |

### 10.2 Accountability Binding

Accountability bindings are managed by G-10:

1. **Session Binding**: The governance session is bound to the initiating principal.
2. **Action Binding**: Each workflow step is bound to the executing agent.
3. **Authority Binding**: The authority grant is bound to the session.
4. **Evidence Chain**: All bindings are linked through immutable events.

### 10.3 Accountability Gap Handling

- **Detection**: G-10 flags workflow actions with no accountable principal.
- **Escalation**: G-00 escalates accountability gaps for investigation.
- **Remediation**: Workflow execution is suspended pending resolution.
- **Audit**: Gaps are recorded as audit findings in G-09.

## 11. Risk and Compliance in Workflow Governance

### 11.1 Workflow-Related Risks

| Risk | Category | Owner | Mitigation |
|------|----------|-------|------------|
| Unauthorized workflow execution | Security | Security Council | Authority validation, policy enforcement. |
| Workflow capability escalation | Security | Security Council | Least privilege, capability bounds. |
| Workflow behavior violation | Operational | Workflow Governance Lead | Policy evaluation per step. |
| Approval bypass | Operational | Workflow Governance Lead | Mandatory approval routing. |
| Data exposure through workflows | Data | Data Governance Lead | Data handling policies, audit. |
| Compliance violation | Compliance | Compliance Owner | Compliance policy evaluation. |

### 11.2 Compliance Obligations

Workflow governance must satisfy compliance obligations:

- **SOX**: Workflow changes must be approved and audited.
- **GDPR**: Workflows handling personal data must have data protection policies.
- **ISO 27001**: Workflow execution must follow security procedures.
- **HIPAA**: Healthcare workflows must have data access controls.

### 11.3 Risk Treatment

Workflow-related risks are treated through:

- **G-07 Risk Manager**: Risk identification and assessment.
- **G-08 Compliance Manager**: Compliance obligation tracking.
- **G-13 Control Manager**: Control design for workflow governance.
- **G-15 Conformance Manager**: Conformance evaluation against workflow governance standards.

## 12. Governance Constraints

### 12.1 Workflow Constraints

- **No implicit execution**: Workflow execution requires explicit authority grant.
- **No capability escalation**: Workflows cannot escalate capabilities beyond their authority.
- **No policy bypass**: All workflow executions must pass policy evaluation.
- **No silent failure**: Workflow execution failures must be audited and reported.
- **No orphaned workflows**: Workflows must trace to a governing authority; orphaned workflows are suspended.

### 12.2 Authority Constraints

- **No self-execution**: Workflows cannot execute themselves without explicit authority.
- **Scope fidelity**: Workflow authority cannot exceed the authority of the defining principal.
- **Temporal bounds**: Workflow execution authority has defined lifetimes.
- **Delegation limits**: Workflow delegation depth is bounded (default: 4).

### 12.3 Audit Constraints

- **Complete logging**: Every workflow execution step is logged.
- **Immutable records**: Audit records are immutable and tamper-evident.
- **RTBF compliance**: Right to be forgotten requests honored within workflow audit scope.

## 13. Workflow Governance Events

Workflow governance events are routed through G-14 (Governance Event Manager) and integrate with Part 12 eventing. Workflow governance leverages the canonical governance event taxonomy defined in [governance-events.md](./governance-events.md); there is no separate `governance.workflow.*` namespace. The table below maps each workflow governance lifecycle point to its canonical `governance.*` event.

### 13.1 Workflow Definition Lifecycle Events

Workflow definition lifecycle events are routed through G-14 via the canonical `governance.policy.*` events (the policy aggregate governs workflow definition policy artifacts) and `governance.approval.*` events (when approval routing is required):

| Lifecycle Point | Canonical Event | Purpose | Producer |
|---|---|---|---|
| New workflow definition created | `governance.policy.created` | A new workflow definition artifact has been drafted and registered. | Policy Service (G-01) via G-14 |
| Workflow definition submitted for review | `governance.policy.submitted` + `governance.approval.requested` | Definition entered review / pending-approval state; approval routing initiated. | G-01 → G-12, emitted via G-14 |
| Workflow definition approved | `governance.policy.approved` | Definition formally approved by authorized governance body. | G-12, emitted via G-14 |
| Workflow definition rejected | `governance.decision.rejected` | Definition rejected at review; recorded as a governance decision. | G-12 / G-04, emitted via G-14 |
| Workflow definition published | `governance.policy.activated` | Definition promoted to active/published state for execution. | G-01, emitted via G-14 |
| Workflow definition deprecated | `governance.policy.deprecated` | Definition marked for retirement; no new executions. | G-01, emitted via G-14 |
| Workflow definition retired | `governance.policy.retired` | Definition withdrawn; existing executions must complete. | G-01, emitted via G-14 |
| Workflow definition validation failure | `governance.policy.validation.failed` | Definition failed structural validation at draft/submit time. | G-01, emitted via G-14 |

### 13.2 Workflow Execution Events

Workflow execution events are emitted through G-14 by the governance session orchestrator and enforcement components:

| Event | Purpose | Producer |
|-------|---------|----------|
| `governance.audit.started` | Governance session (audit scope) opened for workflow execution. | G-00 Governance Manager via G-14 |
| `governance.decision.created` | Governance decision record created for workflow execution result. | G-00 Governance Manager via G-14 |
| `governance.policy.violation.detected` | Policy violation detected during workflow execution. | G-02 Policy Evaluation Engine via G-14 |
| `governance.audit.completed` | Governance session (audit scope) closed for workflow execution. | G-00 Governance Manager via G-14 |
| `governance.policy.exception.requested` / `governance.policy.exception.approved` | Exception requested or applied to workflow execution. | G-11 Exception Manager via G-14 |
| `governance.conformance.failed` | Workflow execution failed conformance check. | G-15 Conformance Manager via G-14 |

> **Note:** Workflow execution steps (individual step execution, suspension, escalation) are operating-context observations that feed the governance session. They are recorded as audit evidence within the session record (via `governance.audit.started` / `governance.audit.completed` envelope events) rather than emitted as standalone canonical governance events.

### 13.3 Governance Decision Events

Governance decision events for workflow execution are recorded through the canonical `governance.decision.*` and `governance.approval.*` / `governance.authority.*` aggregates:

| Lifecycle Point | Canonical Event | Purpose | Producer |
|---|---|---|---|
| Policy evaluation completed | `governance.decision.created` (with evaluation result in payload) | Policy evaluation outcome recorded for workflow. | G-02 Policy Evaluation Engine via G-14 |
| Authority resolved | `governance.authority.delegated` (resolution record) | Authority chain validated for workflow execution actor. | G-05 / G-06 via G-14 |
| Approval requested | `governance.approval.requested` | Approval routed for workflow action. | G-12 Approval Manager via G-14 |
| Approval granted | `governance.approval.granted` | Approval granted for workflow action. | G-12 Approval Manager via G-14 |
| Approval rejected | `governance.approval.rejected` | Approval rejected for workflow action. | G-12 Approval Manager via G-14 |
| Exception applied | `governance.policy.exception.approved` | Exception applied to workflow execution. | G-11 Exception Manager via G-14 |

## 14. Integration with Governance Components

Workflow and execution governance integrates with Part 13 components:

| Component | Workflow Governance Integration |
|-----------|----------------------------------|
| **G-00 Governance Manager** | Central orchestrator — opens governance sessions for workflow executions, coordinates all governance stages. |
| **G-01 Policy Manager** | Manages workflow governance policies: creates, versions, and routes workflow definition policies through approval; packages policies via `publishPackage` to G-03 for canonical storage; G-02 and G-08 read from G-03. |
| **G-02 Policy Evaluation Engine** | Evaluates policies at runtime for workflow executions (called by G-00 via `requestEvaluation`); does not create or modify policies. |
| **G-03 Governance Registry** | Stores workflow definitions, execution policies, workflow authority grants. |
| **G-04 Governance Council** | Defines workflow governance charter, approves workflow frameworks. |
| **G-05 Decision Authority Manager** | Resolves actor authority for workflow executions via `resolveAuthority` (called by G-00); invokes G-06 for chain validation. |
| **G-06 Delegation Authority Manager** | Validates delegation chains via `checkDelegationChain` query (from G-05); records delegation grants in G-03. |
| **G-07 Risk Manager** | Assesses workflow-related risks, monitors risk from workflow execution. |
| **G-08 Compliance Manager** | Tracks workflow compliance obligations, collects workflow compliance evidence. |
| **G-09 Audit Manager** | Records all workflow governance actions as immutable audit entries. |
| **G-10 Accountability Manager** | Binds workflow actions to accountable principals. |
| **G-11 Exception Manager** | Manages workflow execution exceptions, emergency overrides. |
| **G-12 Approval Manager** | Routes approval requests for workflow definitions (from G-01), workflow execution decisions (from G-00), and exceptions (from G-11); records decisions as Approval Schema artifacts in G-03. |
| **G-13 Control Manager** | Designs controls for workflow governance, tests effectiveness. |
| **G-14 Governance Event Manager** | Receives and classifies all `governance.*` events from all components; routes events to G-09 for audit persistence and to subscribers. |
| **G-15 Conformance Manager** | Evaluates workflow governance conformance. |

## 15. Cross-Part Integration

Workflow and execution governance integrates across AI-OS parts:

| Part | Integration |
|------|-------------|
| **Part 1** | Principal identity for workflow initiators and executors. |
| **Part 5** | Principal allocation for workflow authority and capability assignment. |
| **Part 7** | AI Core — model execution within governed workflows. |
| **Part 10** | AI Runtime — workload scheduling and isolation under governance. |
| **Part 12** | Collaboration — council decision mechanisms for workflow approval; event envelope for workflow governance events. |

### 15.1 Bootstrap Workflow Governance

During system bootstrap, workflow governance is initialized through a declared root principal:

1. Bootstrap workflow authority grants.
2. Initial workflow definition policies.
3. Workflow execution policies.
4. Approval routing rules for workflow definitions.

### 15.2 Part 5 Principal Allocation

Part 5 defines the hierarchy of principals and groups. Workflow executors and workflow definition authors are allocated to appropriate groups in Part 5. G-05 validates these allocations at runtime.

### 15.3 Part 12 Collaboration Integration

Part 12 provides collaboration session mechanisms that workflows use for multi-agent coordination. Workflow governance ensures these collaboration sessions conform to governance policies through G-02 policy evaluation and G-05 authority checks.
